## Exact current approval/config/channel constraints

At the pin, `integration-service/migrations/005_source_registry.sql` defines:

- `control.source_registry` keyed by `(tenant_key,source_id)` with `lifecycle`, `current_config_revision`, mapping/identity mapping revisions, `data_owner_user_id`, and `owner_revision`. There is no pending config pointer or switch state.
- Immutable-style revision relations `source_config_revision`, `source_mapping_revision`, and `source_identity_mapping_revision`, each keyed by `(tenant_key,source_id,revision)` and storing JSON plus a 32-byte digest.
- `source_test_report` keyed by UUID and binding config/mapping/identity revisions and digests, source credential revision/generation, endpoint-profile digest, data contract, report and PASS/FAIL. Its foreign keys bind the revision rows; it has no uniqueness preventing multiple historical reports.
- `source_owner_approval` keyed only by UUID. It stores owner ID/revision; config/mapping/identity revisions and digests; credential revision/generation; endpoint-profile digest; data contract and test report. It has ordinary source/Owner FKs but no business-key UNIQUE constraint and no channel ID/epoch or reconciliation digest. Thus the current source approval table itself has no approval uniqueness conflict. API code must always pass/check the exact approval ID and bound proof; do not assume a uniqueness constraint exists.
- `source_channel` permits state `pending`, `active`, `retired`; identity tuple is `(tenant,source,entity,connector,mode,version_domain,channel_epoch)`. It has `UNIQUE(tenant,source,entity,channel_epoch)` and partial unique index `source_channel_one_active_primary_idx` on `(tenant,source,entity)` where state is `active`. Trigger `guard_source_channel_identity` rejects identity tuple changes and prohibits moving `retired` back to another state. A pending row may transition to active if immutable identity is unchanged. Existing `lock_source_channel` returns only the active row and first takes the global security guard. No current service creates or consumes pending rows.

`source-registry/service.ts` update requires `source:write`, locks the current source/security state, and rejects connector/mode/version-domain change while any active or pending source channel exists (`SOURCE_SWITCH_UNAVAILABLE`). For an ordinary config change it inserts a new revision, makes it `current_config_revision`, sets ACTIVE to PAUSED (otherwise DRAFT), updates source credential revision/scope/secret ref, and records epoch change as appropriate. This replaces current configuration; it is not a pending-channel path.

`test()` accepts only the current config revision and stores the probe result. `approve()` requires expected revision to equal current revision and lifecycle TESTED, requires current enabled exact `data_owner_user_id` plus `source:approve`, validates the latest PASS report and all current revisions/digests/profile, inserts a normal `source_owner_approval`, and changes lifecycle to APPROVED. It does not bind channel/reconciliation digest. API routes are existing `/hub/v1/admin/sources/:id/test`, `/approve`, `/activate` and `/pause`; current approve accepts exactly `{revision,test_report_id,data_contract_ref}`, and activate exactly `{revision,approval_id}`.

`activate()` accepts only current revision in APPROVED or PAUSED, revalidates existing Owner approval/test/current credential/config/mapping/profile, and locks each channel. It permits an already active channel only when connector/mode/domain already match. It refuses reactivation if an entity has retired channel history and no current active channel, and only creates epoch 1 where no channel history exists. It has no channel-cutover path. The one-active partial index means the active row must be retired before pending is changed to active in the cutover transaction; deferred work cannot simply insert a second active row first.

## Smallest compatible channel-switch shape

Keep the current approval (`source_owner_approval`) for pending-config eligibility, but add a separate immutable reconciliation receipt. Do not invent a new route or authority. Extend existing source-write PATCH, API-006 test, API-007 approve, API-019 run, and API-008 activate contracts only with strict optional fields for a channel switch.

1. **Create pending revision without replacing current proof.** On existing source update, accept an explicit `pending_config` only for a connector/mode/version-domain switch. Insert a new immutable `source_config_revision`; set `pending_config_revision` plus a switch-state record; preserve `current_config_revision`, current endpoint/profile/mapping/credential approval proof, current credential revision/generation and secret reference, and the current active channel row. Bind the pending config, endpoint/profile, secret reference, and expected pending credential revision/generation independently; do not prematurely upsert pending credentials into the current credential record. Advance ordinary admission fencing and pause the source before reconciliation so old-channel intake stops. Existing frozen jobs continue under their old proof until drained or isolated. Create an immutable pending channel row for each configured entity, with that entity's new tuple and allocated `channel_epoch = previous max + 1`; freeze the complete expected per-entity set. A pre-switch abort clears the pending pointer/rows only while noncurrent and returns to the old current config/approval.
2. **Test and pre-approve the pending config with existing API-006/API-007.** Extend API-006 to explicitly target `pending_config_revision` while the old current config remains selected. It probes the new approved endpoint profile/secret ref and full mappings, including line contract; it does not change current config. Extend API-007 `/approve` with a strict optional purpose/target such as `approval_kind='PENDING_CHANNEL_CONFIG'`; keep the existing required `revision`, `test_report_id`, and `data_contract_ref`. It validates exact current Owner, owner revision, current source credential authority, pending revision and latest matching PASS report. It writes the existing `source_owner_approval` row for the pending revision but leaves registry lifecycle PAUSED and does not activate or replace current config. This is only permission to run the pending-channel reconciliation.
3. **Stage a full reconciliation with no canonical apply.** Extend API-019 optional fields with `purpose='CHANNEL_RECONCILIATION'` and the exact complete `pending_channel_set` plus config approval ID. The set has one frozen `(entity, channel_id, channel_epoch, version_domain)` entry per expected entity; the run freezes pending config/mapping/profile and pending credential proof. Mark it stage-only and allow it only for the current pending switch under the exact `source:write` caller. Use a single read-only source snapshot and full validation. Persist the complete validated stage and deterministic reconciliation digest; do not mutate canonical business rows, current channel, or current config before final cutover approval. A lost source transaction restarts a fresh attempt; partial stage never qualifies.
4. **Capture final current-Owner confirmation through existing API-007.** Extend the same `/approve` route with optional `reconciliation_run_id` (and exact expected pending revision). It recomputes/loads the server-owned validated reconciliation digest, verifies the complete per-entity pending channel set, pending config/test/approval and exact current Owner identity/revision plus source:approve, then inserts a new `control.source_reconciliation_approval` immutable receipt. Bind `(tenant,source,pending config revision,complete sorted per-entity channel IDs/epochs/version domains,run ID,reconciliation digest,field/identity mapping digests,endpoint-profile digest,pending credential revision/generation proof,Owner ID/revision,current security fence,created_at)`. Add receipt idempotency/uniqueness over the exact target tuple so duplicate requests return the same approval receipt and a changed digest cannot reuse it. Do not alter the first config approval, current credential proof, or make pending config current. The source_owner_approval table has no business unique constraint, so this separate receipt gives the final digest a distinct auditable identity.
5. **Cut over through existing API-008 only.** Extend `/activate` with optional `reconciliation_approval_id`; normal first activation continues unchanged. For a switch, verify caller `source:write`, exact pending revision/approval/receipt, complete per-entity channel set, enabled exact current Owner ID/revision, old current credential proof plus the separately frozen pending credential proof, complete validated stage digest, and no matching newer security barrier. The source must still be paused for old-channel admission. Acquire `control.lock_security_barrier_fence()` first; lock source registry, old active channel and every pending channel in a single caller-owned transaction. Ensure old in-flight apply transactions have drained under the shared guard/row locks; mark remaining old work isolated with `CHANNEL_EPOCH_RETIRED` before apply. Retire old active channels first (satisfying the per-entity partial unique index), transition each immutable pending row to active, update current config pointer, current credential revision/generation/secret reference and allowed scope only at commit, set ACTIVE lifecycle, clear pending state, advance source epoch and append lifecycle audit. Consume/mark the reconciliation receipt in the same commit. Only after successful commit may staged new-channel business apply resume under the new frozen proof. Any error before commit rolls back retirement and activation, so old config/channel and credential remain current; source may remain PAUSED until retry or explicit abort/resume.

This shape keeps API-007 source configuration approval separate from the final reconciliation digest. It adds no new user-facing route, permission scope, credential authority, or canonical-write permission to `hub_api`. Do not reuse an old ordinary job's `security_barrier_fence_at_admission` to authorize the pending lane; the reconciliation receipt and post-cutover apply carry their own current proof, and old typed barriers remain effective. Stable canonical UUID matching uses only the already approved identity mappings; missing/ambiguous mappings fail validation and block cutover.

## Remaining load-bearing checks for Phase E design review

- Does the selected 009 switch-state representation allow a pending config revision and complete per-entity pending channel set without updating current config or credential revision? Proposed minimum is one switch row keyed by tenant/source plus one or more immutable `source_channel` pending rows; avoid setting pending values into `source_registry.current_config_revision`.
- Can the existing capability/test report represent the nested order-line relation and its mapping digest? The B contract must be in place first; API-006 pending test must cover header plus every line column, source PK/FK and read-only permission before API-007 approval.
- Ensure approval SQL's current-Owner check is repeated at receipt creation and API-008 cutover, and exact current revision/digest predicates prevent stale Owner/config replays. The existing `source_owner_approval` row has no unique business key, so use receipt ID/idempotency and exact query predicates; do not add an unrelated uniqueness constraint.
- Confirm deterministic reconciliation digest canonicalization (entity key ordering, exact decimal strings, full-precision timestamps, line ordering, null-versus-absent) and the exact stage-complete status that API-007 may approve.
- Confirm cutover lock order is global security fence → source registry → channel transition rows → channel rows, compatible with worker apply's fence-first path. Prove partial unique active index is preserved and a failure injection before COMMIT leaves old channel/current config authoritative and new channel pending.
- Confirm old in-flight jobs drain or durably isolate before new epoch applies; old-epoch work must be rejected before version-domain comparison. Retired channels never become active again; a retry creates the next epoch.

These are focused Phase E design checks, not blockers to Phase A and not a request for user permission. Root freezes the exact implementation base and dispatches each source-writing slice separately after its preceding review.
