## API-021 route, query and errors

### Current route and summary

- `integration-service/ingestion-api/snapshot-routes.ts` registers `GET /hub/v1/admin/etl-runs/:id`. It authenticates a bearer through `currentUser`, then calls `getSnapshotRun`. It does not inspect or validate detail-route query parameters. No `include=delete_candidates`, `candidate_id`, candidate member page, or API-060 route exists at this pin.
- `integration-service/etl-worker/snapshot-runs.ts::getSnapshotRun(pool, auth, principal, runId)` requires `source:read`, validates the run UUID, starts a transaction, locks `control.lock_security_barrier_fence()`, calls `auth.assertCurrentPrincipal(principal,'source:read',client)`, and selects by `(principal.tenantId, runId)`. Its `SELECT_SUMMARY` returns ordinary safe C fields only; it omits the D reconciliation row and candidate summary. It returns the existing safe summary object, not candidate data.
- Route `envelope` is `{request_id,data}`. `fail` uses `AuthError.status` and emits `{request_id,error:{code,message,retryable,details:{}}}`. Existing relevant statuses: input invalid 400; forbidden 403; `SOURCE_CONFLICT` and `IDEMPOTENCY_CONFLICT` 409; source not found 404; unavailable 503. Do not leak raw SQL/candidate fields in errors.

### Query shape to add

Controller clarification requires strict UUID `candidate_id` alongside exactly `include=delete_candidates` for member mode, selecting one per-entity set from the specified run. Use the current public page parameter names `limit` and `cursor`; default 20 and max 100. Reject `candidate_id`, cursor, or limit outside that explicit mode; reject unknown fields, repeated/malformed parameters, bad UUIDs and non-string values. Ordinary detail continues to reject any unexpected query keys.

The current API-021 detail has no query parser. The current run-list parser in `snapshot-routes.ts::strictQuery` allows only `source_id,status,created_from,created_to,cursor,limit`, with `limit` restricted to 1–100. It provides a safe parser/error pattern, but must not be copied without the new mode rules.

`source-registry/service.ts::sourceCustomerCandidates` is the existing public cursor/page convention: default 20/max 100; `limit` + `cursor`; base64url cursor; SQL ordering and seek predicate use `source_pk COLLATE "C"`. Its current cursor binds only source ID and last source key. D2 must use the same parameter names and C collation but a new cursor payload bound to tenant, source, run, candidate ID, candidate revision, candidate digest, and last full identity key. A cursor that differs in any bound fact returns a safe 400/409 without member data. Page output contains full source identity keys only; omit stored canonical UUID and all business names/raw payload.

## Exact current principal and Owner checks

- `UserPrincipal` in `integration-service/auth/types.ts` includes `userId`, `tenantId`, `managementScopes`, `authEpoch`, `issuer`, and `subject`. HTTP authentication returns this principal from the OIDC authenticator.
- `AuthService.assertCurrentPrincipal(principal,scope,client)` in `integration-service/auth/service.ts` re-reads the principal inside the current transaction via `control.lock_api_identity(issuer,subject)`, requires enabled identity binding, enabled subject and tenant, confirms same user, tenant, issuer and subject, and checks the currently stored management scope. This is the existing operation-time currentness path. Exact-set mode needs current `source:read` **and** `source:approve`; call/revalidate both scopes against current DB state. API-060 requires current `source:approve`.
- **Auth epoch gap:** `assertCallerMatches` checks `userId`, `tenantId`, `issuer`, and `subject`, but does not compare the supplied `principal.authEpoch` to the current database epoch. `assertCurrentPrincipal` verifies the requested scope from the current DB row but does not return the refreshed identity/epoch. D2 must persist the actual current DB epoch from a locked `control.lock_api_identity(issuer,subject)` result, not merely copy a caller-provided field. The stored principal-binding tuple should include tenant, user, issuer, subject and `auth_epoch`; also record the approval's required scope. Do not record bearer token material or token expiry.
- The existing exact source Owner pattern is `source-registry/service.ts::sourceCustomerCandidates`: lock source row by principal tenant/source; require `source.data_owner_user_id === principal.userId`; lock and verify enabled tenant/user using local `currentOwner`; then call `assertCurrentPrincipal`. For D2 use the same exact current Owner check on API-021 exact-set reads and API-060. Recheck before any idempotency replay response. For API-021 exact mode, retain both current scopes; a normal summary reader must be denied if current Owner/tenant/source binding is stale.
- Suggested consistent operation lock order: global security-barrier fence, source row, enabled Owner/tenant rows, current OIDC principal binding/scope, then D candidate/approval/idempotency rows. Current `sourceCustomerCandidates` source/Owner/current-principal ordering is a local precedent. Avoid acquiring Owner/principal locks before source where another lifecycle path takes source first.

### Durable approver binding and D3 recheck

D1's candidate is bound to the source Owner and its revision, but that is the **source-config Owner**, not the human who later calls API-060. A D2 approval must derive and persist the actual caller from the operation-time locked principal, and bind it to:

- tenant and user IDs plus OIDC issuer and subject;
- current DB `auth_subject.auth_epoch` observed under `lock_api_identity`;
- required scope `source:approve` (and immutable request/approval record identity);
- current source Owner user ID and Owner revision at approval time;
- candidate ID/revision/digest, run and source/entity, baseline denominator, stable proof/member digest, OBS/time basis, request digest/key, reason and creation time.

D3 needs an existing-authority check that reloads the saved issuer/subject binding and proves it is still enabled and maps to the same tenant/user; tenant and subject remain enabled; current management scopes still include `source:approve`; current source Owner and revision still match the approved candidate; and no relevant security barrier applies. A D3 SQL security-definer helper can query these authorities using fixed search path and worker-only execute instead of widening worker grants. `lock_api_identity(issuer,subject)` is the named existing current-identity function, but its execute grant to `hub_worker` is not established by the inspected paths; do not grant it broadly without checking the role matrix. It may be safer for the worker-only D3 proof function to read the same identity/binding columns internally.

**Policy point for controller/review:** capture the current DB `auth_epoch` at API-060 and define whether any later epoch change invalidates the durable approval or whether D3 invalidates only on disabled/rebound principal or missing `source:approve` scope. Current `assertCurrentPrincipal` confirms current scope and identity binding but has no durable-approval epoch rule. Do not make token expiration an approval-expiry rule.

No reusable generic API idempotency lock/result function was found in these inspected routes/migrations; `lock_agent_credential_idempotency` is specific to agent credential creation.
- API-060 needs a durable idempotency result row scoped to tenant/source/route/key and request digest, bound to the durable approval ID/safe result. Serialize same-key requests (source lock plus approval/idempotency row lock or a narrowly defined idempotency function) so concurrent same-request calls return the same durable result. A unique violation alone is insufficient to guarantee replay semantics unless the winner is re-read. Revalidate current principal, exact current Owner, current candidate/proof/denominator and barriers before returning a replay; if the requester lost current Owner/scope, do not return the old approval response.
- Existing `source-registry/service.ts` appends user lifecycle and mapping events to `control.source_lifecycle_event`; D1's `etl_snapshot_delete_policy_audit` is system-only. Do not overload `SYSTEM_POLICY` actor as a human, claim the C API-007 approval is API-060, or directly grant API access to D1 audit/base tables.
- `AuthError`/route error envelope provides existing 400/403/409/404/503 codes; use `SOURCE_CONFLICT` for stale candidate/owner/proof/denominator/revision (409), `AUTH_FORBIDDEN` for a non-owner or missing current scope (403), `AUTH_INPUT_INVALID` for malformed request/cursor (400), and `IDEMPOTENCY_CONFLICT` for same route/key with changed canonical request (409). No new authority scope is required.

## D2-specific conflict/risk list

1. D1 candidates are immutable revision 1 at freeze and there is no D2 recompute/read helper. D2 must add server-side digest/currentness check and cannot edit membership or increment revision in place; stale means no approval and a later new candidate/run.
2. Existing `assertCurrentPrincipal` does not compare `UserPrincipal.authEpoch`. D2 must fetch the DB current epoch under `lock_api_identity` in the same transaction and persist that value with issuer/subject/user/tenant. D3 must be able to recheck identity binding and scope without trusting an HTTP principal or widening worker reads.
3. API-021 detail is currently query-blind and has no D summary. Implement strict mode isolation: only `include=delete_candidates&candidate_id=<UUID>[&limit=...&cursor=...]` activates candidate paging. The opaque cursor must be bound more tightly than the older source-customer cursor.
4. D1 has no API-readable D relations or member projection. The minimal route must use narrow `hub_api` execution grants, not direct base table grants. Candidate member response exposes only source keys.
5. D1 `SYSTEM_POLICY` audit records the automatic pause and is not a user approval audit. API-060 and sensitive exact-key reads need explicit safe human audit evidence. Existing source lifecycle events have separate source-state semantics and their action constraint must be checked before reuse.
6. API-060 current Owner validation must happen before idempotency replay; request digest must bind path source/candidate ID plus all strict body fields, including `reason`. A replay remains denied to a principal who is no longer the current enabled Owner or lacks current scope.
7. Above-threshold approval is per candidate entity set; D3 is held until every required above-threshold set has current approval. API-060 has no activation/schedule side effect.

No tests, runtime commands, migrations, database, external services, or 001–008 mutation were part of this preflight. The exact source pin should be refreshed after D1 review before D2 implementation.
