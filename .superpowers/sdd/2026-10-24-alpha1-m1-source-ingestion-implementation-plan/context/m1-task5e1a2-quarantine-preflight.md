## API-023: stable unified quarantine index

There is no current common quarantine ID. REST identity is the immutable source fact `(tenant,source,job_id,ordinal)` (the item `event_id` and `source_pk` are also immutable); snapshot aggregate identity is `(tenant,source,run_id,attempt_id,entity,relation,parent_source_pk,source_pk)`. Snapshot `outcome_id` is UUID but REST has no counterpart. A run-level extraction failure is not an aggregate quarantine item.

Add a narrow immutable index/receipt, for example `control.ingestion_quarantine_index`, keyed by a generated UUID and unique on a typed complete origin tuple. Keep separate origin-key columns/FKs or a discriminator with mutually exclusive validated key groups. Store only origin IDs, tenant/source, entity/relation, source key, terminal status/error code, frozen-proof digest/reference, creation time, and any typed dependency key. Do not copy `public_record`, raw batch bytes, snapshot `facts`, credentials, connector output, free-form provider errors, or target payload. Backfill currently terminal REST `QUARANTINED` items and snapshot outcomes with status `QUARANTINED`; expose `CHANNEL_EPOCH_RETIRED` as an explicit quarantine outcome if included in the product definition, but do not relabel generic run `FAILED` as a per-record quarantine. Capture subsequent REST status transition to `QUARANTINED` and snapshot outcome creation in the same transaction (trigger or controlled insert helper). Enforce unique origin plus `ON CONFLICT DO NOTHING`, so migration/backfill/live retry cannot replace the first quarantine identity or its original proof/error.

API-023 may return `quarantine_id`, origin kind, source/entity, job or run/attempt ID, source key (including snapshot relation and parent key), status, code, timestamp, frozen proof version/digest, and a safe dependency summary. Dependencies are machine-coded and scoped: e.g. `customer_ref` source tuple, never record contents. Deterministic paging should order `(created_at DESC, quarantine_id DESC)` and use an opaque cursor bound to tenant, source filter, Owner revision, filters, and last ordering tuple; cap page size. Derive tenant from authenticated principal. Each page request must recheck current exact Owner assignment and source scope under the same transaction/lock protocol used by owner mutation, then apply current security-barrier fence before returning rows. Existing ordinary read endpoint grants do not establish the stronger current-owner predicate. Do not grant API access to raw batch, full `public_record`, snapshot stage or proof tables to implement the listing; use a narrow loader/function and explicit column grants.

## API-024 REST same-target recovery: actual implementable path

The existing REST worker can process a real retry if API-024 transactionally creates a **new one-item child job** and outbox row, and a durable link from original quarantine origin to child/recovery operation. The child uses a fresh job UUID, fresh `operation_id`, its own idempotency identity and correct one-item request digest; it copies the original immutable item tuple and frozen proof exactly. Reuse `batch_id` and `raw_batch_id`: the raw batch FK is valid only for the same tenant/source/route, and raw batch is immutable. Copy original route/entity and all proof fields (including both mapping revisions/digests, credential, channel epoch, owner approval, test report, security barrier fence). Store `received_count=1`, item ordinal `0`, original event/source key/version/operation/time/`public_record`, status `RECEIVED`, and insert exactly one outbox row. Worker claim then selects the new outbox; the original job/item remain terminal and unchanged. `event_id` uniqueness is scoped to `job_id`, so same `event_id` on this child is schema-valid. The new job must be linked to original source origin with a dedicated recovery-operation row; the current job schema has no parent/retry link and does not itself distinguish this operator retry from normal ingestion.

There is no supported caller-facing direct `hub_api` insertion of item `operation_id` in 007 (008 grants only the columns required for automatic default/worker behavior), nor a narrow child-create function in the pinned baseline. Add one narrow `SECURITY DEFINER` transaction API (or grant only the exact child columns if ownership/guards can be preserved) to validate and create the linked child job/item/outbox. Do not permit caller-supplied proof fields, target IDs, `public_record`, or “latest” mappings. The function should lock in this order: global security-barrier fence; exact source/current Owner and source approval; quarantine index row and original item/job (CAS state); current channel/source security facts and canonical mapping/identity evidence; then persist recovery link, child and outbox atomically. Recheck the fence and exact authorization at commit boundary. Replay of the same API idempotency key returns the same child operation only after rechecking caller authority and current barriers; key mismatch returns conflict. Race on quarantine state must return 409, never spawn a second child.

API-024's published `mapping_revision` field is ambiguous because REST proof has distinct `mapping_revision` (field transform) and `identity_mapping_revision` (source-to-target identities). Recommendation: define it as **identity mapping revision** for the quarantine retry operation (the decision that could change canonical target), require exact match to the source mapping revision/proof named by the request, and copy both original frozen revisions/digests unchanged into child job. If API schema may be clarified, name `identity_mapping_revision` explicitly and separately bind expected quarantine `proof_version`/state. `expected_state` must compare a stable CAS token for the indexed origin and original immutable terminal status/error/proof, not a mutable display label alone.

Same-target retry means exact proof reuse, not adopting whatever mapping is current. Before creating a child, establish that the original identity mapping still maps the item’s external identity to the same target, and that any confirmed canonical identity/reference still names that target. For an order, also prove the referenced customer source tuple resolves to its same live canonical customer; worker's `verifyOrderCustomerReference` is an additional check, not a substitute for operator-side eligibility. The target types are not all UUIDs: `canonical_source_identity.canonical_object_id` for customer/order is UUID, while `canonical_identity_reference.target_id` is text for `user`/`department` and canonical UUID text for `customer`. Never assume every mapping target can be compared to a canonical UUID. If exact old target cannot be proven (new object, missing canonical row/reference, external identity is new, or source mapping changed), return 409 `IDENTITY_REMAP_REQUIRES_OWNER_CONFIRMATION`; do not refresh frozen mappings or silently apply the newest revision. Remapping needs the separately authorized E1b path.

The security distinction is load-bearing: a *current security barrier* or retired channel blocks recovery even when the frozen target matches; ordinary source/config/mapping drift alone does not invalidate already-admitted frozen work. Conversely, absence of a security barrier is not evidence that a target may be changed. API-024 must honor exact current Owner plus `source:approve`, current principal identity, exact source tenant, and frozen job authority. No stage/business canonical writes occur before cutover; this recovery child may enter the regular worker only after all eligibility checks pass.

## Snapshot quarantine boundary and API-022 interaction

Snapshot outcome IDs provide stable aggregate identity, but current C is lease/claim bound. `recordAggregate` is unique on the original run/attempt/aggregate; calling it again for an existing quarantine would collide or replay the same range. The REST worker rejects `SNAPSHOT_OBSERVATION`; the C store's stage/proof loaders require a claimed continuation and use the original frozen run proof. Therefore do not route a snapshot quarantine ID through the REST child-job mechanism and do not advertise per-aggregate snapshot API-024 support until there is a real new child operation that preserves stage/proof lineage and makes the aggregate eligible to C's claim worker.

For this phase, recommend API-024 returns a documented 409 `RECOVERY_SCOPE_UNAVAILABLE` for snapshot aggregate IDs; API-022 remains the only implemented/designated snapshot retry path if its full-run scope is authorized. API-022's PRD precondition is specifically the **original failed version** plus reason, producing a new attempt over the reliable cursor (202/409). It is not an implied per-record mutation. An alternative is to delegate snapshot API-024 to the same full-run retry helper only if the product explicitly grants Owner `source:approve` authority over that entire run and the response clearly says it starts a full new run/attempt; absent that authorization, keep API-024 409. In either design, preserve original failed run/attempt/outcomes, require CAS equality with the supplied original failed version, and never advance from a stale “latest” run implicitly. `DUPLICATE` means a valid terminal no-op and should not be counted as a missing/apply failure or converted to a quarantine for this route.

## Minimal E1a2 slices and acceptance oracles

1. **E1a2-1: quarantine identity and listing.** Add immutable origin index, backfill and same-transaction live capture for REST item quarantine and snapshot aggregate quarantine; safe API-023 query/function with exact-owner scope, typed keys, safe dependency code, bounded stable paging. Oracle: existing rows backfill once with stable IDs; repeated migration/capture does not replace IDs; mixed REST/snapshot listing pages without duplicates/omissions; tenant/source/Owner mismatch cannot enumerate; assertion that response and DB role cannot read payload/stage tables.
2. **E1a2-2: executable REST retry child creation.** Add quarantine CAS and durable recovery link plus narrow transaction function/route. Only support exact same-target REST `source_version` origin; insert child item/outbox that existing worker can claim and apply; keep original immutable. Oracle: retry creates one reachable child/outbox and fresh operation ID; worker produces real terminal state; concurrent/replayed same request has one child; mismatched idempotency or stale expected state is 409; original job, item, proof and raw receipt are unchanged; old/new mapping mismatch, missing exact identity evidence, retired channel, or typed barrier cannot create work; order retry must prove customer tuple. A receipt-only `202` is not acceptance.
3. **E1a2-3: snapshot retry contract decision.** Keep API-024 snapshot branch as explicit `409 RECOVERY_SCOPE_UNAVAILABLE` with API-022 guidance until a C-compatible child-run operation is built, or explicitly authorize/delegate whole-run retry to API-022. Oracle: wrong/stale original failed-version CAS returns 409; successful whole-run retry records a new attempt while old run/outcome remains unchanged; no aggregate is applied twice and duplicate outcomes remain terminal no-ops. Do not implement a pretend per-aggregate path in this slice.

These are documentation-level acceptance oracles only; no suite/resource was run in this preflight. E1a2-1 and E1a2-2 are independently reviewable; E1a2-3 is a scope decision and should not block REST same-target implementation if the explicit snapshot 409 is retained.
