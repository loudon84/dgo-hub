Authority is `docs/plans/2026-10-24-alpha1-m1-source-ingestion-implementation-plan.md` M1-3 and frozen rules 1, 4, 6, 8; PRD §§8.6, 9.1–9.3, Appendix A.1–A.2 and C.1–C.2; and task-2-brief/report. The public routes are exactly API-015 `POST /hub/v1/ingest/crm/customers`, API-016 `POST /hub/v1/ingest/orders/orders`, API-017 `GET /hub/v1/ingestion-jobs/{id}`, and API-018 `GET /hub/v1/ingestion-jobs/{id}/items`. API-015 is bound to customer write scope; API-016 to order write scope. Job reads are limited to the source itself or an already-authorized ingestion administrator. API-018 returns event ID, source PK, processing status, and error code; payload is not returned by default. Plan explicitly requires safe summaries only, so do not add a payload opt-in.

Appendix A.1 defines the common success envelope `{request_id,data}` and failure envelope `{request_id,error:{code,message,retryable,details}}`; details are authorized location fields only and must omit SQL, connection data, secrets, and other tenant object names. Appendix C uses `request_id` in the 202 example. Current `app.ts` generates UUID request IDs and disables caller-supplied request-ID headers; pass `request.id` into envelopes. `request_id`, body `batch_id`, item `event_id`, and `Idempotency-Key` are four distinct values.

PRD §9.3 batch object:

| Field | Required contract |
|---|---|
| `schema_version` | exact string `hub.v1` |
| `batch_id` | UUID from the upstream system, for retry lookup |
| `records` | array of 1–100; full HTTP request <= 4 MiB |
| `records[].event_id` | UUID |
| `records[].source_pk` | exact case-sensitive source identifier; 1–128 chars, no edge whitespace |
| `records[].source_version` | decimal integer string, 1–20 digits, nonnegative, no `+`, no leading zero except `0` |
| `records[].operation` | `UPSERT` or `DELETE` |
| `records[].source_updated_at` | RFC3339 timestamp with explicit offset |
| `records[].data` | complete entity image for UPSERT; exactly null for DELETE |

Every object is strict: unknown fields reject (`additionalProperties=false`), repeated JSON property names reject before schema validation, and there is no free-form `extensions`. String encoding is UTF-8. Decimal values are strings, exact scale 2 for amounts and line amounts and scale 6 for quantity/unit price; quantity >0, money and prices nonnegative; no implicit rounding. Currencies are CNY/USD/EUR. Order header amount remains the source's authoritative value and is not required to equal its lines. Complete order line set is 0–200; deleting a line from a newer UPSERT logically deletes that prior line in the later apply transaction. A DELETE preserves version/tombstone; an older UPSERT cannot resurrect it.

Root ruling: API-015 and API-016 both return 202 with `data:{job_id,status:"RECEIVED",received_count,applied_count:0}` on a new durable acceptance. Same-key replay returns the original job's current safe status/counts (during M1-3 the status remains `RECEIVED`); it does not claim the job was just newly received. Return 202 only after intake commit; it proves durable receipt, not applied/queryable business data. Stable errors: `AUTH_INPUT_INVALID` maps through existing Hub route handling to 422; invalid/revoked source credentials remain 401 and scope denial 403 per PRD; `INGEST_INPUT_INVALID` 422 with path/reason only; `INGEST_JSON_DUPLICATE_KEY` 422 without key value; malformed JSON 422; unknown content type 415; `INGEST_BODY_TOO_LARGE` 413; `IDEMPOTENCY_CONFLICT` 409; current source conflict uses existing `SOURCE_CONFLICT` 409. Use the shared envelope.

Root ruling: public customer `department_external_id` is required; the narrow internal adapter maps it to M1-2 `dept_external_id`. Public order `customer_ref` is strict `{source_id: source text ID, source_pk: identifier<=128}`. `source_id` follows the existing registry rule `^[A-Za-z0-9][A-Za-z0-9._:-]{0,255}$`: case-sensitive, 1–256 characters, and leading/trailing whitespace is rejected without trimming or case conversion. It may point to a different same-tenant CRM source than the order source. M1-3 preserves validated public ref values intact as an immutable event fact and does not resolve customer existence or query/add identity grants. The existing order-source frozen typed mapping remains `external_id=ref.source_pk → target_id=canonical customer UUID`. M1-4 adapts `ref.source_pk` to M1-2's `customer_external_id` and cross-checks the full tuple against the same-tenant live core customer before apply, using existing `hub_worker` reads of `control.canonical_source_identity`; missing/conflicting dependency quarantines the item. Another source may use the same PK, but only the tuple that resolves to the frozen mapping target applies. This preserves one mapping authority.

M1-2 canonical input uses `owner_external_id`, `dept_external_id`, `customer_external_id`, and includes `source_pk`, `source_version`, `source_updated_at` internally. The route/apply adapter combines outer record metadata with public `data`; body does not carry tenant/source/channel/proof. `DELETE` maps outer `source_updated_at` normalized to UTC to internal `deleted_at`; public `data` must be null, and internal metadata fields are not accepted inside public `data`.

The pinned source and PRD are compatible on text source IDs: the existing registry validator is `^[A-Za-z0-9][A-Za-z0-9._:-]{0,255}$`, migration 002 constrains storage length to 1–256, source comparison is case-sensitive, and PRD §13.1 rejects leading/trailing whitespace. PRD C.2's `customer_ref.source_id: "crm-demo"` confirms it is not UUID. Preserve exact submitted source text in the public event fact and request digest; do not trim or case-fold it.

## Pin-based seams — original 6bec research

The observations below are from the pinned source only:

- `integration-service/app.ts`: Fastify global body limit is 2 MiB; generated request IDs are UUIDs and request ID header parsing is disabled. It registers route options by injection. M1-3 therefore needs route-local 4 MiB handling for exactly the two ingest POST routes, without raising the global limit. Keep the prior cap for health/admin/other endpoints.
- `integration-service/ingestion-api/routes.ts`: `registerRoutes` is the route aggregation seam. Existing `/v1/ingest/:kind` and `/admin/*` legacy endpoints return early unless `local_lab` and `HUB_ENABLE_LEGACY_LAB=true`. Strict hub.v1 endpoints are separate and must never be routed through those legacy handlers.
- `integration-service/ingestion-api/identity-routes.ts`: current hub APIs use the standard envelope helpers, generated `request.id`, explicit `AuthError` handling, and strict object key checking. Its `AUTH_INPUT_INVALID` maps to 422. Source ingestion needs source Bearer authentication, not the user OIDC helper used by these identity routes.
- `integration-service/ingestion-api/logging.ts`: request serializer includes request ID, method, route; response serializer includes status. Keep payload fields out of serializers and route logging.
- `integration-service/auth/types.ts`: `SourcePrincipal` carries authenticated `tenantId`, `sourceId`, `allowedEntities`, `credentialId`, `revision`, and `sourceEpoch`; current `AuthService` exposes entity-scoped `authenticateSource(token, entity)` and `assertCurrentSource(snapshot, entity, client: PoolClient)`. This is a small interface addition, not a second token authority or scope.
- `integration-service/auth/service.ts`: `assertCurrentSource` calls `control.lock_current_source` on the supplied client and checks credential/tenant/source identity, source digest kind, enabled tenant/credential, ACTIVE lifecycle, entity scope, current credential/config revision, and matching source epoch. - `integration-service/auth/errors.ts`: existing auth codes include `AUTH_INVALID` (401), `AUTH_FORBIDDEN` (403), `AUTH_INPUT_INVALID` (400 at the class, deliberately mapped to 422 by existing Hub route handling), `SOURCE_CONFLICT` / `IDEMPOTENCY_CONFLICT` (409), and unavailable 503. Apply acquires this guard before credential/channel locks, checks that the admission fence is not from the future, and rejects matching barriers with a later `effective_fence`. Preserve this lock order to prevent a source/barrier race or deadlock.

## Required transaction and job behavior

Canonical idempotency key scope is authenticated tenant + authenticated source + exact route + key. Key syntax is `^[A-Za-z0-9._:-]{1,128}$`, case-sensitive and untrimmed; M1 has no TTL or automatic deletion. PRD §13.3 defines `request_digest = SHA256("hub.ingest.v1" + NUL + tenant_key + NUL + source_id + NUL + route + NUL + canonical_json(body))`; it is separate from M1-2 `sourceContentDigest`. Canonical JSON is UTF-8 and whitespace-free, object keys sorted by Unicode code point (equivalent to UTF-8 byte order for valid Unicode), strings retain original Unicode/case, arrays retain order, null differs from absent, duplicate keys and unpaired surrogates reject. Hash the validated public body without normalizing UUID case, timestamps/offsets, source text, optional-field absence, or nulls. Thus JSON whitespace/key order normalize, while batch/event UUID spelling/case, timestamp spelling/offset, absent-vs-null phone, source text, array order, version, operation, and any other body change produce a different request digest. Amount and source_version are decimal strings; source_version follows its strict 1–20 digit no-leading-zero syntax. PRD fixes monetary scale limits but does not explicitly define lexical numeric equivalence for the request digest, so retain the validated submitted amount string; M1-4 may pad decimal scales and normalize timestamps for M1-2 after digesting. Never use JavaScript Number. Same scoped key+digest returns the existing job current safe status/counts; mismatch is 409. Scope is independent across route/source/tenant.

TX-INTAKE writes in one commit: immutable original bytes as `bytea`, job, ordered items with validated public event facts retaining exact string values and missing/null distinctions (including full `customer_ref`), scoped key+request digest, frozen M1-1/M1-2 proof plus admission/approval fence facts, and processing outbox. API returns 202 only after commit; any precommit failure rolls back all intake state. Retry after a lost response returns the committed original job. No later request alters original bytes or proof.

Route parsing detects duplicate keys at all nesting levels before schema validation and retains original bytes. The 4 MiB limit belongs only on the two strict POST routes. Use stable `INGEST_JSON_DUPLICATE_KEY` / `INGEST_INPUT_INVALID` 422, malformed JSON 422, unknown content type 415, and `INGEST_BODY_TOO_LARGE` 413. Raw storage fails closed if the deployment policy is absent; local tests use explicit `local_lab` policy and claim no encryption.

For admission, first take `lock_security_barrier_fence()` and store `securityBarrierFenceAtAdmission`. Load the exact current approval's `approval_security_fence` (added in migration 007); reject a matching typed barrier only if `effective_fence > approval_security_fence`. A barrier covered by a later approved recovery does not permanently block new jobs. Migration 007 adds that column to immutable Owner approvals; historical rows default to 0; a BEFORE INSERT DB trigger captures current fence under the common guard. Existing approval flow acquires that guard before its source/credential locks. Then lock current source/config/active channel and call `assertCurrentSource` on the same client immediately before commit. Freeze exact current proof, including the approval fence, from trusted DB rows. Same credential row ID can recover through fresh Owner test/approval. Ordinary pause/edit/tenant re-enable alone never clears a barrier. After tenant re-enable, explicit existing `pause → test → approve → activate` generates a fresh approval fence; existing service test accepts locked current config and report, approve requires TESTED/current proof, and activation rechecks exact approval and proof. Old jobs remain subject to barriers newer than their admission fence. Never erase barriers or treat source epoch as worker lifetime auth.

API-017/018 query by job ID plus verified caller scope. Source reads use a narrow entity-neutral authentication method against the same source credential authority, tenant/source filter, then entity allowed-list check; unauthorized IDs return 404 like absent IDs. Management reads require OIDC plus same-tenant existing `source:read`. Pagination is default 20/max 100, ascending immutable item ordinal, canonical base64url cursor bound to job UUID+ordinal. API-017 returns safe status/counts/first-last timestamps; API-018 returns only event ID/source PK/item status/error code. Never select/serialize raw bytes.

## Root-ratified contract decisions

1. Public customer `department_external_id` is required and maps internally to `dept_external_id`.
2. Order `customer_ref` is `{source_id: source text ID (1–256, case-sensitive, reject surrounding whitespace), source_pk: identifier<=128}`; the customer source may differ from the order source within the same tenant. Preserve validated reference text immutably. The order source's existing typed customer mapping remains `external_id=ref.source_pk → target_uuid`. M1-3 stores 202 `RECEIVED` without business dependency lookup. M1-4 maps source PK into canonical input and verifies the source tuple resolves through `control.canonical_source_identity` to the exact mapped same-tenant live customer. Missing/conflicting rows quarantine one item; no new map authority or M1-3 identity query grant.
3. DELETE public metadata is outer-only: `data:null`; internal `deleted_at` is outer `source_updated_at` normalized to UTC. Reject internal transport metadata inside public `data`.
4. Both POST routes return new acceptance `RECEIVED`, `received_count`, `applied_count:0`; same-key replay returns original job's current safe status/counters, not a false new-receipt status.
5. Canonical request digest and exact key syntax/retention are frozen in the task brief. Safe stable error codes and status mapping are frozen there; details contain paths/reason codes only.
6. Source job reads use same-authority entity-neutral source identity authentication, then tenant/source/entity allowed-list checks; no new scope. Existing OIDC management reads use same-tenant `source:read`. Unauthorized job and absent job both return 404. Cursor default/max/order/encoding are fixed in task brief.
7. Raw bytes are immutable `bytea`, API insert-only, worker-readable; strict intake fails closed without configured deployment storage policy. `local_lab` tests supply an explicit policy and make no encryption claim.
8. Migration 007 captures `approval_security_fence` for new Owner approvals (old approvals default 0). Admission compares matching typed barriers against the exact current bound approval fence. Fresh Owner-approved recovery with the same credential row ID authorizes new jobs; old jobs continue checking barriers newer than their admission fence. Ordinary pause/edit/tenant re-enable does not clear a barrier. Tenant recovery uses the existing explicit `pause → test → approve → activate` flow after tenant re-enable; do not erase barriers or use timestamps/current generation alone.

**Correction to prior preflight/root ruling:** the previous UUID requirement and its TEXT-vs-UUID compatibility blocker were incorrect; PRD C.2 demonstrates `customer_ref.source_id: "crm-demo"`, and §13.1 defines case-sensitive source text IDs. The source ID blocker is resolved by retaining the existing text contract.
