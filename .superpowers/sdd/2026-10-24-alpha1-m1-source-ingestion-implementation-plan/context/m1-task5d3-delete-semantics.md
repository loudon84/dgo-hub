## Input and digest behavior

- `integration-service/normalization/models.ts` exports a strict `canonicalDeleteSchema` and `canonicalOrderDeleteSchema`, each accepting exactly `source_pk`, `source_version`, and `deleted_at`. `source_version` is canonical decimal text with up to 20 digits. `deleted_at` must be an offset-bearing datetime string. Thus the proposed shape `{source_pk, source_version: bound OBS, deleted_at: second complete run completed_at}` is accepted by the existing delete parser when the timestamp is serialized in its required RFC3339-offset form.
- `integration-service/normalization/canonical.ts::sourceContentDigest` hashes canonical JSON with sorted object keys. It strips `source_version` and other processing/version fields, but does not strip `source_pk` or `deleted_at`. A delete digest therefore identifies the exact source key and inferred deletion time; it does not identify the observation version. Use the exact persisted run time on every replay so the digest remains stable. The projection digest separately includes `{deleted:true, deleted_at}`.
- `canonical.ts::canonicalVersion` and the parser preserve observation as decimal text; `apply.ts` compares receipt versions with `BigInt`. An OBS greater than the last presence receipt passes the normal newer-version path. Equal OBS plus equal delete digest returns `DUPLICATE`; equal OBS with a different digest returns `QUARANTINED/SOURCE_VERSION_CONFLICT`; lower OBS returns `IGNORED_STALE`.
- If a prior receipt is already deleted and its delete digest matches, the helper's OBS fast path writes the new receipt and returns `DUPLICATE` without another outbox row. If a new higher OBS is paired with a different delete digest, the helper proceeds through the delete path and emits another logical DELETE outbox event. D must use stable candidate/run identity and a same-transaction D effect receipt so retries cannot manufacture a changed time/digest or accidentally issue a second logical operation.

## Canonical effects

- `integration-service/normalization/apply.ts::applyCustomer` and `applyOrderAggregate` take a caller-owned `PoolClient` and accept the above delete union. They do not begin or commit the transaction. Each invokes `verifyFrozenApplyContext`, locks the current source receipt by tenant/source/channel/entity/full source PK, compares its `source_version`, then locks source identity and writes canonical logical-delete state, identity row, version receipt, and one append-only outbox row. The deleted source identity UUID is reused when present; a missing identity would use a new random UUID, so D must freeze only live denominator members that have the exact expected current identity and stale if this binding disappeared.
- For an order delete, the helper applies the same `deleted_at` to the existing order and all currently-live order lines. It advances line `hub_revision` but does not set new line `source_version`, version domain, or channel epoch fields and does not write one outbox row per line. The durable aggregate receipt/outbox is order-level. This is the existing helper contract; D should preserve it and include it in the D3 oracle.
- `verifyFrozenApplyContext` takes the global security-barrier fence first; checks credential identity, active/retired channel tuple, complete frozen source-config/test/approval/field/identity/profile proof, and typed barriers; ordinary current source epoch/config equality is intentionally not an apply gate. It validates the frozen Owner approval ID/user/revision against stored proof, but does not compare that Owner revision to the current `source_registry` Owner at apply time. D must separately revalidate current Owner/proof currentness for approval-bound actions and stale any pending D candidate when the current Owner/proof has drifted, including automatic below-threshold work under the controller's currentness ruling.

## C proof reuse and D loader boundary

- C's `snapshot-apply-worker.ts::applyContext` is a private adapter from `SnapshotCProof` to `ApplyContext`. It copies C run-bound credential/source epoch, entity channel ID/epoch/domain, Owner approval/user/revision, config/mapping/identity revisions and digests, profile/test, and security fence. C's normal apply transaction then calls `assertApplyClaim` and `record_etl_snapshot_aggregate` while the run is `APPLYING` under its C claim.
- `snapshot-continuation-store.ts::loadProof` calls worker-only `control.read_etl_snapshot_c_proof(tenant,source,run,attempt,claim)` and requires the proof status to match the live claim; migration 009's proof/claim guard accepts C continuation states, not terminal `COMPLETE`. `finish_etl_snapshot_run` clears the C continuation token when it marks the run complete. Therefore D cannot reuse `loadProof`, a C claim, `assertApplyClaim`, or `record_etl_snapshot_aggregate` for post-C effects.
- D needs its own fenced loader that reads the immutable C `etl_run` proof, exact successful validation seal and manifest/attempt, run-bound observation, and matching frozen revision rows while checking C status `COMPLETE`. It can reconstruct the same legitimate `ApplyContext` values from the C proof; `verifyFrozenApplyContext` itself does not require C run status or a C claim. The D effect must instead be fenced by a D claim and recorded through D-owned effect/outcome procedures in the same caller transaction as the canonical helper. It must not reinterpret current config/mappings as the accepted C proof.
- Verify at D3 pin refresh that C manifest/seal/observation FKs and JSON digest checks provide every needed immutable input and that the candidate's entity/channel slice is one of the run's frozen enabled entities. Current Owner approval is a second D-specific gate; the C Owner approval in `ApplyContext` only preserves C's original frozen ingestion proof.

## Timestamp precision

C stores run `completed_at` as PostgreSQL `timestamptz` and sets it from `clock_timestamp()`. The Node `pg` default parser returns JavaScript `Date`, which preserves milliseconds but can discard PostgreSQL sub-millisecond precision. To use the exact second-run DB time as the immutable inferred delete timestamp, read/format it losslessly as RFC3339 text in SQL with microseconds (UTC `Z` or explicit offset) before handing it to the strict Zod parser. Do not round through JS `Date`, call worker `new Date()`, or substitute another timestamp.

## Audit/pause observation

The scoped `source-registry/service.ts::pause` operation is a user-driven pause: it requires `source:write`, locks source/credential facts, sets lifecycle `PAUSED`, disables the enabled schedule, advances the source epoch, and appends `source_lifecycle_event` with `actor_user_id=principal.userId` and a reason. No worker-actor automatic-pause audit pattern was visible in the specifically inspected C worker/helper files. D1 must reuse an existing authorized safe actor/audit seam after pin refresh; do not impersonate the Owner or invent worker identity/authority. This is a D1 coordination note for the parent.

## Concrete D3 contract check

The helper input can carry the proposed OBS and second-run timestamp, but a passing parser is not sufficient proof. D3 must bind both to the immutable latest cohort/candidate, recheck OBS > last presence under the same effect transaction, persist exact RFC3339 time and D effect identity, and prove helper replay/outbox behavior. Current Owner check and D claim/effect records are missing from C and must be additive D controls; no alternate canonical writer is needed if the refreshed D loader can build the immutable C-derived context and preserve the helper's frozen-proof guard.
