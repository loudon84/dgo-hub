## API-023 request and response

Representation boundary: `auth_epoch`, `owner_revision`, and every PostgreSQL bigint in proof JSON stay canonical decimal **strings** through TypeScript, cursor context encoding and response serialization. Never convert them through JavaScript `Number` or JSONB numeric serialization. UUIDs and digests are strings; bounded `ordinal` and `limit` remain numbers. Add an independent helper assertion using `9007199254740993` and `9007199254740995` to prove the canonical context JSON and SHA-256 preserve values above `2^53` exactly, without changing the live source authorization fixture.

`GET /hub/v1/admin/quarantine` is registered alongside the strict ingestion management reads. It accepts only these query keys: required `source_id` matching `^[A-Za-z0-9][A-Za-z0-9._:-]{0,255}$`; optional exact `origin_kind=REST|SNAPSHOT`; optional `error_code` of 1–96 characters matching `^[A-Z0-9_:-]+$`; optional canonical positive decimal `limit` from 1 through 100 (default 20); and optional canonical base64url `cursor` no longer than 1024 characters. Repeated/array keys, unknown keys, noncanonical lexical forms, and malformed cursors map to the existing `AUTH_INPUT_INVALID` 400 envelope.

The route accepts only a user OIDC bearer, requires `source:read`, and never accepts tenant or Owner from the request. It derives tenant/user/issuer/subject from the verified principal and asks the auth service to recheck the principal under locks on every page. Success is the existing `{request_id,data}` envelope with `{items,next_cursor}`. An item contains only `quarantine_id`, `origin_kind`, `source_id`, `entity`, complete qualified source identity (`relation` and `parent_source_pk` for snapshot), origin identifiers (REST job/item ordinal/event; snapshot run/attempt/outcome), terminal status and nullable stored `error_code`, six-fraction UTC `created_at`, frozen proof references/revisions/digests, and a typed dependency status/code. Dependency status is `UNKNOWN` and dependency code null unless an existing typed dependency proof is available; this slice does not infer dependency from arbitrary error text. No `public_record`, raw batch bytes, snapshot stage/facts/pages, SQL/provider exception, credential, token, or connector configuration is returned.

The cursor JSON binding is exactly `{"v":1,"context_sha256":"<lowercase 64 hex>","created_at":"YYYY-MM-DDTHH:MM:SS.ffffffZ","quarantine_id":"<canonical lowercase UUID>"}` in that key order, encoded as unpadded base64url. The SHA-256 input is UTF-8 canonical JSON in this exact key order: `{"tenant_key":...,"source_id":...,"issuer":...,"subject":...,"auth_epoch":"<canonical unsigned decimal>","owner_user_id":...,"owner_revision":"<canonical unsigned decimal>","origin_kind":null|"REST"|"SNAPSHOT","error_code":null|"...","limit":<integer>}`. Strings use JSON canonical escaping; the digest is over the encoded JSON bytes. The digest plus last tuple is a continuation context binding, not a signature or authorization token: changing its position may change pagination, but cannot bypass independent server-side predicates. Every page repeats authorization and current Owner checks. Timestamp serialization retains PostgreSQL UTC microseconds as exactly six fractional digits and is compared as a timestamp without conversion through millisecond `Date`. Seek is strict descending tuple order; query `limit+1`, return a cursor only when a further eligible row exists. An invalid cursor is 400; valid-but-stale current authority/filter context is `SOURCE_CONFLICT` 409. Established auth/source mappings remain `AUTH_CONTEXT_CHANGED` 401, `AUTH_FORBIDDEN` 403, inaccessible source `SOURCE_NOT_FOUND` 404, and authorization DB failure `AUTH_UNAVAILABLE` 503.

## Eligibility and typed read-security predicate

The visible records are only actual REST item `QUARANTINED` states and snapshot apply-outcome `QUARANTINED` states. `CHANNEL_EPOCH_RETIRED`, generic run `FAILED`, `APPLIED`, `DUPLICATE`, and `IGNORED_STALE` are excluded. Nullable REST `error_code` remains null and does not match any explicit error filter. Snapshot relations are only the supported `customer` and `order`; parentless snapshot records keep `parent_source_pk=''` exactly.

Read authority is the current, enabled tenant and subject, current enabled OIDC binding matching verified tenant/user/issuer/subject, `source:read` in the locked current management scopes, and the source row's exact current `data_owner_user_id` with its current `owner_revision`. The applicability of a source barrier is typed: `TENANT_DISABLED` denies through the current enabled-tenant check; a `CREDENTIAL_COMPROMISE`, `SOURCE_SCOPE_SECURITY_REMOVAL`, or `CHANNEL_RETIRED` barrier blocks future source admission/worker application according to the existing source fence, but does not by itself revoke this separately authenticated current Owner's read access to safe quarantine metadata. The transaction acquires and holds the existing global security-barrier fence before source/auth row locks through commit, so a concurrent barrier/disable serializes with the read. Ordinary `DRAFT`, `PAUSED`, disabled credential, source epoch/config/mapping drift, and retired channel state do not independently deny a current Owner read. No ACTIVE-only ingestion proof loader is used.

## Lock order and error behavior

One caller-owned PoolClient transaction per page: `BEGIN`; `control.lock_security_barrier_fence()` first; exact `control.lock_source_credential(tenant,source)`; lock source registry row for update and compare current Owner/revision; call `auth.assertCurrentPrincipal(principal,'source:read',client)` (which locks and re-reads OIDC identity); read current locked subject epoch; invoke the narrow loader with verified tuple/current authority; `COMMIT`. All locks stay held through response materialization. Map principal rebinding to `AUTH_CONTEXT_CHANGED`, missing scope/non-Owner to `AUTH_FORBIDDEN`, inaccessible tenant/source per established safe source behavior, and DB/loader failures to `AUTH_UNAVAILABLE`. Do not use source credential authentication as Owner authority.
