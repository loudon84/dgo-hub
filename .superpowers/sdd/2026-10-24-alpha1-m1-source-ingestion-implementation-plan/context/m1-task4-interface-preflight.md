## Frozen `007` contract as observed at the pin

`raw.ingestion_batch` stores one immutable original request body as `bytea`, scoped to tenant/source/exact intake route, with a 1–4 MiB check and immutable UPDATE/DELETE rejection. `hub_api` receives only INSERT on its intake columns; `hub_worker` receives SELECT. This is the source of exact transport bytes; API-017/018 do not have raw-payload columns or permissions.

`control.ingestion_job` stores the accepted job, scoped idempotency key/digest, safe job status/counts, source/entity/route/batch/raw identifiers, and frozen admission proof: credential ID, source epoch at admission, credential revision/generation, channel ID/epoch/version domain, Owner approval/user/revision and approval security fence, config/mapping/identity-map revisions and digests, endpoint profile digest, test report ID, and security-barrier fence at admission. The update trigger prevents changing those receipt/proof facts; the worker may update only `status` and `applied_count` among job columns. Tenant/source and the scoped foreign keys are stored, but that does not give `hub_worker` implicit tenant RLS: code must bind tenant/source from the job and explicitly scope every read/update.

`control.ingestion_job_item` stores immutable ordinal/event/source PK/version/operation/time/public record facts. Its item state vocabulary is `RECEIVED`, `VALIDATING`, `APPLYING`, `APPLIED`, `DUPLICATE`, `IGNORED_STALE`, `QUARANTINED`, `RETRY_PENDING`; only `(status,error_code,updated_at)` is currently granted for worker updates. `source_version` is `numeric(20,0)` and `source_updated_at` is `timestamptz`; `public_record` is JSONB. Preserve the exact original body in `raw.ingestion_batch`; do not confuse JSONB’s structured fact representation with the raw transport bytes or rewrite source facts during adaptation. Task 3 fix R2 uses all submitted timestamp instants and retains microsecond endpoint precision. M1-4 must read validated timestamp lexemes from item facts/raw body and normalize without passing through JavaScript millisecond `Date` precision.

Carry the reviewed intake limits into the adapter: source PK and line identifier rules, 1–256 case-sensitive text customer source ID, 1–128 external identity IDs with no edge whitespace, line count <=200, exact monetary/quantity scale and precision, string-only enum checks, strict fields, safe schema paths, and nesting depth 32. Public `CONFIRMED`/`COMPLETED` orders require 1–200 lines; only `DRAFT`/`CANCELLED` may have an explicit empty array.

`control.ingestion_processing_outbox` is currently one row per job with only `id`, `job_id`, and `created_at`. Existing hub_worker access is SELECT only. There is no persisted lease, claimant, expiry, next-available time, ACK state, per-item operation identity, attempt count, or retry schedule in 007. Job status accepts `RECEIVED`, `PROCESSING`, `SUCCEEDED`, `PARTIAL`, `FAILED`.

Worker permissions in 007: SELECT on raw batch, job, item and processing outbox; UPDATE only job status/applied_count; UPDATE only item status/error_code/updated_at; and execute `control.lock_security_barrier_fence()`. No outbox mutation/ACK right exists. API permissions are narrow intake inserts/safe reads and do not include raw SELECT or canonical core DML. Maintain `REVOKE PUBLIC` and verify runtime grants with the actual shared worker role and least-privilege negative checks. The same trusted worker backend is permitted to process jobs across tenants; tenant boundaries are enforced by tenant-qualified queries and frozen apply proof, not a fictitious per-tenant database role or implicit RLS.

## Frozen M1-2 apply interface and role boundary

`ApplyContext` is a readonly input carrying tenant/source, credential ID, admission source epoch, credential revision/generation, entity, channel ID/epoch/version domain, Owner approval ID/user/revision, config/mapping/identity-mapping revisions and digests, endpoint profile digest, test report ID, and `securityBarrierFenceAtAdmission`. The caller-transaction entry points are:

- `applyCustomer(client: PoolClient, context, canonicalCustomerOrDelete)`
- `applyOrderAggregate(client: PoolClient, context, canonicalOrderOrDelete)`

The caller owns the transaction. The apply implementation first locks the global security barrier fence, then the source credential, checks immutable channel identity/epoch/version domain and exact frozen approval/test/config/mapping proof, then checks typed security barriers newer than the job admission fence. For M1-4, acquire that global guard before every other lock in the item apply transaction; only afterward verify and lock the outbox claim token/expiry, then lock the item and proceed through apply. Ordinary current epoch/generation mismatch is deliberately not a worker lifetime gate. Outcomes include `APPLIED`, `DUPLICATE`, `IGNORED_STALE`, `QUARANTINED` (`SOURCE_VERSION_CONFLICT`, `AUTHORITY_MAPPING_SUPERSEDED`, `SECURITY_BARRIER_ACTIVE`, mapping errors), and `CHANNEL_EPOCH_RETIRED`.

M1-2 worker role has DML only for canonical customer/order aggregates and complete order-line replacement, canonical source identity/reference, source version receipts, ownership audit/remap artifacts, and canonical apply outbox. It reads source config/mapping/identity mapping revisions, tests/approvals, channels and security barriers; it has the required lock/fence functions. It does not have permission to change source registry, tenant, credential, auth subject, Owner/config approvals, or barriers. M1-4 should call the apply functions as that existing worker role and add only job/outbox claims and result writes through a later narrow migration if needed.

`control.canonical_source_identity` is keyed by `(tenant_key,source_id,entity,source_pk)` and stores canonical object UUID plus live customer/order references. `control.source_version_receipt` is keyed by source/channel/entity/source PK and binds `SOURCE_VERSION` vs `SNAPSHOT_OBSERVATION`. `canonical_apply_outbox` is the immutable business apply side effect. Each canonical item apply must keep aggregate, receipt, and canonical apply outbox in the same transaction as durable item outcome; processing ACK is a separate queue fact and follows commit.

## Security and lifecycle rules to carry through

PRD §8.6 says a persisted job continues under its frozen config after ordinary pause/edit. It isolates unexecuted work on source overreach, credential compromise/leakage, or channel switch. M1 plan and Task 3 extend the typed barrier controls to explicit credential compromise/revocation, source-scope security removal, tenant disable, and channel retirement. The barrier table’s current types are `CREDENTIAL_COMPROMISE`, `SOURCE_SCOPE_SECURITY_REMOVAL`, `TENANT_DISABLED`, and `CHANNEL_RETIRED`. A same-credential security recovery with a new Owner approval fence authorizes new admissions only; it does not rewrite old job proof or delete historical barriers.

Do not treat source epoch, current config/mapping/Owner revision, or ordinary pause as a cancellation signal. Use the job’s frozen contract and allow M1-2 proof verification to decide whether it is still applicable. The narrower M1-2 `AUTHORITY_MAPPING_SUPERSEDED` correction can block affected queued work where an explicitly approved identity remap changed an existing canonical relationship; unrelated ordinary frozen jobs continue. A retired channel is isolated before version comparison. No path compares a REST source version with a snapshot observation.

## Contract cross-check and root rulings carried forward

- PRD §9.3 states the REST version matrix: lower version `IGNORED_STALE`; equal version/equal content `DUPLICATE`; equal version/different content isolated as `SOURCE_VERSION_CONFLICT`; higher version applies transactionally. Delete tombstones cannot be undone by equal/lower versions; only a higher explicit UPSERT can restore.
- PRD §9.3 says each batch item is processed/queried independently and gives job statuses `RECEIVED / PROCESSING / SUCCEEDED / PARTIAL / FAILED`. All `APPLIED`, `DUPLICATE`, or `IGNORED_STALE` yields `SUCCEEDED`; mixed terminal success/failure yields `PARTIAL`; all rejected yields `FAILED`. This job summary must be derived from persisted terminal item states, including after restart.
- PRD §9.4 freezes `5, 30, 120` second delays and “累计最多 3 次自动重试”: one initial application plus up to three automatic retries, at most four application starts. Persist attempt starts separately from retries. Claiming a job and skipping a terminal item do not consume an attempt. A started attempt remains counted, with its next due time and budget, across crash, lease expiry, and restart. Stable operation identity is per `(job_id, ordinal)`.
- Root fixed `applied_count` to actual `APPLIED` canonical effects only, including DELETE. `DUPLICATE` and `IGNORED_STALE` are successful terminal outcomes for `SUCCEEDED` but do not count as applied. Pending items and scheduled retries keep the job `PROCESSING`; mixed terminal success/quarantine is `PARTIAL`, and all terminal quarantine is `FAILED`.
- Manual quarantine retry and API-023/024 are deferred to M1-5. M1-4 adds no retry route and does not reinterpret old jobs under the latest mapping. FI-03 proves affected old-job isolation after an explicit remap fence while unrelated frozen work completes; it does not claim successful manual retry.
- Root’s latest Task 3 addendum requires explicit `lines` and permits `[]` only for `DRAFT`/`CANCELLED`; `CONFIRMED`/`COMPLETED` require 1–200. Task 3 report states intake enforces this before persistence. M1-4 must preserve the rule in its public-record adapter and state any defensive behavior for corrupted/legacy rows.
- API-017/018 remain the only job-status read surface in scope; raw/event payload remains private. API-060, snapshot run queries, UI/P04, and source changes are out of scope.

## Migration gap and worker transaction design

Root resolved the migration gap: M1-4 uses additive `008_durable_worker_leases_and_retries.sql`, extending the existing 007 outbox/items and worker grants; no duplicate queue is added. Migrations 001–007 are immutable. Root will renumber the M1-5 snapshot migration to 009 in the public plan.

Use one job-level lease on the existing one-row-per-job outbox. A short bounded claim transaction uses `FOR UPDATE SKIP LOCKED`, records claim token/lease expiry and commits before apply. It performs no auth/source mutation and carries no row lock into apply. Each item apply transaction first acquires the global security barrier guard. It then checks the current lease token/expiry under the outbox row lock and retains that lock through one item's mutation, while also serializing the item row. On expiry, a reclaimer issues a new token; a stale token cannot change status or ACK. ACK is token-fenced after commit and only when all items are terminal; otherwise release/reschedule the job for the next due item. This lock order keeps the global security guard ahead of all other apply locks and avoids claim/apply deadlocks.

Migration 008 stores a stable operation ID per `(job_id, ordinal)`, durable attempt-start count, retries-used count, and next due time. Commit attempt start before application begins; a crash after start preserves the consumed budget and due time. Claim and terminal skip do not consume an attempt. Crash after committed apply/status but before ACK leaves a terminal item, so replay skips it and ACKs without duplicate core/outbox effects. A failed item transaction leaves no partial canonical data, receipt, business outbox, or terminal item status.

## Observable assertions prepared for implementation

1. Competing workers claim distinct unexpired job leases with `SKIP LOCKED`; expired lease is reclaimable with a new token; old token cannot update or ACK. Verify positive and least-privilege negative behavior using the actual shared worker DB role.
2. Same item is serialized if a worker lease expires during apply; security fence is acquired before other apply locks; outbox lease row lock and item lock prevent double mutation and claim/apply deadlocks.
3. Failure injection at header, Nth order line, before status update and before COMMIT rolls the whole item TX back to an independent T0 oracle; no partial core row, receipt, canonical outbox, or terminal item result remains.
4. Crash after apply transaction commit but before ACK replays/skips terminal state; canonical receipt/outbox is unchanged. Crash before commit retries same operation identity/frozen proof.
5.
