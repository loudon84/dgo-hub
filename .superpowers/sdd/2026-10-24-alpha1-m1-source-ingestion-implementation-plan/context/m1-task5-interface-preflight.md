## Existing concrete seams at pin

### Connector, capability, endpoint, and secret seams

- `source-registry/service.ts` exports `Connector = 'rest' | 'postgresql' | 'sqlserver'`, `SyncMode`, `VersionDomain`, `SourceConfig`, `FieldMapping`, `IdentityMapping`, `SecretResolver`, `EndpointAllowlist`, `CapabilityProbe`, `SourceRegistryDependencies`, `createSourceRegistryService`, `SourceRegistryService`, and fail-closed default providers. `SourceConfig` already stores connector/mode/version domain, endpoint allowlist reference, secret reference, entities, delete contract, and the resolved endpoint profile in approved revisions.
- `SecretResolver` is exactly `isConfiguredReference(reference)` plus `resolve(reference): Promise<string>`. `EndpointAllowlist.resolve(reference)` returns a profile. `CapabilityProbe.run` receives config/profile/secret/mappings/identity mappings and returns pass/check codes. No new credential authority or secret store is needed.
- `source-registry/capability-probe.ts` exports `EndpointProfile`, `ProbeEnvironment`, `createBoundedCapabilityProbe`, `validateEndpointProfile`. PostgreSQL table identifiers are validated against an allowlist-like identifier grammar and individually quoted by the bounded probe; supported capability checks inspect `information_schema` and read-only permissions. `probePostgres` is only a bounded capability test. It does not create a long-lived consistent snapshot, stream all configured relations, prove completeness, persist stage pages, or reconcile deletes.
- There is no generic connector runtime/provider abstraction or injected PostgreSQL pool factory at this pin. The approved endpoint profile does not by itself represent permission to accept arbitrary DSNs/host/port input. M1-5 needs a narrow connector factory that takes the approved profile and in-memory resolved secret and returns an owned single-source pool/connection, with bounded lifetime, no secret persistence/logging, TLS/endpoint policy, and explicit close/discard. Avoid process-env source URLs and reuse of `resolveWorkerSources`.
- The endpoint profile has per-entity table and version/delete column names, but no demonstrated complete order-line relation contract. A mapping/schema gap must be settled before implementation: lines need their own approved relation, source line key, and fields/identity in the frozen config/contract; using implicit table or column names would violate mapping-derived identifier safety.

## Recommended durable contract for implementation

Freeze these structures before coding, with exact names/types finalized in the migration design review:

1. `control.etl_run`: immutable acceptance proof and run identity/scope; mutable status/counts/lease-safe lifecycle facts only. Unique active run guard scoped to `(tenant_key, source_id)` and a request idempotency key. Retain channel/config/mapping/identity-map/credential/Owner/test/endpoint/security proof and expected entity set.
2. `control.etl_run_attempt`: attempt ID, run FK, ordinal, stable operation ID, state, start/end/error, source-snapshot identity and retry budget/due time. If upstream transaction is lost, terminalize that extraction attempt as incomplete and require a new REPEATABLE READ scan attempt.
3. `control.etl_stage_record`: `(run_id, attempt_id, entity, source_pk[, source_line_pk])`, ordinal/page and mapped complete record facts/digest, exact version/timestamp strings, line ownership/header relation, validation state/error. Durable stage can be applied only when the run's all-entity manifest is `COMPLETE` and validated.
4. `control.etl_stage_page` or equivalent manifest: entity/page range, deterministic key boundaries, row count/digest and commit marker. Page receipt commits in the same destination transaction as page records. A source cursor remains session/transaction-bound and is never treated as a durable cursor after source connection loss.
5. `control.etl_range_receipt` plus checkpoint: range identity/digest/count/status and last fully applied range. Checkpoint advance and range receipt commit atomically with item effect/outcome. Idempotent replay uses stable `(run_id, attempt_id, entity, source_pk)` operation identity plus M1-2 version receipt/outbox. Do not advance any “complete snapshot” checkpoint until full validation.
6. `control.etl_delete_candidate` and an immutable approval/audit fact (or equivalent): source/run/channel/candidate revision, exact sorted candidate identities, recomputed SHA-256 digest, exact denominator active count, candidate count/ratio, consecutive successful full-run IDs, Owner ID/revision, approval and apply state. API-060 may authorize only this digest/revision. Do not retain a caller digest as proof; recompute server side.
7. Snapshot quarantine references durable run/stage record and preserves original source facts, frozen proof and safe error/dependency; API-023 presents summaries; API-024 appends a new explicit retry operation/frozen mapping decision and never overwrites original facts.

All stage pages may be durable while extraction continues, but until a final complete and fully validated manifest is committed, no stage page participates in absence/deletion inference, observation allocation, checkpoint completion, or canonical apply. Durable stage replay after that complete boundary is safe; source scan resume after losing its transaction is not.

## Root rulings and remaining load-bearing design issue

The following decisions are frozen for the M1-5 builder contract:

- A lost PostgreSQL source transaction means a fresh full scan attempt. Partial stage is diagnostic only and is never applied or used for absence. A fully complete and validated stage manifest may resume destination apply.
- The exact required entities are frozen from approved config `allowed_entities`. Customer-only is valid. Orders require an explicit approved line relation, source line key, order FK, and complete header/line mappings; the connector does not guess. `SOURCE_VERSION` requires a safe complete aggregate version and matching delete contract. Hard-delete absence without safe source version requires `SNAPSHOT_OBSERVATION`; otherwise fail closed.
- Page stage and immutable page receipts may persist before validation, but no observation, complete checkpoint, business apply, or absence reconciliation happens before the entire expected-entity manifest and validation report commit. Atomic apply is per complete customer/order aggregate plus receipt/outbox/outcome/range/checkpoint.
- Failed/stale/partial/invalid runs neither advance nor reset consecutive hard-delete absence. Successful complete absence advances; successful complete presence resets that identity.
- Hard-delete candidate set is per tenant/source/entity, over full source identity tuples. Denominator is exact active canonical objects in the same scope, frozen under serialization guard. Compare with integer arithmetic `candidate_count * 100 > active_count * 5`. Above 5%, pause before any candidate action and bind API-060 approval to the sorted full candidate keys, source/run/revision and exact denominator digest. Canonical core physical DELETE is forbidden; approved changes use logical tombstones with identity/version receipt preserved. At or below threshold, auto-reconcile only under explicit approved hard-delete contract.
- API-060 is `POST /hub/v1/admin/sources/{id}/delete-candidates/{candidate_id}/approve`. It uses existing `source:approve`, and requires the current enabled same-tenant exact bound Owner identity/revision. Server recomputes the set/digest; changed candidate set is 409. No new scope is added. API-007 approval remains a distinct source-config action.
- API-019/022 use `source:write`; API-020/021 and filtered API-023 use `source:read`; API-023/024/060 require current exact Owner according to the M1-5 root contract; API-024 also uses `source:approve`. Admin APIs reject source-token auth. API-019/022/024/060 require route-scoped tenant/source `Idempotency-Key`; safe pagination defaults 20/max 100.
- API-024 appends a retry operation and preserves original event/run/raw facts/proof. Unchanged mapping dependencies retry with original frozen proof. Changed target requires explicit current Owner reconfirmation and current approved mapping bound to original source identity, canonical UUID, and target. Never rewrite terminal original row, reset its barrier fence, or bypass an old security barrier; ambiguity remains quarantined/409.
- Migration 009 remains root-owned through the whole M1-5 phase. Phase reviews do not freeze it. Start with the minimal run/schedule foundation, add only needed schema in later focused diffs, or use a later migration only if implementation evidence requires it. Migrations 001–008 remain immutable.

The remaining load-bearing issue for Phase E is how to bootstrap approval for a pending channel without making pending configuration current or conflicting with existing approval uniqueness. The recommended sequence is a separately persisted pending config/channel revision, its own normal API-007 test/approval, complete validated staging with no business apply, then an exact current Owner reconciliation receipt bound to the final pending channel/config/reconciliation digest. One guarded caller transaction retires the old channel and activates pending config/new epoch. Apply under the new frozen proof starts only after cutover. Any precommit failure leaves the old channel current. Resolve the approval receipt and uniqueness details in a focused Phase E design review before coding.
