## Bootstrap assumptions that do not hold at the accepted source

1. **No pending source state exists.** A config revision can be inserted immutably without moving the current pointer, but current API/service code has no durable object that says which noncurrent config, maps, credential proof and complete pending channels belong together. The current config pointer cannot carry a second proof.
2. **The provisional API-006 test cannot be reused as written.** It is a current-revision-only test. Its successful/current attempt updates source lifecycle and its active-source path advances source epoch. It queries current `source_credential`, current maps and current config. Changing it to select arbitrary config revision without a switch-bound immutable snapshot would allow stale/mixed proof or a race with edits.
3. **The provisional API-007 preapproval cannot reuse `source_owner_approval` unchanged.** Existing approval is discovered by intake/snapshot code as the active current proof; it has no purpose/switch/channel-set columns and current approval sets lifecycle APPROVED. It must not be the receipt that authorizes pending stage or appear as a current-lane approval before cutover. A separate switch preapproval receipt (or explicit equivalent with purpose and binding) is needed.
4. **Current credential update is immediately effective.** The source config update path also changes the sole current source credential row and bumps generation/epoch. E2a cannot use that method to prepare a connector password/reference or a new source bearer. A pending reference and proof must be separate; credentials are promoted only in E3's atomic cutover.
5. **Channel validation is current-only.** `lock_source_channel` and strict ingestion resolve active channels; activate does not switch channels and cannot create a second active row because of the partial unique index. Pending channel rows can be reserved with next epoch, but no API binds them to a pending config/test/approval or verifies the whole set.
6. **Mapping revisions need explicit pending binding.** Field-map `mapping_revision` and identity-map `identity_mapping_revision` are separate, and each has an independent digest. Existing report/approval bind both, but the public bootstrap needs an explicit decision on whether a switch reuses current map revisions or stages new immutable map revisions. Do not overload the public `mapping_revision` with identity mapping revision.
7. **Stage-only validation belongs to E2b.** API-019 in 009 only admits the active current proof. E2a can establish pending config eligibility through capability metadata/permission checks and a preapproval, but cannot claim complete snapshot reconciliation, run validation, canonical apply, observation allocation, or delete-candidate behavior.

## Recommended E2a state and proof seam

Use unreleased 009 only for the smallest phase-owned additive schema. Keep current `source_registry` pointer, lifecycle, `source_credential` row, active channel set, and current approval unchanged throughout E2a. Require source identity `(tenant,source)` plus a unique `pending_switch_id`; allow only one open switch per source, and preserve every aborted/expired attempt as a terminal audit row rather than deleting its proof.

Recommended immutable header `control.source_channel_switch` (name provisional):

- stable `switch_id`, tenant/source, state `PREPARED | TESTED | PREAPPROVED | ABORTED | SUPERSEDED`;
- request idempotency key and request digest, actor, created/updated time;
- captured **current/base** config, field mapping and identity mapping revisions+digests; current source credential ID/revision/generation/source epoch (no digest or secret material); current Owner ID/revision; current complete active-channel set;
- **pending target** config revision+digest, field/identity revision+digests, endpoint/profile digest, contract, connector-secret reference identifier (or separate proof row), intended allowed entity set, and switch-proof digest;
- test report ID/result and preapproval ID once present, each tied to same switch proof digest.

Add a child `source_channel_switch_entity` keyed `(switch_id,entity)` with pending channel UUID/epoch/connector/mode/version-domain. It must exactly cover the sorted expected entity set; each pending epoch is `max(channel_epoch)+1` for that entity under the source lock. Insert in state `pending`; never activate or retire channels here. Store a canonical complete-set digest and reject a config whose entity set, credential scope, pending channel children and existing per-entity proof differ. FK proof revision+digest to immutable config/map rows and (where possible) channel rows to switch identity. Add DB constraints/guard so switch proof, entity set and pending channel identity cannot be rewritten after creation; lifecycle transitions are narrow state-only changes.

For a pending test, create a dedicated immutable `source_channel_switch_test` report keyed by UUID and unique on `(switch_id,switch_proof_digest,operation_id)`; include exact pending config/map/identity digests, endpoint digest, connector secret reference version/identifier, expected complete channel set digest, source identity result, safe check codes, PASS/FAIL, actor and timestamps. Do not insert a normal current `source_test_report` that current activate/intake might select as newest. After test I/O, re-lock and compare all captured current/base facts and pending switch proof digest before storing the report. A current-lane change during the probe invalidates the pending test (record stale/conflict), never silently retargets it.

Create a distinct `source_channel_switch_preapproval` receipt keyed by UUID and unique/idempotent over exact `(switch_id,proof_digest,test_report_id,owner_user_id,owner_revision)`. It grants only E2b stage eligibility for that exact pending switch; it is not `source_owner_approval`, not final reconciliation approval, and not a cutover token. Require PASS test with exact proof digest, exact current enabled same-tenant Owner and `source:approve`, exact current principal, exact same source tenant, and no matching newer typed security barrier. Inserting it sets switch state PREAPPROVED only; it does not change source lifecycle or current pointer/credential/channel.

### State transitions

```text
PREPARED --targeted capability proof PASS--> TESTED --exact current Owner preapproval--> PREAPPROVED
   |                                          |                                      |
   +--------------------- explicit abort/supersede (immutable terminal receipt) -----+
```

Configuration or Owner drift does not turn the switch into a current proof. If the captured base changes before preapproval, fail closed with `SOURCE_CONFLICT` and require a new switch; do not rewrite the old proof. Security-barrier match, disabled tenant/Owner, or credential compromise blocks testing/preapproval. Ordinary current config edits should conflict while an open switch exists or explicitly supersede it through a separate audited transition; they must never retarget the switch.

## Smallest bounded route contract; controller decisions required

Do not add a public route without controller ruling. Proposed minimal extension is to existing source routes, with strict disjoint request branches so legacy current-lane behavior remains unchanged:

1. Existing `PATCH /hub/v1/admin/sources/:id`: add a clearly discriminated `pending_switch` branch that supplies `expected_current_revision` and a complete pending config plus explicit mapping selection/material and connector credential proof reference. It prepares immutable target revisions and the complete pending entity/channel set but must not accept `data_owner_user_id` in the same branch. Stage requires `source:write`; pending identity mapping may only reuse current exact revision unless controller explicitly authorizes a separate pending identity-map input owned by `source:approve`.
2. Existing `POST .../:id/test`: retain `{expected_revision}` for current config. Add a separate pending branch keyed by `switch_id` and exact proof digest. It calls the existing bounded capability probe with the frozen pending config/profile/secret and selected maps, validates safe source identity/read-only permissions/schema, and writes only the pending test report. Scope remains source:write.
3. Existing `POST .../:id/approve`: retain current approval behavior. Add an explicitly named `purpose: 'PENDING_CHANNEL_SWITCH'` branch requiring `switch_id`, `test_report_id` and exact proof digest; exact current Owner plus source:approve produces a pending preapproval receipt only. No lifecycle APPROVED update.

Controller rulings needed before implementation:

- Whether to extend these existing route bodies as above or keep E2a as internal service operations until a separate public contract is approved. No new route is implied here.
- What “pending credential” means: **recommended minimum** is a pending connector `secret_ref` + resolver/endpoint proof while the current Hub source bearer digest/credential ID/revision/generation stays unchanged. If the requirement includes rotating the source bearer token, it needs a separate pending token/digest credential row and controlled issue/activation semantics; do not store it in current `source_credential` during E2a.
- Whether pending map material is supported in E2a. Lowest-risk baseline reuses exact current field and identity map revisions. If schema changes require new mappings, stage new immutable field/identity revisions and bind both digests to switch; identity mapping edits need explicit current-Owner approval authority, not ordinary source:write.
- How the source reports pending connector credentials. `secret_ref` is an opaque external reference, not secret bytes. Only pass resolved secret transiently to the bounded probe; never return it, persist material, or include it in report/error/log.
- Operation/idempotency contract for the three existing calls. Pending creation must be tenant/source/route scoped and replay same switch only after rechecking current principal, Owner/source authority, exact request digest and security barrier. Test/preapproval must bind exact switch proof and cannot replay authority after drift.

## Transaction, locks, grants, and effect boundary

Use existing caller-owned `PoolClient` and the barrier-first order. In DB phases: (1) `control.lock_security_barrier_fence()`; (2) lock exact `source_credential` row; (3) lock `source_registry`; (4) revalidate current principal/scopes and lock tenant/auth subject/current Owner; (5) lock switch header, then pending entity/channel rows in deterministic entity order; (6) read exact immutable config/map/test rows and relevant security-barrier facts; (7) insert/transition one switch receipt and commit. Match the current service's credential-before-registry order so pending operations serialize with current update. Do not call external network while holding row locks.

For the targeted test, use two short transactions around bounded probe I/O: first barrier-first lock/snapshot the current-base tuple and exact pending proof; release DB locks; resolve allowlisted profile and secret ref, run read-only capability probe; second transaction repeats barrier-first credential/source/Owner/switch locks and compares all captured base IDs/revisions/digests, pending proof digest and barrier state before persisting report. A stale capture yields conflict and no PASS report. Require missing/null token or lease checks wherever any asynchronous claim is introduced; simplest E2a need not introduce a worker claim if the bounded test remains synchronous.

New switch tables/functions: deny PUBLIC and all runtime principals by default. Prefer explicit column grants or narrow SECURITY DEFINER functions for prepare, report persistence, preapproval and page/read metadata. Keep hub_worker grants limited to current proof/channels unless E2b adds a separate stage-only claim/read. Do not widen `hub_api` to credential digests, secret material, raw source payload, stage records, canonical tables, observation allocation, snapshot apply, or delete candidate tables. E2a has zero writes to canonical customer/order, source-version receipts, snapshot observations, delete candidates, schedules, run state, current channel state, current config/credential pointers, and current source lifecycle.

## Bounded E2a acceptance oracles

- Stage a pending REST or PostgreSQL config while current config, source credential, source epoch/generation, current Owner approval, lifecycle and active channels remain byte-for-byte logically unchanged; only immutable new revision/switch/pending-channel rows appear.
- Exactly one pending switch per source; same idempotency request returns same switch after authority recheck; changed digest conflicts; another pending create conflicts without advancing any current revision.
- Pending channels include every and only configured allowed entity, each with unique next epoch and expected connector/mode/domain; no active channel count changes. Incomplete/extra set, mismatched credential scope or base drift fails closed.
- Bounded capability test uses exact pending digest and resolver ref, validates endpoint/profile/schema/read-only permission and order-line contract; external secret never appears in SQL output, API output, report JSON or error. PASS report is bound to switch and cannot be selected as current report or activate current lane.
- Concurrent current config/map/Owner/credential change during external probe causes stale proof conflict on second transaction; it cannot attach the PASS result to a newer switch or edit the original immutable proof.
- Preapproval needs exact same-tenant current enabled Owner + source:approve + current principal; ordinary source:write cannot approve. Owner revision change, revocation, typed barrier or retired/changed active channel proof causes conflict. Success creates pending preapproval only; source lifecycle/current config/current credential/active channels remain unchanged.
- DB-role checks prove hub_api can reach only intended switch operations/columns; hub_worker and source credential cannot create or approve pending switches; all current config/credential/channel mutation remains E3-only.
- E2a has no API-019 run, stage rows, `canonical_*`, `source_version_receipt`, observation, delete-candidate or business writes. That is the separate E2b stage-only contract and must be verified before cutover work.
