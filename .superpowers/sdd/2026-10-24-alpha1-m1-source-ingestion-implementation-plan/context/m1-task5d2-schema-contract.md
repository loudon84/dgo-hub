# M1-5D2 schema, function, lock, and grant contract

Fixed dispatch base: `7c8d815d81e015f1594c6990ee7853cc3ef7543c`; accepted product source: `634e0c84cf2cf3d7953feb1e03d35f3387b27dfd` (D1 Fix 1). D2 extends only phase-owned `integration-service/migrations/009_snapshot_runs_and_recovery.sql`. This contract was recorded before product edits from the accepted-pin preflight and bounded `git show` reads of the named seams.

## Existing authorities and facts

- API transactions use `AuthService.assertCurrentPrincipal(principal, scope, client)`. It calls `control.lock_api_identity(text,text)` and checks current identity mapping, enabled subject/tenant, and current scope. It does not return the locked row or compare an old principal epoch, so D2 will query the same locked authority in-transaction and bind its database `auth_epoch`.
- Lock order for D2: `control.lock_security_barrier_fence()` first; then source credential/source row (`control.lock_source_credential(text,text)`, `control.lock_etl_snapshot_source(text,text)`); enabled current source Owner and tenant/subject rows; `control.lock_api_identity(text,text)`; then run/reservation/candidate/approval/idempotency rows. Current Owner means source `data_owner_user_id` and `owner_revision` still match, and tenant plus Owner subject remain enabled.
- API-021 `GET /hub/v1/admin/etl-runs/:id` uses `getSnapshotRun(pool, auth, principal, runId)`, which checks `source:read`, takes barrier lock, revalidates principal, and tenant-scopes the run. D2 adds safe D summary and an explicit exact-member mode. The latter requires both current `source:read` and `source:approve`, exact current Owner, strict `candidate_id`, and the `limit`/`cursor` convention (default 20, max 100, base64url, C-collated full-key seek). Cursor claims tenant/source/run/candidate/revision/digest/last key.
- `control.etl_snapshot_delete_run` binds reservation `(tenant_key,source_id,run_id,attempt_id,reservation_ordinal)` to C facts `sequence_value` and `c_completed_at`, immutable after reservation. `scope_digest`/`stable_scope_json` bind once during the first successful consume, initially from `{}`/its hash. `candidate_count`/`above_threshold` bind on candidate freeze; existing freeze can later finalize an older consumed `PENDING` reservation as `COMPLETE` and zero its aggregate count. Preserve those exact lifecycle transitions in the guard. `status`, `pause_reason`, `last_worker_checked_at`, and `updated_at` are operational. Install the first D2 schema change as a selective UPDATE trigger rejecting changes to identity/C facts and any rebinding of scope/freeze facts while permitting only the observed one-time bind/finalization and operational transitions. Existing blanket immutable guard is `control.guard_etl_snapshot_delete_immutable()`; add a focused trigger/grant and real consume/freeze lifecycle regression. Do not grant direct UPDATE to API or worker.
- Frozen candidate schema is `control.etl_snapshot_delete_candidate(candidate_id,tenant_key,source_id,run_id,entity,candidate_revision,scope_digest,stable_scope_json,baseline_count,candidate_count,baseline_membership_digest,candidate_digest,frozen_at)`. D1 freezes only the denominator count, not its exact live member set; same-count replacement would otherwise evade D2 freshness. Extend phase-owned 009 with an immutable `baseline_membership_digest`, seeded from proof/scope, entity, count and folded over all eligible live baseline `(tenant_key,source_id,entity,source_pk COLLATE "C",canonical_object_id)` tuples in C order at freeze. Include that fingerprint in the candidate digest seed, then fold the exact candidate member tuples with the same SQL serializer; D2 recomputes both current baseline and candidate digests at approval and conflicts if any tuple changes, including equal-count swaps. Candidate members remain in `control.etl_snapshot_delete_candidate_member(candidate_id,...,source_pk,canonical_object_id,origin_run_id,second_run_id,sequence_value,inferred_completed_at)`. D3 can reconstruct the exact original baseline by unioning the current live baseline tuples with this candidate's own committed tombstone full tuples (retained source identity plus canonical UUID), then compare the same fingerprint; do not attempt to reverse a digest or subtract a count. D2 reads these only through fixed-search-path security-definer projections/procedures. Public member projection returns full key scope (`tenant_key`, `source_id`, `entity`, `source_pk`), never canonical UUID.
- Reuse `control.etl_snapshot_delete_proof_current(text,text,uuid)` and the exact SQL digest algorithm inside 009. Approval procedure recomputes digest from frozen proof JSON plus entity/run/revision/denominator/count and every member ordered by `source_pk COLLATE "C"`; caller digest is compared, never trusted. Currentness also checks latest reservation/run, latest same-revision test report (including FAIL), source Owner revision, source pause, and security barrier.
- Existing ratio helper is `control.etl_snapshot_delete_ratio_exceeds(bigint,bigint)`. More than 5% is a source-wide obligation: each above-threshold entity candidate gets a distinct approval; D2 leaves source paused and schedule disabled. Approval never mutates canonical identity or applies candidates.

## New phase-owned durable records and procedures

Add immutable approval, human audit, sensitive-read audit, and scoped idempotency result records with FKs/unique constraints binding tenant/source/run/candidate/entity/revision and request route/key. Approval stores exact digest, denominator/count, proof/scope and OBS basis, relevant run IDs, source Owner/revision, approver tenant/user/issuer/subject, locked DB `auth_epoch`, required scope `source:approve`, canonical request digest/key, reason, actor, and creation time. No bearer token or expiry is persisted. A changed DB auth epoch invalidates the approval for future D3 authority.

Expose only narrowly scoped `SECURITY DEFINER` functions (fixed `search_path`, actual effective-role check using the established `coalesce(nullif(current_setting('role',true),'none'),session_user)` convention rather than definer `current_user`, PUBLIC execute revoked) to `hub_api`: safe summary read; exact member page plus read audit; API-060 guarded approval/idempotency transaction plus approval audit. Deny API direct SELECT/INSERT/UPDATE on D tables and all canonical DML. Keep candidate application state/transition functions out of D2; no D3/worker grant is added here. Existing API grants on `control.lock_api_identity(text,text)` remain the principal authority.

API-060 procedure input binds path tenant/source/candidate and strict five-field body plus scoped idempotency key. Lock order follows the list above. It revalidates current principal, exact enabled Owner, current candidate/proof/digest/membership/denominator, current latest run, source pause, barrier, and all source-wide approval obligations before either initial approval or replay. Same scoped key plus same request returns the immutable original approval result; a different request conflicts. Stale authority or evidence returns 409 without approval. Result is HTTP 200; no schedule activation/unpause or business DML.

## Boundaries

Only API-021 safe summary/exact members and API-060 exact approval are added. API-014 remains the sole identity-mapping write path. Ordinary source readers never see member keys or approver OIDC identity. D1 C remains `COMPLETE` independently of D status. Formal 48/site/Hermes gates remain unverified absent their actual runtime evidence.
