### Manual recovery state and authority rules

- Preserve the original immutable source fact, run/stage, outcome, mappings, credential/config proof, and terminal state. New recovery operation rows should identify original fact + operation UUID + attempt(s) + exact frozen target; attempts should carry non-null claim token and live DB-time lease when claimed. Claims alone consume no durable starts. Use initial start plus at most three retries at DB-clock 5/30/120 seconds where a retry budget applies.
- Same-target retry is allowed only while current security barriers, source/credential authority, exact current Owner where gated, and the frozen proof remain valid. A consumed idempotency key rechecks those facts before returning the saved operation; authority drift cannot mint recovery authority by replay.
- Remap/reconfirmation requires an explicit Owner action bound to the original immutable fact, its full-qualified source identity, selected canonical UUID, and approved exact mapping revision/digest. Missing/ambiguous mapping, target drift, revoked Owner, matching barrier, or retired channel fail closed. Do not silently choose a new target or reinterpret another source object.
- C stage and outcomes already bind run/attempt, claim token, leases, manifest and validation digests. A retry after lost upstream MVCC connection must start a fresh complete source scan; incomplete pages/checkpoints do not become a valid completed stage. Do not “recover” by restarting a terminal original run or resetting its token/lease/status.
- Lock order for any recovery effect is global `lock_security_barrier_fence()` → exact source serialization fence → recovery operation/claim and immutable source fact → current Owner/authority rows → existing canonical helper locks. Hold exact non-NULL token + unexpired non-NULL lease and current authority locks through one aggregate/effect/outcome commit. Existing D worker follows guard/source/D-run/candidate/authority/canonical order; C aggregate path uses guard, asserts claim then delegates to canonical helpers. Keep epoch-retirement/barrier evaluation before source-version comparison.

## E2/E3: pending stage and cutover limits

The bootstrap is directionally sound on preserving current credential proof and making final Owner confirmation a separate immutable reconciliation receipt, but is not implementation-ready:

1. Existing `POST /sources/:id/test` and `/approve` accept only the current config. `source-registry/service.ts:test()` persists current config/mapping/identity/profile and credential proof; `approve()` requires current revision + `TESTED` + exact current bound Owner. `activate()` requires current revision/approval, validates current credential/profile, and can only create epoch 1 when there is no channel history. Existing `PATCH /sources/:id` promotes new config to `current_config_revision`, updates the sole AuthService credential row and source epoch, and rejects a connector/mode/domain change while active or pending channel exists. These are not pending-configuration APIs.
2. `API-019 createSnapshotRun(pool, auth, principal, sourceId, approvedConfigRevision, idempotencyKey)` requires source:write, locks the global security fence, current principal, source credential, source row, and active channels; requires lifecycle ACTIVE, current revision, matching enabled credential/tenant, existing test/Owner approval and no matching barrier. It inserts a normal `etl_run` whose worker path reaches validation and canonical apply. `snapshot_stage` and C continuation proof loader are bound to that current active-channel run. Calling it for a switch either fails on PAUSED/current revision or runs business apply against an ordinary current lane. Do not add a late “skip apply” branch to the ordinary worker as the only stage-only boundary.
3. Pending configuration, endpoint/profile, mappings, credential revision/generation/secret ref and one pending immutable channel per configured entity need separate frozen proof and purpose. Freeze the complete sorted entity set and exact channel IDs/epochs/version domains before staging. The existing one-active-primary unique index requires retiring old channel before promoting pending rows, in one transaction. Failed cutover must roll back all lane changes. New epoch is `previous max + 1`; retired channels never reactivate.
4. Approval has two separate gates: pending config capability test + config permission to stage; then final validated stage/digest approval by the exact *current* Owner for cutover. Do not make stage eligibility depend on pending channel already active (circular). Do not reuse `source_owner_approval` as a reconciliation digest receipt; it has no channel/run/digest identity or business-key UNIQUE. Use an immutable, exact-tuple final receipt with idempotency, and repeat current Owner ID/revision/enabled + source:approve checks both at receipt creation and cutover. API-007 currently lacks idempotency and has a bounded contract-ref generated as `${sourceId}/config/${revision}/contract`; don't assume it can represent a max-length 256-character source ID plus suffix.
5. Stage-only must prove the same full immutable snapshot identity and complete customer/order/header/line set, exact decimals/timestamps, mapping/identity mapping, current endpoint profile and pending credential proof; it must stop before observation allocation that has business-version meaning, canonical helper invocation, deletion candidate/checkpoint advancement or application outbox. No partial/lost scan can satisfy final approval. Current C loader expects complete C state and current active channels; its assumptions require an explicit separate pending proof/load/validation path.

### API-022 input and immutable retry shape

The PRD API table specifies `POST /hub/v1/admin/etl-runs/{id}/retry` core input **“原失败版本、reason”** (the original failed version and a reason), output a **new attempt** that reuses a reliable cursor, with `202/409`. It does not give a literal JSON property spelling; use `failed_version` as the request field for the original failure version, alongside `reason`, and document it as an optimistic concurrency token for the failed run version/state. It is a run failure version, not `source_version`. Current `etl_run` has no failure-version counter, so 009 needs a monotonic `failure_version` or an equally explicit state revision; `updated_at` alone is not a safe semantic version. API-024 PRD core input remains `expected_state,mapping_revision,reason`; expected state is the original quarantine record version, not the source record's version.

Do not implement API-022 by transitioning a terminal `FAILED` run to `SCANNING` or reusing its terminal `etl_run_attempt`: the run/status, attempt operation IDs, stage pages, manifest, C validation, outcomes and ranges are immutable facts or have terminal status, and API-019 idempotency is already bound to `(tenant,source,route,key)`. Migration 009 allows at most four automatic extraction attempts per run; manual retry after exhaustion needs a new linked recovery run/operation with a fresh attempt and exact copied frozen source proof, while the original run remains FAILED. If a complete extracted manifest exists, link the new operation to the original sealed stage/digest and resume only unapplied aggregates under a distinct recovery attempt; never rescan and silently replace the original stage. If extraction failed before a complete manifest (including lost MVCC connection), create a linked child and do a fresh full consistent scan; do not resume from partial page cursor.

The child operation must retain `original_run_id`, `original_attempt_id`, failed-version CAS value, exact proof digest and one new immutable operation ID. Same-key replay returns that same child only after rechecking current caller scope, exact source/owner as required, current typed barriers and channel retirement; it cannot create another child or broaden target identity. Ordinary config/epoch drift alone is not a security barrier and must not disqualify an already durable operation's frozen proof. Explicit credential compromise/scope-removal/tenant-disabled/channel-retired barriers do disqualify it; no latest-config retargeting. Verify `CHANNEL_EPOCH_RETIRED`/barrier rejection before comparing source versions.

Avoid counting a child replay of a fully sealed C snapshot as an additional successful deletion observation. Link the child to its original run and teach the D reservation/cohort selection to count the original snapshot lineage at most once. A fresh full rescan after incomplete extraction has a new actual source snapshot identity, but API-022 replay must still not manufacture two D absences for one retry lineage. Do not reuse or reset D1/D2/D3 candidate/effect rows; D remains accepted and its own one-currentness/one-effect rules continue to govern deletes.

### E1a/E1b dispatch recommendation updated from the matrix

- **E1a functional path:** API-022 linked child retry for failed run versions plus API-023 redacted quarantine read and API-024 same-target REST item retry. API-024 should create a child `ingestion_job`/new immutable recovery-operation linkage and fresh item `operation_id`, reusing the original public record and frozen proof; the existing worker can then claim its ordinary outbox and run the same canonical helper. Bind `expected_state` + mapping revision + route/source scope into API idempotency; preserve original item/job and error. It must perform real canonical work, not return an operation receipt without a worker effect. Ensure the child schema can reference the same `raw_batch_id` while satisfying strict route/entity checks, or use a narrowly granted worker operation queue that executes `applyCustomer`/`applyOrderAggregate` with the same full proof. Do not grant hub_api direct canonical/business table writes.
- **E1b remap path:** only when the new mapping revision changes or creates a canonical target, or no prior target evidence exists. Requires current exact Owner confirmation explicitly linking original `(tenant,source,entity,source_pk/full identity)` to the exact canonical UUID and mapping revision/digest. Persist as immutable remap/recovery receipt; prevent duplicate/ambiguous aliases and add the narrow identity fence needed so old jobs cannot revert the approved correction. Do not hide this authority change inside ordinary retry.
- **API-022 stage semantics:** C extraction failure before manifest starts a fresh consistent snapshot in a linked child; fully sealed C validation/application recovery consumes the exact original stage and scope digest with per-aggregate idempotent ranges, and does not allocate a second observation. Preserve the original failure state in either case. Failed/partial C never advances D absence; if a stage replay yields another completion record, D consumes its lineage only once.
