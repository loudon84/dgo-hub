- `control.finish_etl_snapshot_run(tenant,source,run,attempt,claim)` first checks the current C continuation claim and durable validation seal, counts expected staged customer/order aggregates, and requires one terminal outcome per expected aggregate. On success, in one function transaction it sets run status `COMPLETE`, `completed_at=clock_timestamp()`, safe completeness summary and applied count, and clears the matching schedule active run while advancing schedule due time/last-success. On failure, it records run failure and releases the matching schedule slot. It clears the matching C claim. D1 must insert the D reservation and any D `PENDING`/`SKIPPED` summary in the same successful C finish transaction before clearing `active_run_id`; a later D claim would leave a race window for API-019 or due admission.
- `control.claim_etl_snapshot_continuation` and `control.assert_etl_snapshot_continuation` acquire `control.lock_security_barrier_fence()` before `control.lock_etl_snapshot_source(tenant,source)`, bind exact run/attempt/token/lease and active schedule identity, and reject applicable typed barriers (`TENANT_DISABLED`, `CREDENTIAL_COMPROMISE`, `SOURCE_SCOPE_SECURITY_REMOVAL`, `CHANNEL_RETIRED`). Reuse this established guard/fence ordering and add D checks without weakening these conditions.
- `control.persist_etl_snapshot_observation` requires the matching durable validation seal and semantic/proof digests, binds the run to an already chosen observation, and only considers the current allocated high-water `next_value-1` for reuse; the candidate reuse scope and a prior `COMPLETE` binding must match. - C `COMPLETE` itself means all expected aggregate outcomes exist and none is `QUARANTINED`, `CHANNEL_EPOCH_RETIRED`, or `FAILED`. D must remain a separate reconciliation dimension; changing C status after the fact would falsify C's approved contract.

## D contract clarifications from controller

1. An eligible run scope includes frozen config, field mapping, identity mapping, endpoint/profile, Owner/approval, channel/domain, entity and delete-contract proof. A complete run with changed scope starts a fresh streak at 1. Failed/partial runs neither increment nor reset. Preserve old facts for diagnosis.
2. D source-busy states `PENDING`, `AWAITING_OWNER`, `APPLYING` block API-019 and due admission; activation during unresolved approval/action returns 409. C already admitted under original proof drains first. D candidate effects wait until no C active run. Terminal D `FAILED/STALE/COMPLETE/SKIPPED` releases reservation but preserves pause and cannot enable scheduling. Currentness drift in Owner/proof/newer C makes the candidate `STALE`, never silently retains its approval.
3. D reservation is created in the same successful C finish transaction that writes C `COMPLETE` and clears the active C slot, only for an eligible absence-enabled `SNAPSHOT_OBSERVATION` contract. Unsupported/no-contract runs receive safe `SKIPPED` reconciliation summary and no fabricated `SOURCE_VERSION` tombstone.
4. `baseline_count` is immutable. Before each candidate effect, expected current active count is baseline minus this exact candidate's successful D tombstones. Those own tombstones do not stale the remaining set. Unrelated count or membership change stales before the next effect.
5. C OBS time/sequence is immutable and never worker wall-clock or incremented. The inferred absence deletion timestamp is DB `completed_at` of the second successful complete snapshot establishing that streak; explicitly describe it as observed/inferred time, not a source event. Candidate binds origin run(s), second run and its already-bound observation; apply only if OBS is greater than last presence receipt.
6. Backlog is chronological and each C `COMPLETE` run is consumed once. Never let an older absence act over newer presence. Freeze/action the latest current cohort only after newer pending run presence facts have been processed. Resolve the exact ordering/current-canonical race in D1/D3 with the least state needed; no unreviewed queue or new authorization.
7. Every future implementation evidence command uses a fresh UUID runtime under absolute `M0_RUN_EVIDENCE_ROOT`; record actual HEAD and dirty/blob source before/after with explicit whitelist, and owned PostgreSQL/Node child cleanup. Do not broaden tests here; this is a planning-only task.
