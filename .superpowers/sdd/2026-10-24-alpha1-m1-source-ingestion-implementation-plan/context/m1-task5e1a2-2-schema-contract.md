## Canonical request and digests

Canonical JSON means ECMAScript `JSON.stringify` of the ordered object specified below, encoded UTF-8 without BOM, whitespace, trailing newline or Unicode normalization. Strings use JSON.stringify escaping, including its handling of control characters and lone surrogates. UUIDs are canonical lowercase; decimal revisions are strings in canonical positive decimal form. Trim reason with ECMAScript `String.prototype.trim`, then require 1–1000 code points using `Array.from`.

API digest is SHA-256 over eight length-prefixed UTF-8 strings in exact order: `hub.recovery.api024.v1`, tenant, source, literal route template `/hub/v1/admin/quarantine/{quarantine_id}/retry`, quarantine UUID, expected state, field mapping revision, and `JSON.stringify(trimmed reason)`. Each field has a four-byte unsigned big-endian byte length followed by exactly those UTF-8 bytes. No BOM, separators or newline are included. The definer recomputes and compares the digest from the locked scoped origin and supplied normalized fields. Expected state is unpadded base64url of UTF-8 `JSON.stringify({v:1,quarantine_id,generation:"0"})`, with precisely that field order; reject unless decoding and re-encoding yields the exact supplied string.
Child digest is SHA-256 over the concatenation of 18 length-prefixed UTF-8 strings, in this exact order: `hub.recovery.rest.v1`, tenant, source, original ingestion route, quarantine_id, operation_id, origin_job_id, origin_ordinal, event_id, source_pk, source_version, operation, channel_id, channel_epoch, owner_approval_id, lowercase config digest hex, lowercase field mapping digest hex, lowercase identity mapping digest hex. For each string append a four-byte unsigned big-endian byte length followed by its exact UTF-8 bytes; there is no terminator, BOM, separator, or newline. Ordinal, version and epoch are canonical decimal strings, UUIDs lowercase. SQL computes this inside the definer from the immutable original, with `int4send(octet_length(convert_to(value,'UTF8'))) || convert_to(value,'UTF8')`; each input is bounded below 2^31 bytes. SHA-256 results are 32-byte bytea. The separate domains do not reserve a public key namespace or prove collision impossibility. Generate a fresh valid random child key; insertion collision rolls back and returns `IDEMPOTENCY_CONFLICT`.

## Locking and race contract

All recovery, replay and worker verification runs under `control.lock_security_barrier_fence()` for the complete transaction. Source evidence: `006_canonical_data_and_receipts.sql:10` takes exclusive transaction advisory lock `(1296905544,1)`; `remap_canonical_identity` acquires that guard at line 641 before inserting/updating the remap fence and changing canonical references. `normalization/apply.ts` acquires the same guard in `verifyFrozenApplyContext` before credential/proof/receipt and identity processing; both customer and order call it before any receipt or identity path, including creation for a missing identity. `etl-worker/worker.ts` apply transaction takes guard before claim row and calls canonical apply before commit. Thus the global guard serializes actual remap, normal canonical apply, recovery acceptance and worker check, including absent identity and multiple identities, and makes ordering among identity locks non-deadlocking across those cooperating writers. It is not enough to take a new advisory lock only in recovery.

After guard: API locks source credential, source registry, current OIDC authority, then private origin/link and target rows. Worker takes claim and item rows after guard, then the same verification under guard immediately before canonical apply. Within each transaction acquire source identity advisory locks `(hashtext(tenant),hashtext(JSON.stringify([source,entity,source_pk])))` in deterministic lexical tuple order, followed by identity row `FOR UPDATE`; check own UUID and order referenced customer tuple. The global guard is the actual cross-writer serialization, since API-014 remap does not take these per-identity advisories. The guard stays held until transaction completion, including canonical write. Verify exact active original channel/epoch/domain and frozen approval, PASS report, config, field and identity digests, credential identity and barriers after original fence; do not require current generation/config equality. Reject a later matching identity remap fence and missing or mismatched original targets; allow unavailable but provable exact dependency. Recheck the same proof on replay and at worker apply. Never allocate identity to prove eligibility.

Identical concurrent keys serialize and return the same IDs after full current authority and target recheck; reused key with changed digest is `IDEMPOTENCY_CONFLICT`, consumed CAS or field mismatch `SOURCE_CONFLICT`, absent/changed identity or remap `RECOVERY_TARGET_CONFLICT`, and snapshot `RECOVERY_SCOPE_UNAVAILABLE`. No source write credential is implied by approval. Strict malformed input uses 400; existing auth/non-enumeration and DB error envelopes apply. All failures leave original and linked facts unchanged.

## Helper interface and authority lookup

`control.resolve_recovery_owner_origin(tenant,quarantine_id,user,issuer,subject,auth_epoch)` executes only for effective `hub_api`. It first takes the global guard, then reads the immutable index by `(tenant,quarantine_id)` internally to identify the source without returning it. It locks that source credential, source registry and `(tenant,subject,binding)` rows in the existing API-023 order, checks enabled tenant/subject/binding, exact issuer/subject/auth epoch, current Owner and `source:approve`, and returns only source ID and current Owner revision on success. An absent/inaccessible origin yields the same safe not-found response. The calling API subsequently invokes `assertCurrentPrincipal` in the same client transaction and repeats the owner comparison, holds all locks through commit and never trusts a source ID supplied by the request. The insertion helper repeats role and authority checks itself, and selects the immutable original by its full scoped identity; no caller-supplied proof or target is authoritative.

`control.check_recovery_worker_binding(tenant,source,job_id,ordinal,operation_id,claim_token)` executes only for effective `hub_worker`, takes the guard, and verifies the matching unacknowledged outbox with a non-null exact claim token and live non-null lease, the scoped APPLYING item, and immutable operation link. It returns `ORDINARY` only when no link exists for that child job; recovery link and item operation ID must match. For a linked child it checks the stored binding, original proof and remap fence under the guard and deterministic identity advisory/row locks, returning `VALID` or a safe target conflict. The worker holds its existing claim/item locks, calls this helper before `verifyOrderCustomerReference` and canonical apply in the same transaction, and records a terminal quarantine on target conflict without applying. `ORDINARY` retains existing behavior. A new link cannot be introduced on an existing ordinary job because the creation helper generates and inserts the job/item/link together; child job uniqueness and scoped FKs enforce this relationship. The worker does not receive target values or payload from the helper. The checks must include all frozen proof and target predicates before returning VALID, including on receipt duplicate paths.

The creation transaction inserts the fresh child job, child item, operation link, then processing outbox in FK order; any exception aborts the transaction. 

## Concrete operation relation

`control.ingestion_recovery_operation` columns are: `operation_id uuid PRIMARY KEY`; `quarantine_id uuid NOT NULL UNIQUE`; `tenant_key text NOT NULL`, `source_id text NOT NULL`, `entity text NOT NULL`; `origin_job_id uuid NOT NULL`, `origin_ordinal integer NOT NULL`, `event_id uuid NOT NULL`, `source_pk text NOT NULL`, `origin_operation text NOT NULL` restricted to UPSERT or DELETE; `child_job_id uuid NOT NULL UNIQUE`, `child_ordinal integer NOT NULL CHECK(child_ordinal=0)`; `route text NOT NULL CHECK(route='/hub/v1/admin/quarantine/{quarantine_id}/retry')`, `idempotency_key text NOT NULL CHECK(idempotency_key ~ '^[A-Za-z0-9._:-]{1,128}$')`, `request_digest bytea NOT NULL CHECK(octet_length(request_digest)=32)`, `expected_state text NOT NULL`, `mapping_revision bigint NOT NULL CHECK(mapping_revision>0)`, `reason_json text NOT NULL CHECK(char_length(reason_json) BETWEEN 2 AND 6002)`, `approved_by text NOT NULL`, `approved_owner_revision bigint NOT NULL CHECK(approved_owner_revision>0)`; `own_object_id uuid NOT NULL`, `binding_kind text NOT NULL`, `user_external_id text`, `user_target_id text`, `department_external_id text`, `department_target_id text`, `customer_source_id text`, `customer_source_pk text`, `customer_object_id uuid`, `created_at timestamptz NOT NULL DEFAULT clock_timestamp()`. A unique `(tenant_key,source_id,route,idempotency_key)` is required. `binding_kind` is `DELETE`, `CUSTOMER`, or `ORDER`; a CHECK requires only own UUID for DELETE; all four user/department text fields for CUSTOMER; all three customer tuple/UUID fields for ORDER; unrelated fields are NULL. Entity must match the binding kind except DELETE. The API trims and bounds the reason at 1–1000 Unicode code points. Its immutable JSON string representation preserves embedded NUL and unpaired UTF-16 surrogates, and is the final digest field; SQL bounds the encoded representation to 2–6002 characters.

Add unique index on index `(quarantine_id,tenant_key,source_id,entity,job_id,ordinal,event_id,source_pk)`; FK the matching origin columns to it. Add unique index on item `(job_id,ordinal,event_id,source_pk,operation_id)`; FK `(child_job_id,child_ordinal,event_id,source_pk,operation_id)` to it. A unique item index `(job_id,ordinal,event_id,source_pk,operation)` supports scoped FKs from both origin and child tuples, enforcing the same operation. CHECKs bind DELETE to `origin_operation=DELETE` and customer/order bindings to UPSERT. FK child `(child_job_id,tenant_key,source_id,entity)` to job `(id,tenant_key,source_id,entity)`. These and all links use `ON UPDATE RESTRICT ON DELETE RESTRICT`. An immutable UPDATE/DELETE trigger rejects modifications with 55000. All suffix indexes and tables use idempotent creation, and function/trigger creation is replay-safe for the suffix; existing full 009 remains unchanged before the suffix.
