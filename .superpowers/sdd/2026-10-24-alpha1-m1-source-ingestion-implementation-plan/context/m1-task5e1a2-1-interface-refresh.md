## Contract corrections and pinned limits

`GET /hub/v1/admin/quarantine` is absent at this pin. The only legacy retry route in `integration-service/ingestion-api/routes.ts` is `POST /admin/etl/:source/retry`; it updates an ETL watermark and supplies no API-023 behavior. The draft is otherwise compatible with the existing response envelope shape, but should lock these details before implementation:

| Input / identity | Pinned source constraint | Recommended API-023 rule |
|---|---|---|
| `source_id` | Source-registry `SOURCE_ID` is `^[A-Za-z0-9][A-Za-z0-9._:-]{0,255}$` (`source-registry/service.ts`); max 256 characters. | Required scalar, 1–256 chars, exact regex; reject arrays/repeated keys. |
| `origin_kind` | No existing enum for a unified quarantine listing. | Optional exact `REST` or `SNAPSHOT`, uppercase only. |
| `error_code` | REST item accepts `^[A-Z][A-Z0-9_]{0,95}$`; snapshot outcome accepts `^[A-Z0-9_:-]{1,96}$`. REST item code is nullable and snapshot outcome code has no length/pattern check in this schema. | Optional 1–96 chars matching the snapshot superset `^[A-Z0-9_:-]+$`; match stored values exactly. Do not assume codes are non-null or invent a code enum. |
| `limit` | Existing ingestion read routes use default 20, max 100 and reject noncanonical forms with `AUTH_INPUT_INVALID`. | Preserve draft: canonical `1`–`100` decimal, default 20; reject 0, leading zeroes, signs, arrays, and >100. |
| `cursor` | Existing `strict-ingestion.ts` cursor is canonical base64url JSON, max 256 chars, and binds a job id/ordinal; registry customer cursor max is 1024 and binds source id/source key. Use the pinned application’s established signed-cursor facility if one exists; none was found in the inspected seams. Fastify routes read `request.query`; the new handler must explicitly reject any `Array.isArray` value and unknown keys. Do not rely on TypeScript query types to reject repeated query parameters. Invalid query/cursor syntax maps to existing `AUTH_INPUT_INVALID` (400). Keep established auth mappings: `AUTH_INVALID`/`AUTH_CONTEXT_CHANGED` (401), `AUTH_FORBIDDEN` (403), `SOURCE_NOT_FOUND` (404), `SOURCE_CONFLICT` (409), `AUTH_UNAVAILABLE` (503); safe not-found behavior may use the existing `NOT_FOUND` envelope used by strict job reads. Do not introduce quarantine-specific public error codes in this slice. A source that exists but is not owned by the caller should receive the same safe denial class as other forbidden management operations, without returning whether quarantine rows exist.

## Full immutable origin identity

The actual origin schemas require a specific normalization that the draft should state explicitly:

* REST quarantine origin is `(tenant_key, source_id, job_id, ordinal)`. `ingestion_job_item` has `PRIMARY KEY(job_id,ordinal)`, immutable `event_id`, `source_pk` length 1–128, mutable `status,error_code,updated_at`, and no item `created_at`. The parent job supplies entity, route and all frozen proof columns. REST error code is nullable.
* Snapshot origin is `(tenant_key, source_id, run_id, attempt_id, entity, relation, parent_source_pk, source_pk, outcome_id)`. `etl_snapshot_apply_outcome` has `outcome_id` UUID, unique natural key `(tenant,source,run,attempt,entity,relation,parent_source_pk,source_pk)`, `parent_source_pk text NOT NULL DEFAULT ''`, and FK to the exact stage-record key. The associated range uses the same natural key and links the outcome. `parent_source_pk` is never SQL NULL for this schema: preserve empty string `''` for parentless customer/order aggregates and the exact nonempty parent key when present. Do not convert `''` to NULL or use a nullable unique-key shortcut; PostgreSQL ordinary unique constraints treat NULLs as distinct.
* Snapshot C outcome `relation` is only `customer` or `order`; `entity` is customer/order. `order_line` exists in staged records, not in this outcome relation. The draft's generic promise of distinct parent/relation keys across current eligible snapshot outcomes is stronger than the actual outcome schema can produce. Test all supported key forms, including the empty-parent sentinel, but do not fabricate an `order_line` quarantine origin.
* Backfill only REST item rows with status `QUARANTINED` and snapshot apply outcomes with status `QUARANTINED`. `CHANNEL_EPOCH_RETIRED` is a real separate outcome status, not currently a quarantine status; omit from this index unless controller explicitly revises the inclusion contract. `DUPLICATE`, `FAILED`, `IGNORED_STALE`, and run-level failures remain excluded.

The generated public UUID is the common stable ID. Index origin columns need composite FKs to the complete REST and snapshot origins and a unique constraint for each discriminator's complete natural key. A pair of partial unique indexes, one over REST key columns and one over the full snapshot natural key, is clearer than nullable uniqueness. Use a CHECK that enforces mutually exclusive key groups. Store the source's immutable terminal status/error and time plus only the proof references/digests needed for a safe summary; do not copy `public_record`, raw bytes, stage `facts`, or provider text. A snapshot FK/check using the `outcome_id` and complete natural tuple is necessary to prevent a bare-UUID cross-source join.

## Authorization, lock and role seam

The current TypeScript authority pattern is in `integration-service/source-registry/service.ts` and `integration-service/auth/service.ts`:

1. Begin one DB transaction; acquire `control.lock_security_barrier_fence()` first.
2. Lock exact source credential via `control.lock_source_credential(tenant,source)`; then lock the tenant-scoped `source_registry` row (`FOR UPDATE`). The service's `sourceRow(..., true)` uses this order.
3. Compare `source_registry.data_owner_user_id` exactly with verified `UserPrincipal.userId`; require `source:read`. Lock current tenant and `auth_subject` (the existing `currentOwner` pattern) and call `auth.assertCurrentPrincipal(principal,'source:read',client)`. That method re-reads the bound OIDC principal under lock, compares user/tenant/issuer/subject and checks current scope; context changes map to `AUTH_CONTEXT_CHANGED`, missing scope to `AUTH_FORBIDDEN`. It does not compare `principal.authEpoch` to the newly read epoch. Select the current locked subject epoch explicitly for the cursor binding (and ensure each request reauthenticates the principal); do not label the method itself an epoch comparison. A revision-only check is insufficient: exact current Owner and enabled subject/tenant/binding must be current.
4. Read the index only after those checks and while the same locks remain held. The current source_registry API grants are broad (`005_source_registry.sql` grants SELECT/INSERT/UPDATE to `hub_api`), so no additional broad table grant is needed or justified. The snapshot run/outcome/stage tables are intentionally not directly granted to `hub_api`; the index also should not receive direct table access. Expose a narrow `SECURITY DEFINER` loader, fixed `search_path=pg_catalog,control`, revoked from PUBLIC and all roles except the exact API role, with explicit return columns and verified scope parameters. The loader must validate tenant/source/current Owner and current auth tuple internally or be called only after the TypeScript transaction checks above; do not trust a body-supplied tenant/Owner. It may return only index metadata and typed dependency codes. No raw or stage body authority is required.

Recommended application seam: add a focused `registerQuarantineReadRoutes(app, {pool, authenticator, authService, quarantineStore})` registered from the ingestion API route composition, plus `parseQuarantineQuery`, `encodeQuarantineCursor`/`decodeQuarantineCursor`, and `quarantineStore.listCurrentOwnerPage(client, principal, sourceId, filters, after, limit)`. The route authenticates a user OIDC bearer only (no source credential actor), and the store receives the already-verified `UserPrincipal`; it must not accept tenant/Owner in query/body. SQL page seek is `created_at < $last_created OR (created_at = $last_created AND quarantine_id < $last_id)`, ordered descending, `LIMIT limit+1`. Cursor authority is compared to the current DB source owner/revision and the locked current subject auth epoch before seeking. Current-owner checks and page query belong to one transaction.

For the migration, add the index plus one narrowly owned writer seam for live capture, not table grants to `hub_api` or `hub_worker`. REST capture should be part of the same transaction that changes the existing item to `QUARANTINED`; snapshot capture should be part of the same transaction that inserts the corresponding terminal apply outcome. Any index-write failure must abort that original transition/insert. Backfill and live capture must share the same immutable-origin uniqueness rule and preserve the first generated quarantine UUID on conflict. Migrations 001–008 remain untouched; the controller already designates 009 as phase-owned.

## Acceptance fixture adjustment

The draft's “at least 23 actual eligible mixed origins” is achievable without copying the broad snapshot harness: use the existing focused DB/API fixture once to create an owned source and valid frozen proof, create one REST batch with 12 records and drive them through the ordinary worker to genuine `QUARANTINED` item outcomes, then create one valid small snapshot run with 11 eligible customer/order stage aggregates and drive C through its ordinary claimed continuation to genuine `QUARANTINED` outcomes. Query all 23 through API-023 and check exact complete origin tuples, mixed-origin paging at 20 and a small limit, stable unique IDs, and no payload fields. Include parentless `parent_source_pk=''` and both current snapshot relations. Do not fake snapshot `order_line` outcomes.

The tied-`created_at` oracle needs a deterministic seam: REST timestamps come from item `updated_at` (no immutable item creation time) and snapshot outcome `created_at` uses `clock_timestamp()`, so ordinary worker execution does not guarantee equal timestamps. Seed the actual origin rows in a focused DB fixture with controlled source timestamps before running backfill, or permit a test-only index fixture timestamp override; do not claim the tie case was exercised from uncontrolled worker timing. The broader acceptance remains valid once this explicit fixture method is supplied.
