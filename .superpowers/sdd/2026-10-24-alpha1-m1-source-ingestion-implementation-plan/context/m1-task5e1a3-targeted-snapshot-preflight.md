# M1-5E1a3 targeted snapshot aggregate recovery preflight

**Fixed source pin:** `a724c25fee95669bdeb2ceb9d88ec065cf0a4234`, read only through `git show` for the snapshot C/apply/proof seams. Read the master E brief, E1a2 quarantine preflight, and E1a1 API-022 schema contract first. No mutable source, runtime, tests, or unrelated documents were inspected. This is a provisional design note; refresh at the accepted immediate predecessor before implementation.

## Decision

A real one-aggregate API-024 retry is possible without changing API-022 semantics, but it cannot reuse API-022's run child or current C continuation as-is. Implement an independent, worker-owned targeted-recovery operation and lease, with its own terminal result linked to one immutable original outcome. Load one exact aggregate from a sealed original stage, run the existing `applyCustomer` or `applyOrderAggregate` helper under the saved original `ApplyContext`, and commit that one canonical effect plus the targeted result atomically. Do not write an original run's `etl_snapshot_apply_range`, outcome, stage, manifest, validation, attempt, checkpoint, schedule, observation, or D reservation.

This is viable as a separate additive 009 E1a3 seam and worker path; do not widen or reinterpret the API-022 recovery operation. If E1a3 is restricted to existing API-022 tables/functions/worker without this separate targeted claim and outcome path, it is not viable: the existing API-022 child represents an entire run and the C worker applies its full validated aggregate set.

## Eligible origin and terminal-run ambiguity

Only a per-aggregate C outcome with a recoverable terminal status (recommend `QUARANTINED` only) and a complete immutable original extraction/validation proof is eligible. The quarantine index ID must resolve to exactly one original outcome and exact stage key, not a run ID supplied by the caller. Require original EXTRACTED manifest, matching immutable validation seal (manifest, proof-scope and semantic digests), and the complete aggregate rows. If the proof's version domain is `SNAPSHOT_OBSERVATION`, require the exact observation value already allocated to the original run/attempt. A failed run with a completed sealed C stage can qualify; a failure before complete extraction/validation cannot and must go through API-022's FRESH_SCAN flow.

The request's phrase “from a COMPLETE or failed run” needs a precise status definition. At the pinned C boundary, `finish_etl_snapshot_run` sets run status COMPLETE only when there are zero QUARANTINED, CHANNEL_EPOCH_RETIRED, or FAILED outcomes; any such outcome makes the run FAILED. Thus an `etl_run.status='COMPLETE'` origin cannot ordinarily contain the retryable quarantine. Recommendation: define eligibility as “original stage/validation is COMPLETE/SEALED, and the selected outcome is QUARANTINED,” regardless of run's terminal application status (normally FAILED). If API-024 literally accepts a run with `status='COMPLETE'`, it should return 409 `QUARANTINE_NOT_RETRYABLE` unless a separate indexed per-aggregate quarantine exists; do not invent a quarantine or reopen a successful outcome.

Reject `CHANNEL_EPOCH_RETIRED` outcomes for retry while the original channel is retired. The canonical helper requires original channel ID/epoch to remain active. Do not silently retarget the operation to the new active epoch; that would mix versions/domains/proof. Reject `APPLIED`, `DUPLICATE`, and `IGNORED_STALE` outcomes as already terminal successes. If an outcome status FAILED is included by the public quarantine policy, allow only a typed explicitly recoverable record code and complete sealed stage; otherwise keep the API-024 target status to QUARANTINED.

## Narrow targeted operation model

Add an API-024-only immutable request/provenance row and a separate mutable claim/attempt/outcome relation; do not add API-024 to API-022's `route` check or relax its one-child-per-parent rule.

The immutable operation row should bind:

- `operation_id`, tenant/source, route `API-024`, tenant/source/route idempotency key, normalized request digest, request ID/reason, actor issuer/subject/tenant/user/auth epoch/scopes, exact current Owner ID/revision;
- quarantine UUID and exact origin run/attempt/outcome ID plus `(entity,relation,parent_source_pk,source_pk)`, original terminal status/error and expected-state CAS token;
- original run/attempt status/version domain, manifest digest, validation proof-scope and semantic digest, full-snapshot proof IDs/digests, channel ID/epoch/domain, owner approval/test, field mapping revision/digest, identity mapping revision/digest, credential ID/revision/generation and security-barrier fence;
- original aggregate digest plus exact selected page receipt IDs/digests/coverage. For an order this covers the header and all `order_line` children. For `SNAPSHOT_OBSERVATION`, bind the original observation allocation/sequence and its creation proof; never allocate a new one.
- public `mapping_revision` value as the original **field mapping** revision, leaving identity mapping revision server-bound and distinct.

Use a separate `etl_snapshot_targeted_recovery_claim` or equivalent worker queue row keyed by `operation_id`: non-NULL claim token, database-clock lease expiry, next retry time, start count, last safe error code and state. Add a separate immutable terminal operation result linked by operation ID and the original outcome ID; store outcome status/error, aggregate/proof digests and canonical apply result. The API-024 terminal result is not an `etl_snapshot_apply_outcome` in new coordinates: the original range has a FK to original stage/outcome and original proof and must remain untouched. A targeted result record should distinguish `APPLIED`, `DUPLICATE`, `IGNORED_STALE`, and safe quarantine/failure results; it must never imply full-run completion.

The API transaction creates operation+claim queue row atomically after revalidating authority and exact origin state. Same idempotency key/digest returns the same operation only after current authority/barrier recheck; changed digest or stale quarantine CAS returns 409. A unique active/accepted operation for the same origin proof state prevents duplicate manual effects. No new `etl_run`, snapshot schedule update, API-022 source:write permission, or full source scan is needed.

## Worker path and transaction boundary

Add a worker-only `runSnapshotTargetedRecoveryOnce` path (or equivalent) which claims only API-024 operation rows. It must not enter the full C worker loop or call `finish_etl_snapshot_run`.

1. **Admission:** strict body/key validation; authenticated current principal; exact same-tenant Owner/source:approve; lock security-barrier fence first; lock source credential and source serialization row; lock current principal/Owner rows; then lock quarantine origin/outcome and pending operation/idempotency rows. Recheck exact active original channel and absence of matching typed barrier before expected-state CAS/replay. Store actor and frozen proof reference. Never trust caller tenant, source, run, source key, identity revision, target object ID or stage coordinates.
2. **Claim/heartbeat:** use a new SECURITY DEFINER claim function with fixed search path and `hub_worker` only. It claims exact operation with non-null random token and DB-clock live lease, non-overlapping through source serialization. A claim is not a start. Add begin/heartbeat/fail functions; heartbeat requires exact token and unexpired lease; retryable failures use DB-clock 5/30/120 delay and max four starts. Every write checks token+lease in the same transaction. Losing/NULL/expired token aborts without canonical or result write.
3. **Targeted proof load:** a worker-only function takes operation ID + claim token and resolves original coordinates only through immutable operation row. It validates original manifest/validation seal, exact current indexed outcome and immutable stage page receipts, then returns original frozen C proof and exactly one target aggregate. For customer, return one customer row. For order, return one header plus all exact child lines under that parent, checking relation/key/line count, receipt coverage and digests. Recompute selected aggregate digest in TS using existing snapshot canonicalizer/digest functions and compare with original indexed/original proof facts before apply. Do not use caller-supplied stage coordinates or raw-source fetch.
4. **Apply transaction:** run barrier-first caller-owned PoolClient transaction. Assert target-operation claim token+lease; lock source/credential/channel in an order compatible with existing canonical helper; ensure original channel is still active exact ID/epoch/domain; check matching typed barriers and current target identity refs before version comparison. For order, use a claim-bound equivalent of `lock_etl_snapshot_order_customer_reference` proving the original customer `(source_id,source_pk)` maps to the same canonical UUID and live customer. Convert with original frozen mappings and original version domain/time; for SNAPSHOT_OBSERVATION supply the original observation sequence. Call only `applyCustomer` / `applyOrderAggregate` with original frozen `ApplyContext`. Persist targeted operation result and terminal state in the same transaction as canonical tables, source-version receipt and canonical apply outbox effects produced by the helper. A transaction rollback must roll all effects back together. Do not call `record_etl_snapshot_aggregate` against the original run.
5. **No full-run accounting:** never update original `applied_count`, `quarantined_count`, checkpoint, run status, schedule, observation, original outcome/range, or D candidate/cohort state. Targeted API completion is one operation, not a change to original run completion or snapshot coverage. D absence requires full validated scans; this targeted record must not create/reopen a D reservation. No upstream source I/O is permitted.

## Exact target identity and version/barrier policy

Public `mapping_revision` remains the field mapping revision. Require it to equal the original field-map revision for ordinary same-target retry. The service resolves the original identity-map revision/digest from the saved run proof and proves the affected targets still resolve to the same exact typed IDs before queueing. For customer data, inspect exact `user` and `department` identity refs (text IDs plus enabled auth subject/department match); these are not canonical UUIDs. For an order, prove its configured customer source tuple maps to the same live `canonical_source_identity.customer_id` UUID. For an existing target entity, prove the current `canonical_source_identity`/receipt still identifies the same canonical object UUID. If an original target is missing, ambiguous, changed or not proven, return 409 requiring the separate E1b explicit Owner remap route; API-024 must not create a new mapping, select current “latest” identity mapping, or move an existing canonical UUID.

At claim admission and immediately before version comparison/apply, the current security-barrier fence and exact source credential identity are checked, then original exact channel identity/state is checked. Matching credential compromise, source-scope removal, tenant disable, or channel-retired barrier fails closed. Retired epoch is returned/recorded before applying/comparing `source_version`; no comparison crosses `SOURCE_VERSION` and `SNAPSHOT_OBSERVATION`. Ordinary config/admission revision drift alone does not replace the original frozen proof, but any required current-target continuity failure blocks this manual same-target operation. Never clear or reinterpret barriers.

For `SOURCE_VERSION`, canonicalizer receives original row `source_version`. For `SNAPSHOT_OBSERVATION`, the operation reads the already allocated original run sequence only after proving original run/attempt validation digest linkage; no call to `persist_etl_snapshot_observation` and no allocation/child observation row. This gives a retry the same observation and lets the existing canonical receipt classify exact duplicate/stale/applied semantics. A quarantined row's retry cannot reset source-version receipts.

## Grants and exact bounded acceptance oracles

New tables default to no grants; revoke PUBLIC. Only `hub_api` receives a narrow admission function after app-side `assertCurrentPrincipal(...,'source:approve')` plus server-owned exact Owner/scope validation. Only `hub_worker` receives execute on claim/heartbeat/load/fail/commit functions. Keep raw secrets, stage facts, original full payload access, canonical tables and original outcome/range tables unavailable to `hub_api`. Worker helper functions return only selected facts internally and never log them. Existing source C full-stage functions remain unchanged.

1. API-024 request for exact original QUARANTINED outcome creates one target operation and one queue claim; duplicate same idempotency request replays it after authority recheck; mismatched request/state/Owner/tenant/source returns 409 with no second operation. API-022 remains unaffected and still does full-run retries with `source:write` only.
2. Customer targeted retry loads one exact row and order retry loads header+complete line set from immutable original stage; mutate/corrupt page digest, parent key, line coverage, target aggregate digest, proof scope or observation binding in a fixture and assert no canonical effect/result success.
3. Competing target workers cannot hold one live operation; NULL/old/expired lease, stale token, crash before apply, crash during transaction and crash after commit/reclaim create exactly one canonical effect/result. DB-clock backoff and four-start bound are target operation scoped; a lease claim without start does not spend a try.
4. Success records an operation-local result and preserves byte/logical equality of original raw/stage/manifest/validation/observation/run/attempt/checkpoint/schedule/outcome/range. Check canonical `source_version_receipt` and canonical apply outbox are committed once with operation terminal result; no original range or outcome rewrite/duplicate key conflict.
5. `CHANNEL_EPOCH_RETIRED`, matching typed security barrier, changed identity target, remap fence, stale public field mapping revision, nonrecoverable terminal status, and incomplete/unsealed source stage each return/record a safe conflict/quarantine before any version comparison or canonical write. Active exact original epoch succeeds under frozen proof even if ordinary current config revision drifted, only when typed target continuity is proved.
6. For SNAPSHOT_OBSERVATION, the original sequence and timestamp are reused exactly; assert sequence allocator/allocation and observation tables are unchanged. Assert no D candidate/reservation, no full-run finish/schedule update, no source read and no second canonical writer.

These are planning oracles only; no tests/resources were run. The first implementation brief should decide the COMPLETE-vs-SEALED eligibility wording and whether any FAILED status besides QUARANTINED is manually retryable. A new public API-024 route is already named by the product contract, but any change to its body/response requires controller resolution under the master brief.
