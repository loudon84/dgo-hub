# M1-5C additive schema/function contract

Contract recorded from BASE `9e12d44be952cebae4b6286ea92cf1b1b29497ae`, branch `feat/alpha1-implementation`, with the C brief and apply preflight as authority. Migration 009 is still phase-owned and may be extended before its first accepted ledger checksum. Migrations 001–008 and the existing immutable B rows remain unchanged in meaning.

## Existing records and frozen facts

- `control.etl_run` is keyed by `run_id`; `(tenant_key,source_id,run_id)` is unique and binds the admission proof, expected entities, source/channel epochs, config/mapping/identity revisions and digests, endpoint profile digest, approval/test IDs, original security fence, status and safe counts. Existing run-proof trigger protects those facts; only guarded status/count/timestamps/summaries may change.
- `control.etl_run_attempt` is keyed by `attempt_id`, unique on `(tenant_key,source_id,run_id,ordinal)`; B extraction ordinals remain 1–4. Keep complete B attempt and snapshot provenance immutable.
- `control.etl_snapshot_schedule` has one `(tenant_key,source_id)` row, `active_run_id`, due/last-run state and `schedule_revision`; serialize C lifecycle/finalization under `control.lock_etl_snapshot_source(text,text)` and only clear the matching active run.
- B stage tables are `control.etl_snapshot_stage_page` keyed by tenant/source/run/attempt/entity/relation/page_no; `control.etl_snapshot_stage_record` keyed by `(tenant_key,source_id,run_id,attempt_id,entity,relation,parent_source_pk,source_pk)`; and `control.etl_snapshot_manifest` unique by run/attempt. Existing FKs scope all stage rows to their run/attempt. All are immutable after insertion. Add immutable `page_no` and `row_ordinal` coordinates to each record, scoped by the same page key, and write rows plus page receipt in one `write_etl_snapshot_page` transaction. They locate rows in page order; they do not change B facts or digest input. Full order-line identity is parent order key plus line key; do not impose global line-key uniqueness.
- Add indexes for `(tenant_key,source_id,run_id,attempt_id,entity,relation,page_no,row_ordinal)` and stage full-key lookups/joins. Preserve existing PKs and immutability. C reads require an exact complete `EXTRACTED` manifest/attempt and return bounded ordered pages; they cannot read partial attempts.

## Additive C durable state

Add the following private `control` tables with tenant/source/run/attempt composite FKs and restrictive delete/update behavior. No stage facts are updated.

- `etl_snapshot_continuation`: one row per run, fields `tenant_key,source_id,run_id,attempt_id,claim_token,lease_until,c_start_count,next_retry_at,last_error_code,created_at,updated_at`; states are represented by run `VALIDATING/APPLYING` plus claim/retry fields. Claim rotates/fences token and lease but does not consume a start. A separate guarded `begin_etl_snapshot_c_start(...)` consumes one of the initial plus three automatic transient starts immediately before processing. Failure persists DB-clock relative waits of 5/30/120 seconds. An expired started lease is accounted as a failed start before another start. Keep the source `active_run_id` during waits. C starts are distinct from B attempts.
- `etl_snapshot_validation`: one immutable successful seal per exact run/attempt/manifest digest and frozen proof scope; stores entity/relation coverage counts, normalized semantic digest, validation summary hash, and creation time. A seal is written only after full streaming validation and all indexed uniqueness/reference joins pass. Invalid diagnostics may be recorded separately without a success seal. Uniqueness is per `(tenant_key,source_id,run_id,attempt_id)`; no sequence or canonical effect is permitted before this seal.
- `etl_snapshot_observation_sequence`: source-scoped counter keyed by `(tenant_key,source_id)`, storing the next sequence as exact numeric; allocate monotonically under source lock after full seal.
- `etl_snapshot_observation_allocation`: immutable source sequence allocation keyed by `(tenant_key,source_id,sequence)`, unique for one newly allocated 20-digit value, with semantic digest and full reuse scope. A new allocation advances the counter; a valid reuse references an existing allocation.
- `etl_snapshot_observation`: immutable per-run binding, unique `(tenant_key,source_id,run_id)`, FK to allocation. Multiple successful runs may bind the same allocation on valid reuse; sequence uniqueness applies to allocations, not bindings. Reuse scope is semantic digest plus exact config/field-mapping/identity-mapping revisions and digests, endpoint profile digest, channels/epochs, entity set and version domain. Exclude ephemeral credential/Owner approval IDs, credential revision/generation and admission source epoch; each run still validates its frozen credential/security proof and typed barriers independently. Only prior COMPLETE successful runs qualify; failed/partial runs are excluded. `SOURCE_VERSION` runs retain source text and do not allocate/bind an observation.
- `etl_snapshot_apply_outcome`: append-only terminal result per run/attempt/entity/full source PK and aggregate digest; statuses `APPLIED,DUPLICATE,IGNORED_STALE,QUARANTINED,CHANNEL_EPOCH_RETIRED,FAILED`; FK to exact staged aggregate. Unique exact range identity. Only successful expected outcomes can contribute to completion; only APPLIED contributes to applied count.
- `etl_snapshot_apply_range`: immutable receipt per exact aggregate/range identity `(tenant,source,run,attempt,entity,source_pk,aggregate_digest)` with proof/observation bindings and outcome ID. It is inserted in the same transaction as canonical helper writes and outcome.
- `etl_snapshot_checkpoint`: one mutable per-run/entity cursor/count summary advanced atomically with range receipt/outcome; compare-and-set from the immediately preceding deterministic full-key range. It is a recovery index only; durable receipts/outcomes are authoritative.

All private state has append-only triggers for proof/outcome/range/observation, tightly scoped FKs and indexes. `hub_api` receives only selected safe run summary columns/view access. `hub_worker` gets no direct INSERT/UPDATE/DELETE on these private tables: expose narrow `SECURITY DEFINER` operations with fixed search paths and actor-role checks. Revoke execution from PUBLIC/API/MCP/publisher/Hasura-reader.

## Worker procedures and transaction inputs

Every procedure takes explicit `p_tenant_key,p_source_id,p_run_id`; stage operations also take `p_attempt_id`; effect operations also take `p_claim_token`. It first calls the common security-barrier guard, locks the source fence, verifies exact run/attempt/status, current token/lease and original admission proof, then touches data. Procedures are worker-only.

- `claim_etl_snapshot_continuation(tenant,source,lease_seconds)` returns only run/attempt/token/current start count/status for a due `VALIDATING/APPLYING` run. It checks the active schedule and proof barriers, serializes source admission, and atomically rotates the C token/lease. Claim is not a start and does not consume the start budget.
- `begin_etl_snapshot_c_start(tenant,source,run,attempt,token)` verifies the live claim and lease, rejects an exhausted budget, and commits the next durable C start immediately before processing. Expired processing leases are accounted before the next start, with 5/30/120 failure-relative DB-clock backoff. Add heartbeat/assert-claim and fenced failure operations; stale tokens cannot begin, heartbeat, record failure or cause an effect.
- `read_etl_snapshot_page(tenant,source,run,attempt,token,entity,relation,page_no)` returns one bounded page with receipt and row ordinals only when claim/status and complete manifest match. `load_etl_snapshot_proof(tenant,source,run,attempt,token)` supports VALIDATING/APPLYING and returns frozen revision JSON (including identity mappings), digest columns, channel proof and admission fence; application recomputes canonical JSON digests for config, field mappings, identity mappings and endpoint profile and compares run plus revision values.
- `seal_etl_snapshot_validation(tenant,source,run,attempt,token,manifest_digest,proof_digest,coverage,semantic_digest)` rechecks fence/claim and persists the sole success seal after application has streamed all records, recomputed B manifest/page digests, checked expected relations, canonical payloads, complete line groups, unique source keys and same-/foreign-source identity targets. All referenced canonical UUIDs are validated by exact same-tenant source identity and Owner mapping. It transitions `VALIDATING` to `APPLYING`; no effect is possible before seal.
- `persist_etl_snapshot_observation(...)` rechecks seal/scope and allocates or binds a reusable prior COMPLETE-successful observation under the active-source lock. It is idempotent for this run and never compares sequences across domains/sources/channels.
- `record_etl_snapshot_aggregate(...)` is called in the caller-owned transaction surrounding existing `applyCustomer(client,context,input)` or `applyOrderAggregate(client,context,input)`. Inputs bind the exact aggregate digest, full source key, outcome and prior cursor. The transaction acquires the barrier guard first, verifies current claim and frozen proof, performs helper writes, inserts immutable outcome/range receipt, CAS-advances checkpoint and updates safe counts, then commits. A crash before commit leaves none; after commit leaves all. Replay skips only a matching committed receipt/outcome.
- `finish_etl_snapshot_run(tenant,source,run,attempt,token,status,summary)` verifies exact expected ranges/outcomes and seal, then commits COMPLETE only if all required outcomes succeeded; otherwise terminal failure. Under source fence it updates last-success only on COMPLETE and clears only matching schedule active_run_id. Terminal semantic/proof failures release matching run; transient errors retain active run and set DB-clock retry delay. Ordinary pause/config drift alone does not erase accepted run proof.
- `heartbeat_etl_snapshot_continuation(tenant,source,run,attempt,token,lease_seconds)`, `assert_etl_snapshot_continuation(...)`, and `fail_etl_snapshot_continuation(...,error_code,retryable)` recheck the active token under the source fence. Failure stores `next_retry_at=clock_timestamp()+5/30/120 seconds` from failure time, retains active run while retryable, and terminally releases only the matching run after four starts or permanent semantic/proof failure.

No C path performs source IO inside a Hub transaction, physical canonical deletes, absence actions, B claim reuse, or 008 item leases.

## Safe API-013 discovery projection

Add a narrow source-qualified view/query over `control.canonical_source_identity` joined to live canonical customers. Its only returned fields are `tenant_key,source_id,source_pk,canonical_customer_id`; rows are scoped to one requested tenant/source, live targets, and exact source identity. Do not grant API access to the base identity table. The existing API-013 route adds explicit `mode=source_customers`, strict `limit` default 20/max 100 and opaque source-qualified C-collation cursor. At operation time verify current principal, `source:approve`, enabled requested source and exact enabled registered Owner; token and non-Owner callers are denied. The ordinary route mode/shape stays unchanged. This endpoint only discovers pairs; API-014 remains the sole mapping confirmation/write path.
