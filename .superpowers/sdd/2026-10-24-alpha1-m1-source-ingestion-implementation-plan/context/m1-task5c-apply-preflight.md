## Existing canonical contracts at this pin

Never split an order from its lines or group multiple independent aggregates into a checkpoint range whose commit cannot be atomic with each aggregate.

`ApplyContext` carries tenant/source/credential identity, source epoch and credential revision/generation at admission, entity/channel ID+epoch, version domain, Owner approval ID/user/revision, config/mapping/identity mapping revisions+digests, endpoint profile digest, test report, and the original admission security barrier fence. `verifyFrozenApplyContext` takes the global security-barrier guard first, locks the source credential, validates the immutable active/retired channel tuple and exact config/mapping/identity/test/Owner/credential/profile proof, and rejects applicable newer typed barriers. Preserve that frozen-proof behavior: ordinary pause/config/mapping edits alone do not invalidate an accepted run; tenant disable, credential compromise, source-scope security removal, or channel retirement still blocks matching work. The C fenced proof loader must load frozen identity-mapping JSON and recompute its canonical digest, then compare it with the frozen run digest and revision digest; a digest column alone is insufficient.

`applyCustomer` and `applyOrderAggregate` run their guarded proof check in each aggregate transaction. Their results are `APPLIED`, `DUPLICATE`, `IGNORED_STALE`, `QUARANTINED`, or `CHANNEL_EPOCH_RETIRED`. `canonicalVersion` accepts canonical decimal digit strings up to 20 digits; apply compares using `BigInt`, not JS `Number`. Bind config, field-mapping, identity-mapping, endpoint-profile, channel IDs/epochs, entity set, and version domain as separate proof scope; do not let identical rows under a changed proof scope reuse an observation.

The helper's `source_version_receipt` key is `(tenant, source, channel, entity, source_pk)` and includes channel epoch/domain, numeric(20,0) version, content/projection digests, canonical UUID, deleted state, and transaction XID. `canonical_apply_outbox` is append-only by trigger. ## Critical first-load customer-to-order mapping gap

Current canonical order input has only `customer_external_id` (no customer source/system discriminator). `applyOrderAggregate` looks up the frozen `IdentityMapping(kind='customer', external_id=customer_external_id)` for the order source, requires its `target_id` to be a UUID, and requires that exact UUID to exist as a live `hub.canonical_customer`. Missing/null/invalid target quarantines. It does not auto-derive the target from a staged customer row.

`applyCustomer` allocates a random UUID on first apply when no `canonical_source_identity` row exists, then inserts the canonical customer/identity/reference, receipt and outbox. There is no existing deterministic-ID or canonical UUID reservation helper. `canonical_source_identity.canonical_object_id` defaults to a random UUID. API-014's customer candidates come from live `api.canonical_customer_identity`; `updateIdentityMapping` validates a customer target against that same live-customer view. Therefore, for a new source containing both unseen customers and orders that reference them, the exact-frozen-map precondition cannot be met before applying the customers. A full-stage validation cannot safely invent/assign the order mapping based on the customer's later random apply UUID.

**Current valid no-new-authority first-load path:** onboard the source first with an explicitly approved customer-only `allowed_entities` set (customer-only snapshots are a supported complete entity set); complete its full scan/validation/apply using already approved owner/department mappings to enabled sales identities, letting `applyCustomer` create live canonical UUIDs; have the exact current Owner discover source-key/UUID pairs through the optional API-013 source-customer mode and explicitly map each order-side customer external key to the resulting live UUID through API-014; then add the order entity/approved lines to source config and mappings, retest/reapprove/reactivate under the same connector/mode/version domain, and start the first combined customer+order run. Existing `source-registry.update` blocks only connector/mode/version-domain changes when channels exist; same-domain config changes pause and revise current config, and `activate` can add a channel for an entity without prior channel history. Validate the combined run completely before its first aggregate apply. This two-config bootstrap preserves Owner confirmation and avoids silently replacing the run's frozen identity mapping.

This is the root-approved operational two-pass onboarding contract; it is not a one-run all-entity bootstrap. API-013 source-customer discovery is read-only and returns unconfirmed source-key/live-UUID candidates from a narrow safe view; API-014 remains the explicit Owner confirmation and mapping write. Never update a run's frozen identity-mapping proof in place, auto-select UUIDs from random `applyCustomer` results, or weaken `applyOrderAggregate`'s live-target check.

**Root-resolved cross-reference contract:** B freezes entities.order.customer_source_id as the source ID, optional when customers are in the same enabled source and required in order-only mode. Same-source orders must reference a key in the complete staged customer PK set, and the exact frozen Owner mapping target must equal the live canonical source-identity tuple UUID. Explicit other-source references are allowed only when the full tuple is live in the same tenant and the exact frozen Owner mapping points to that UUID. Never infer cross-source identity. Validate the source ID, external key, tuple, mapping and live UUID before any observation or effect. Unresolved new customer UUIDs use the accepted two-pass path: customer-only apply, API-013 source-key discovery, API-014 Owner confirmation, approved combined run.
