# M1-5D1 schema contract

**Implementation base:** `3040666fa9da2de19ba7b8bf632c4765f278b455` (D1 branch pin). The product interfaces inspected at this base match the bounded C preflight pin `1546dcfb33fed12e3d474c5e96b4a0c8761a965b`; the intervening commit changes only D planning documents.

**Scope:** phase-owned unreleased migration 009 and the existing C/API-019/due/activation seams. Migration 001–008 stay byte-frozen. D1 writes reconciliation facts and immutable candidate membership only; D2 owns candidate approvals and D3 owns canonical logical deletes.

## Durable rows and scoped keys

### `control.etl_snapshot_delete_run`

One reservation and reconciliation summary per C run, keyed by `(tenant_key, source_id, run_id)` and bound to the exact C attempt by restrictive composite FKs to `etl_run` and `etl_run_attempt`. It records `status` (`PENDING`, `AWAITING_OWNER`, `APPLYING`, `STALE`, `COMPLETE`, `SKIPPED`, `FAILED`), `attempt_id`, scope digest and stable scope JSON, run observation as `numeric(20,0)`, C `completed_at`, candidate revision/digest, exact denominator/member counts, pause reason, and immutable timestamps. A partial source/status index covers only unresolved busy statuses `PENDING`, `AWAITING_OWNER`, `APPLYING`. Immutable C binding, proof, time, scope and digest fields are guarded; only the private D worker procedure may move status and update reservation-owned mutable state.

The source busy marker is derived from these rows; there is no second queue or independently mutable busy bit. A unique `(tenant_key,source_id,run_id,attempt_id)` key supports the child FKs. The current run's attempt FK is restrictive and composite so an attempt cannot cross tenant/source/run.

### `control.etl_snapshot_delete_consumption`

Reservation order is a DB-generated immutable bigint identity allocated inside the existing guard/source lock during C finish. Workers consume by this ordinal (not timestamp or UUID); it is ordering metadata only and is excluded from the stable scope/digest. Once-only worker receipt keyed by `(tenant_key,source_id,run_id)`, with the same exact attempt FK, successful `COMPLETE` status binding, and consumed timestamp from DB time. Rows are immutable. C finish creates `etl_snapshot_delete_run` reservation atomically; only the D worker consumes it. The receipt is inserted in the same transaction that updates presence and streak facts, so retry/restart cannot double count.

### `control.etl_snapshot_delete_presence`

Immutable observed-live full-key membership for a consumed C run, keyed by `(tenant_key,source_id,run_id,entity,source_pk)` with `source_pk COLLATE "C"`, entity constrained to the frozen enabled entity set, restrictive FK to the exact D run/attempt, and FK to the exact C stage header and source-key stage row. The presence set includes every observed top-level customer/order source key, including an explicit source tombstone; presence resets absence even when that source row is deleted. Only validated C stage rows with `relation=entity` and empty parent key are source headers; order-line rows are not standalone delete identities. Presence rows do not require canonical identity because C may legitimately observe an explicit tombstone without a live canonical object. Index by `(tenant_key,source_id,run_id,entity,source_pk COLLATE "C")` supports ordered joins. Populate with bounded SQL `INSERT … SELECT` from immutable stage records; do not accumulate a Node-wide candidate list.

### `control.etl_snapshot_delete_streak`

Mutable latest streak state keyed by `(tenant_key,source_id,entity,source_pk,scope_digest)`, using the complete source key and C collation. It stores the stable scope JSON/digest, last processed C run, last presence run, first/second absence run IDs, `smallint absence_count` constrained to `0..2`, exact second-run `numeric(20,0)` observation, and second-run `completed_at`. Composite restrictive FKs bind run IDs to the same tenant/source. A source/entity/scope and C-key index supports current-scope joins. Presence resets the matching key's absence count; missing on the next distinct successful complete run increments to 2. A replay is stopped by the consumption PK. Failed, stale, partial, invalid, or interrupted C runs create neither presence nor reset facts. Stable scope hashes only tenant/source/entity, config revision/digest, field and identity mapping revisions/digests, endpoint/profile digest, active channel IDs/epochs/version domains, frozen enabled entity set, delete contract, and Owner/revision/approval binding. It excludes run/attempt/operation IDs, transport/page/cursor/snapshot provenance, OBS/time, claim/lease values, and ordinary admission/security fence counters.

### `control.etl_snapshot_delete_candidate` and `control.etl_snapshot_delete_candidate_member`

Each immutable candidate header is per entity and has a generated `candidate_id uuid PRIMARY KEY`, unique `(tenant_key,source_id,run_id,entity,candidate_revision)`; it stores that entity's exact scope digest, frozen stable-scope proof, distinct live canonical-object baseline count, distinct candidate-object count, digest, and freeze time. Duplicate live full keys mapping to one canonical object fail closed as `STALE` before candidate freeze. Exact member rows reference the candidate UUID and are keyed by `(candidate_id,entity,source_pk COLLATE "C")`; each member independently binds its first/second absence runs, exact second-run OBS and DB `completed_at`, actual full source key and live canonical object UUID. The matching scoped streak retains the most recent presence run and sequence. Restrictive composite FKs prevent cross-source/entity members. Header and members are insert-once, with immutable triggers and indexes on source/run/entity/revision and candidate/key. Candidate ordering is `(source_pk COLLATE "C")` within each entity; freeze uses indexed Hub joins and DB insert-select, with bounded ordered reads only for digest streaming.

`candidate_count * 100 > baseline_count * 5` uses PostgreSQL exact integer arithmetic. A zero/zero set is terminal `COMPLETE`. If any entity set is above 5%, every candidate set for that source cohort remains blocked and the source is durably paused with its schedule disabled before any D1 completion/summary is visible. No D1 path writes canonical tombstones, receipts, outbox, or approvals.

## Procedures, guards, grants, and lock order

- `control.etl_snapshot_source_delete_busy(text,text)` checks for a D summary in the three busy statuses. `hub_api` and `hub_worker` may execute this narrow function; the worker has `SELECT` on D reservation rows only, and neither API nor worker has direct D base-table DML. Manual API-019 invokes it after current-principal validation and the existing idempotency replay lookup, before any new admission. Due admission invokes it while holding the existing guard and source lock, before claiming the due schedule. Activation calls the equivalent conditional check while the source row is locked; before migration 009 exists, the existing optional-table pattern leaves first activation behavior intact. Existing idempotent API-019 replay returns the original accepted run after current-principal validation even while D is busy; a different/new key is rejected with the existing 409 `SOURCE_CONFLICT`.
- `control.reserve_etl_snapshot_delete_run(text,text,uuid,uuid)` is a narrow internal function called by successful `finish_etl_snapshot_run` in the same transaction and before `etl_snapshot_schedule.active_run_id` is cleared. It inserts exactly one `PENDING` reservation for supported absence-enabled `SNAPSHOT_OBSERVATION`; unsupported contracts get a safe `SKIPPED` summary. Reservation uniqueness plus the source lock and row-level transaction closes manual/due/activation admission races.
- `control.consume_etl_snapshot_delete_run(text,text)` is executable only by `hub_worker`. It loads and independently validates exact C COMPLETE run/attempt, manifest, validation, frozen config/mappings/identity/Owner/approval, run-bound observation, current stable proof binding, and matching typed security barriers; it does not use or synthesize a C continuation claim. Matching typed barriers or current Owner/config/profile/map/channel/delete-contract drift finish as safe `STALE` without touching streaks. Unrelated typed barriers do not invalidate this run. It processes eligible COMPLETE reservations by DB reservation ordinal, commits immutable consumption, source-header presence, and streak updates together, and only freezes the latest fully accounted current cohort after no C run is active. C's frozen proof and existing typed fences remain authoritative.
- `control.freeze_etl_snapshot_delete_candidates(text,text)` is a private worker-only helper called inside consumption. It creates the full exact candidate sets and denominators before any potential future effect, binds the second run's existing OBS and DB completion time as explicitly inferred absence time, and computes a deterministic streaming digest over full UTF-8/C-ordered keys and proof. No sequence allocation, worker timestamp, `Date` millisecond conversion, fabricated `SOURCE_VERSION`, or unbounded Node candidate arrays.
- The worker-only candidate-freeze path pauses under the source lock: it updates lifecycle to `PAUSED`, disables the existing schedule and advances its schedule revision, advances ordinary `source_epoch`, and inserts a row in the private `etl_snapshot_delete_policy_audit` event table with `actor_kind='SYSTEM_POLICY'`, actual database worker-role identity, reason code, run/candidate digest, and frozen Owner approval as authority provenance. It never writes an Owner user as the acting principal or calls the existing user lifecycle API. The existing lifecycle row requires non-NULL `actor_user_id` (`source_lifecycle_event_actor_user_id_not_null`); that user event is not used for automatic D policy. Do not weaken this constraint.
- D terminal finalizers release busy status for `STALE`, `COMPLETE`, `SKIPPED`, or `FAILED`, but never re-enable scheduling or set source lifecycle to `ACTIVE`. Ordinary `source_epoch` advance caused by D's own pause is not candidate staleness; the stable scope excludes it. Current typed fences are checked independently against original C proof.

C finish keeps its existing security-fence then source serialization locks; its reservation insert occurs in that same transaction before the schedule active slot clears. D worker procedures acquire `control.lock_security_barrier_fence()` first, then `control.lock_etl_snapshot_source(tenant,source)`, then lock the eligible reservation/streak facts they mutate. Manual admission, due admission, and activation preserve their existing guard/source row order and consult the D busy function while the source is serialized. Source connector credentials remain read-only and D1 introduces no connector call.

## Current bounded-source constraints

`finish_etl_snapshot_run` presently validates C proof/outcomes and then clears the schedule active slot in its successful branch; the reservation call belongs between setting C COMPLETE and clearing that slot, in the same Hub transaction. API-019 currently returns an identical-body cached idempotent run before proof/active-source checks; busy enforcement must preserve that order. Due admission locks the global fence, source credential, source row, channel rows, and schedule. Activation obtains the source-row lock and advances ordinary source epoch only after source/approval/channel validation.

Canonical identity is keyed on `(tenant_key,source_id,entity,source_pk)` with `"C"` collation. `source_version_receipt.source_version` is `numeric(20,0)` and captures channel/entity/key/version-domain/deleted status; canonical customer/order rows expose `deleted_at`. D1 only records proof and candidates; D3 uses `CanonicalDelete` input `{source_pk,source_version=bound OBS,deleted_at=frozen second-run completed_at}` and hashes key/time, preserving exact 20 digit text throughout SQL/BigInt comparisons.
