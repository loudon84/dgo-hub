## Critical currentness and baseline issue

The D2 `candidate_current` predicate cannot be reused unchanged after the first successful tombstone: its live-only baseline fingerprint/count will shrink, and its live-member count will fall below the frozen candidate count. D3 must reconstruct the original baseline as the union of (a) current live exact full-qualified identities and (b) identities for this exact candidate whose D success receipt committed atomically with its tombstone. Recompute and compare the original full-membership fingerprint and original `baseline_count`; separately enforce expected current live count `baseline_count - own committed tombstones`. This detects equal-count substitutions and other-object changes without treating D's own prior success as drift. A row marked success without a matching candidate/member, receipt and canonical deleted state must not enter the union.

The candidate currentness recheck also needs an own-effect-aware member predicate: each member is either still live with its exact canonical UUID and its frozen OBS newer than its last pre-D presence receipt, or is already deleted by this candidate with its matching durable D outcome. Any unrelated receipt/version, remapped identity, missing object, proof/Owner/barrier drift, invalid approval or newer reservation/cohort makes remaining actions STALE. D3 must validate all required above-threshold approvals before the first effect, and revalidate approver authority/epoch before every effect as directed by the brief.

`candidate_current` rejects a candidate whenever **any** newer reservation exists, but does not itself check older unconsumed reservations. D3 claim should require the chronological C-completion backlog to be consumed/processed and the candidate to be the latest current cohort; otherwise a pending older or newer C cohort can reorder presence evidence. Never let a previously COMPLETE older candidate act over later presence facts.

## Transaction, claim and worker coexistence design

Before every effect, the caller transaction must acquire `control.lock_security_barrier_fence()` first and `control.lock_etl_snapshot_source(tenant,source)` next, then revalidate current claim token/lease, exact candidate/member, latest cohort, proof/barrier, current source Owner and (when required) each approval's actual saved principal/epoch/scope. Revalidate own-effect-aware baseline and membership, then call the existing canonical helper with that same client. Record a unique D item outcome/effect receipt in that same transaction after the helper succeeds; a crash before commit leaves no canonical/outbox/D success, and a crash after commit leaves all together. No network/source I/O belongs inside the transaction.

The existing `runSnapshotDeleteWorkerOnce` scans source groups in `PENDING/AWAITING_OWNER`, ordered by minimum `last_worker_checked_at` (NULL first), reservation ordinal and source. Its `consume_etl_snapshot_delete_run(text,text)` also takes the global barrier and exact-source serialization fence, selects the oldest unconsumed `PENDING`, defers while C is active, and then freezes/processes the cohort. To coexist safely, D claim must take the same serialization fence and atomically transition the chosen candidate/run to `APPLYING` with D token/lease; the C consumer then cannot race it, and the D1 scanner excludes `APPLYING`. Keep D's retry scheduling fields distinct from D1 `last_worker_checked_at`: D1 may continue refreshing that hint for pending approvals, while a claimed `APPLYING` run is absent from its scan. Require no active C run and no older unconsumed completion before claim. A lost/expired token cannot commit or finalize; recovery reclaims the same immutable candidate and consults committed D effects.

## Risks to carry into implementation/review

- D2's currentness helper is useful as the first-action baseline but becomes false after D's own first effect; replace/extend with a transactionally locked own-effect-aware predicate, not a bypass flag.
- API approval capture has auth epoch, but worker cannot execute `lock_api_identity`; a D3 helper must verify current binding, enabled tenant/subject and `source:approve` scope and epoch without broad grants.
- The existing D worker freshness clock is for C reservation consumption. Keep D claim freshness separate so worker ordering is fair and D1 cannot update/overwrite lease state.
- The latest-cohort rule must account for reservations arriving after approval and process backlog in completion order. Newer presence or reservation invalidates older candidate authority before any further action.
- Existing canonical helpers may return DUPLICATE/IGNORED_STALE/quarantine. Only the matching previously committed D effect is a resumable success; do not convert an unrelated helper replay or stale result into a D success receipt.

### Shared digest serialization now available to D3

Migration 009 factors D1 freeze, D2 currentness recomputation and baseline calculation through the same private immutable SQL serializer functions:

- `etl_snapshot_delete_baseline_digest_seed(jsonb,text,bigint) -> bytea` initializes the live-baseline fingerprint with `{proof, entity, baseline, kind="live-baseline-v1"}`.
- `etl_snapshot_delete_baseline_member_digest(bytea,text,text,text,text,uuid) -> bytea` folds one `(tenant_key,source_id,entity,source_pk,canonical_object_id)` tuple into that fingerprint. Feed members in `source_pk COLLATE "C"` order.
- `etl_snapshot_delete_candidate_digest_seed(jsonb,text,uuid,integer,bigint,bigint,bytea) -> bytea` initializes the candidate digest with proof, entity, run, revision, baseline/count and the baseline membership digest.
- `etl_snapshot_delete_candidate_member_digest(bytea,text,uuid,uuid,uuid,numeric,timestamptz) -> bytea` folds candidate key, canonical UUID, origin/second run, OBS sequence and inferred completion time.

All four are immutable SQL helpers with fixed `pg_catalog` search path and execution revoked from PUBLIC, `hub_api`, `hub_worker`, MCP, publisher and Hasura reader. `etl_snapshot_delete_baseline_fingerprint(text,text,text,jsonb)` now reuses the first two; `etl_snapshot_delete_candidate_recomputed_digest(uuid)` and D1 freeze reuse the latter two. D3's own-effect-aware baseline reconstruction should call the **same baseline seed and member serializers** from a narrow security-definer worker procedure: union current-live members with only exact candidate members having a committed matching D effect, deduplicate by full identity tuple, sort by C collation, then fold. This preserves the frozen `baseline_membership_digest` byte-for-byte and catches equal-count substitutions. Do not invent a second Node/SQL serializer.

Candidate digest timestamps now serialize explicitly as UTC RFC3339-like text with six fractional digits (`YYYY-MM-DDTHH:MM:SS.USZ`) inside the digest member JSON, rather than relying on PostgreSQL JSON rendering of `timestamptz`. This is a UTC instant representation, preserving microseconds. D3's operation input must still pass exact second-run `completed_at` losslessly to the canonical Zod parser as an offset-bearing RFC3339 timestamp; candidate member `inferred_completed_at` is frozen in `timestamptz`, and the shared candidate serializer normalizes it to the same UTC microsecond string. SQL `to_char(... AT TIME ZONE 'UTC', 'YYYY-MM-DD"T"HH24:MI:SS.US"Z"')` is the serialization seam to match. Keep exact effect operation timestamp text stable across retries; JS `Date` truncation remains unsafe.

The helper functions are private at the application-role boundary, but remain available to a suitably owned D3 security-definer routine; verify its owner and fixed search path in implementation. No extra API grant is warranted for these serializer helpers.
