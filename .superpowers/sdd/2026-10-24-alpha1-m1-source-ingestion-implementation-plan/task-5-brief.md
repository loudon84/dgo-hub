Use the existing M1 registry, AuthService, canonical apply functions, and M1-4 durable worker boundary. Preserve source-system read-only access and stable canonical UUIDs. SQL Server remains M1-6. Do not enable legacy pulls or query gates. Formal 48-row acceptance and real CRM/SQL Server/Hermes/site IdP checks remain NOT_RUN.

M1-5 is one scoped task but has sequential review gates because later writes depend on durable interfaces:

1. **009 schema, run admission, and read APIs:** freeze run/proof/stage/checkpoint/range/quarantine contracts; implement additive migration and authenticated API-019–021 plus durable scheduling. Review before extraction work.
2. **PostgreSQL snapshot attempt and staging:** create the approved-connector read-only REPEATABLE READ transaction; extract customers, orders, and all lines from the same database snapshot; write bounded pages to destination staging. If the source transaction or connection is lost before complete extraction, abandon that attempt for reconciliation and start a fresh source snapshot. Keep partial stage for diagnosis only; never infer absence from it.
3. **Completeness validation, apply, observation, and recovery:** validate the entire required entity set and its cross-references before assigning any snapshot observation or applying any aggregate. Persist complete-run proof and stable observation allocation; apply only verified aggregates via existing `applyCustomer` / `applyOrderAggregate` caller-transaction APIs. Atomically commit canonical effects, receipts, apply outbox, stage outcome, and processed range receipt/checkpoint. Recovery after complete staging may resume destination apply from durable stage; it must not pretend a lost upstream MVCC snapshot can resume.
4. **Deletion candidates and API-060:** update consecutive-complete-snapshot facts only after a successful complete reconciliation; retain tombstones/receipts; enforce exact candidate digest, 5% denominator, current Owner revision/identity, and audit before physical hard-delete application. API-060 approvals bind to exact source/run/candidate revision/digest and become invalid on Owner revision change.
5. **Manual recovery and channel switch:** add API-022–024 with idempotency and stable source facts. For a channel switch, stop old-channel admission, drain or isolate old work, reconcile and validate the new lane, obtain current Owner approval against exact pending channel/config/reconciliation digest, and commit channel retirement/config/epoch change atomically. Failure before commit leaves old channel/epoch current. Never compare `SOURCE_VERSION` with `SNAPSHOT_OBSERVATION`.

Each slice is one writer at a time; independent Spec/Quality review closes before dependent slice proceeds. Freeze migration-009 ownership and contracts before code. ## Frozen behavior contract

- Default is one serialized `FULL_SNAPSHOT` per tenant/source every 300 seconds. At most one run may scan or reconcile a source. Scan and apply ordering is serialized; use explicit source/tenant/job predicates, not assumed RLS.
- Snapshot extraction reads customer rows, order headers, and all order lines under one PostgreSQL `REPEATABLE READ, READ ONLY` transaction and one MVCC view. Use sequential page reads from a single cursor/connection or equivalent snapshot-preserving keyset reads. SQL values are bound parameters; table/schema/column identifiers come only from frozen validated mappings and are individually quoted. Exact numeric/version fields must be cast to text at the source before driver decoding; preserve decimal strings and 20-digit versions without JS `Number`.
- Freeze at run admission: tenant/source/entity set; source credential ID/revision/generation and source epoch at admission; channel ID/epoch/connector/mode/version domain; config, field mapping, identity mapping revisions and digests; endpoint-profile digest; test report; Owner binding/revision where a gated action uses it; security barrier fence. Store sufficient immutable proof so later worker/recovery actions do not resolve under current mappings. Ordinary pause/config edit alone does not cancel an accepted run; current typed barriers and retired channel are checked before each apply. Owner-gated API-060/cutover always revalidates the currently enabled same-tenant Owner and revision at execution.
- Staging records must retain exact source IDs, entity, complete mapped business facts, source version as canonical string when present, source update instant at full precision, line membership, deterministic digest, and run/attempt/page provenance. Stage data is private to worker/admin; API-021 and API-023 expose summaries only, never raw credentials or full source payload by default.
- Full validation is an all-or-nothing gate before any absence-based reconciliation or `SNAPSHOT_OBSERVATION` allocation: required entities complete (customer/order/lines per configured contract), unique source PKs and line keys, supported mappings, exact decimal ranges/scales, complete order/customer references, valid source identity, configured delete/version contract, complete page manifest and stable snapshot identity. Duplicate keys, missing required entity, interrupted pages, mapping/amount/reference errors, stale channel, or source disconnect mark the attempt incomplete/quarantined and create no observation allocation, checkpoint advancement, delete-candidate increment, or absence action.
- For sources without a safe aggregate source version, assign one server-side monotonic `SNAPSHOT_OBSERVATION` only after complete validation and persist it once on the run. Reuse that observation on apply recovery/replay. Unchanged canonical content advances the receipt as appropriate but emits no second canonical apply outbox event.
- Process verified entities through M1-2 apply contracts. One customer or complete order-plus-lines aggregate per caller-owned destination transaction; use full source tuple and frozen mappings; canonical UUIDs stay stable. Keep tombstone/delete receipt and source version domain. Never mutate accepted source facts to make a retry pass.
- `FI-04`: a source disconnect before staging completes yields no absence deletion and no completed cursor/checkpoint. Partial stage can be inspected or explicitly discarded later, but is not a valid snapshot and cannot resume from a different source transaction. A restart may resume apply only after a complete validated staging manifest exists.
- `FI-05`: after an applied range/item commits but before its checkpoint response/next range commit, restart replays the same durable range/operation identity; canonical receipt/outbox make it idempotent, and checkpoint/range receipt are committed atomically so no range is falsely marked complete. Final rows and amounts match an independently authored oracle.
- Tombstone deletion is applied according to frozen delete contract. For hard-delete-only sources, a candidate must be absent from two consecutive *successful complete* snapshots. Failed, stale, partial, invalid or interrupted runs neither increment nor reset the streak. One-run candidates remain candidates only. If candidates exceed 5% of active objects, pause the source and require explicit API-060 approval before any candidate in the bound set can apply. Do not physically delete canonical core rows; apply the approved logical delete/tombstone and preserve identity/version receipt/history.
- API-022 retry creates a new run attempt with the original frozen run proof and reliable durable stage/range state; it cannot rewrite source facts. API-024 manual quarantine retry requires `expected_state`, explicit current mapping revision and reason, an authorized current Owner, and an unambiguous explicit remap confirmation where mapping changed. It creates a new stable retry operation ID while preserving the original quarantined event/run, facts, and frozen proof. Ambiguous or stale identity/reference mapping remains quarantined; do not silently select a new target.
- Follow 5/30/120-second delays, at most three automatic retries after first start (four starts total). Persist attempt starts, due times, stable operation IDs, lease/fencing and terminal status across crashes. Reuse M1-4 worker leasing/claim semantics; do not add a competing queue.

## Root contract rulings (2026-10-24)

These rulings replace the earlier open choices in this brief and bind every later M1-5 slice:

- **Lost source snapshot:** a lost source transaction/connection ends that extraction attempt. Keep its partial rows for diagnostics only, mark it incomplete, and begin a fresh full scan attempt. Partial stage can never be applied or used for absence. A fully validated complete stage manifest may resume destination apply after restart.
- **Entity contract:** the exact required entity set is frozen from the approved config's `allowed_entities`. Customer-only snapshots are valid. Any config allowing orders must include an explicit approved line relation, source line key, order foreign key, and complete header/line field mappings. No guessed tables, joins, keys, or mappings. `SOURCE_VERSION` is allowed only with a safe aggregate version and matching delete-version contract. Hard-delete absence without a safe source version requires `SNAPSHOT_OBSERVATION`; otherwise fail closed.
- **Durable completion boundary:** stage pages and their immutable page receipts may commit incrementally for diagnosis, but the full expected-entity/page manifest and completeness validation must commit before observation allocation, complete checkpoint, or business apply. An individual apply commits its canonical aggregate, source receipt, canonical apply outbox, durable outcome, range receipt, and checkpoint atomically.
- **Absence streak:** only a successful, complete reconciliation advances a candidate's consecutive absence count. Failed, stale, partial, interrupted, or invalid runs neither advance nor reset it. A complete snapshot where that identity is present resets its absence streak.
- **Delete denominator and effect:** candidate sets are scoped by tenant/source/entity and use full source identity tuples. Freeze the exact count of live active canonical objects in that same scope under the serialization guard. Compare with exact integer arithmetic: `candidate_count * 100 > active_count * 5`. Above 5%, pause before any candidate action and require API-060 approval for the exact set. Physical `DELETE` against canonical core is forbidden; approved candidates apply logical tombstones while preserving canonical identity and version receipts. At or below 5%, auto-reconcile only when the explicit approved hard-delete contract allows it.
- **API-060:** add `POST /hub/v1/admin/sources/{id}/delete-candidates/{candidate_id}/approve`. Require the current enabled same-tenant exact bound Owner and existing `source:approve`; request carries `run_id`, `candidate_revision`, `candidate_digest`, `expected_owner_revision`, and reason. Server recomputes sorted candidate full keys and digest, verifies source/run/revision/denominator and Owner binding, and persists approval/audit/idempotency, returns 200 with `approval_id` and status, then permits worker logical apply. Stale/changed candidate set returns 409. API-007 config approval is separate. Add no new permission scope.
- **Admin APIs and idempotency:** API-019 and API-022 require `source:write`; API-020/021 and API-023 require `source:read` with source-level authorization; API-023 is limited to the exact current same-tenant Owner. API-024 requires exact current Owner plus `source:approve`. These are user-authenticated admin calls; a source credential/token cannot call them. API-019/022/024/060 require `Idempotency-Key`, scoped to tenant/source/route. API list endpoints use safe envelopes and pagination default 20, maximum 100; strict input rejects missing/unknown fields.
- **Manual retry:** API-024 appends a new retry operation and preserves original event/run/raw facts and frozen proof. If the original mapping/dependency remains valid, retry keeps that proof. A changed mapping requires explicit current Owner reconfirmation and approved current mapping proof bound to original source record, canonical UUID, and target. Never rewrite/reset a terminal original row or bypass an old security barrier. Ambiguous target remains quarantined and returns 409.
- **Channel switch:** stage pending config/channel separately; stop old admission and drain or isolate old work; validate full initial reconciliation; require exact current Owner approval for pending channel/config/reconciliation digest; only then, in one caller-owned control transaction, retire the old lane and activate config/new epoch. Precommit failure leaves old lane current. Resolve the approval/bootstrap sequence and existing approval uniqueness in the Phase E design review. No staging apply may occur before cutover under the pending lane.
- **009 ownership:** root owns migration `009_snapshot_runs_and_recovery.sql` through the full M1-5 review. Intermediate slice reviews do not freeze or approve it. Slice A may establish the minimum run/schedule foundation; later slices may extend 009 only with a focused diff upgrade and review, or use a later additive migration only if the implementation design proves it necessary. Do not create speculative future tables. Migrations 001–008 remain immutable.
- **Verification and claims:** five slices run sequentially with one source writer at a time and independent Sol review between dependent slices. Use red/green tests, exact per-slice source/evidence manifests, and owned local PostgreSQL fixtures only after root freezes the exact implementation base. No existing/real database or production deployment. Formal 48 acceptance rows remain NOT_RUN.
