## Scope after gates

Implement the existing `etl-worker/worker.ts` and `etl-worker/retry.ts` seams as the durable consumer for the strict REST job/outbox from migrations 007 and the canonical apply functions from migration 006. Add a single later additive migration only for confirmed worker schema/permission gaps. Keep 001–006 immutable; treat 007 as immutable after the Task 3 review closes. Do not create a new worker service, queue, migration runner, auth registry, mapping authority, API route, or top-level module.

The worker takes the existing one-row-per-job processing outbox through a job-level lease and handles each item independently. Each eligible item is adapted from immutable public event facts into the M1-2 canonical customer/delete or order/delete input. Apply the item and write its durable item result, error code, job summary, and `applied_count` in the same caller-owned PostgreSQL transaction. A transaction failure leaves no partial canonical aggregate, receipt, canonical-apply outbox row, or terminal item status. A durable attempt-start record is committed before application, so a crashed started attempt continues to consume its retry budget after lease recovery. Claiming work and skipping an already-terminal item do not consume attempts. Queue acknowledgment is token-fenced and allowed only after the item/status transaction has committed and all job items are terminal.

Do not dispatch the old local legacy pull worker for M1 traffic. ## Frozen proof, barriers, and drift

Build `ApplyContext` solely from the job’s frozen proof columns: tenant/source, credential identity, admission source epoch, credential revision/generation, entity, channel ID/epoch/domain, Owner approval/user/revision, config/mapping/identity-mapping revisions and digests, endpoint profile digest, test report ID, and `security_barrier_fence_at_admission`. Do not rebuild context from current config and do not accept proof from a payload.

Inside every item apply transaction, the global `control.lock_security_barrier_fence()` guard is the first database lock, before lease/outbox, item, credential, channel, or canonical identity locks. Verify the claim token and lease expiry under the outbox row lock and hold that lock through the item mutation. The separate bounded claim transaction uses `FOR UPDATE SKIP LOCKED`, performs no auth/source mutation, and commits before an apply transaction starts; do not carry the claim lock into the apply transaction or invert guard/claim lock order. `apply*` is the authoritative validator of exact frozen approval/test/config/mapping proof and current typed security facts. Isolate a matching credential compromise, source-scope security removal, tenant disable, or channel retirement newer than the job’s admission fence. An expired lease, worker restart, ordinary source epoch/config revision/mapping revision/owner revision drift, or ordinary pause by itself does not cancel frozen work. Do not compare job admission epoch to current epoch as worker lifetime authorization. Do not pass frozen work through a matching security barrier.

The M1-2 explicit identity-remap correction has its own affected-identity fence and outcome `AUTHORITY_MAPPING_SUPERSEDED`; preserve that narrow correction behavior. It is not general permission to reinterpret a job under a newer mapping. A source mapping/config change without a matching security barrier or affected identity-remap fence leaves the job on its frozen revision. A post-barrier Owner-approved recovery permits new admissions only; it never changes old job proof or erases barriers.

## State, retry, idempotency, and recovery

- Treat durable item status as the primary fact. Existing 007 item states are `RECEIVED`, `VALIDATING`, `APPLYING`, `APPLIED`, `DUPLICATE`, `IGNORED_STALE`, `QUARANTINED`, and `RETRY_PENDING`; job states are `RECEIVED`, `PROCESSING`, `SUCCEEDED`, `PARTIAL`, and `FAILED`. API-017/018 expose only safe state and counts; never return raw bytes, `public_record`, credentials, secret refs, or SQL.
- Derive terminal job state from persisted item terminal states. All `APPLIED` / `DUPLICATE` / `IGNORED_STALE` yields `SUCCEEDED`; mixed terminal successes and failures yields `PARTIAL`; all terminal quarantines yields `FAILED`. Pending items and scheduled automatic retries keep the job `PROCESSING`. `applied_count` counts only items with actual `APPLIED` canonical effect, including a committed DELETE effect; `DUPLICATE` and `IGNORED_STALE` count as successful terminal outcomes for job status but do not increment `applied_count`.
- Follow PRD §9.4: one initial application attempt plus up to three automatic retries, for at most four application starts total. Persist attempts separately from retries. Use delays of 5, 30, and 120 seconds after the initial failure and subsequent retry failures. Claiming a job and skipping a terminal item do not consume an attempt. Commit a stable operation ID for each `(job_id, ordinal)` before starting application. A started attempt remains counted and its next due time/budget survives a crash, lease expiry, and restart; never reset the attempt budget when a claim token changes. After the retry budget is exhausted, persist `QUARANTINED` with a safe stable code.
- A crash after canonical commit but before queue acknowledgment must find the item already terminal and skip reapplying it; if the core item transaction rolled back, retry the same operation identity and frozen input. M1-2 receipt/version logic remains the idempotency backstop. Persist terminal item status in the same caller transaction as canonical aggregate, receipt, and canonical apply outbox.
- Manual quarantine retry/API-023/024 is deferred to M1-5. M1-4 adds no retry route and never applies an old job under the latest mapping. FI-03 must prove isolation of the affected old identity after the explicit remap fence and continued completion of unrelated frozen work; it must not claim successful manual retry. Security-blocked old items remain isolated after later ordinary edits or recovery.
- Use one job-level lease on the existing job outbox. Claim bounded rows with `FOR UPDATE SKIP LOCKED` in a short separate claim transaction. Each apply transaction checks the claim token/lease expiry under the outbox row lock, retains that lock through one item's atomic mutation, and serializes the item row. On expiry, a reclaimer issues a new token; stale holders cannot write status or ACK. Acknowledge with the current token only after commit and after all job items are terminal; otherwise release/reschedule the job to its next due item. A crash after commit but before ACK safely replays terminal rows without a duplicate mutation.

## Schema gap and migration-number decision

Migration 007 currently has a one-row-per-job `control.ingestion_processing_outbox(id,job_id,created_at)` with no claim status, lease, availability/ack field, or worker UPDATE/DELETE grant. Items have no attempt counter, retry due time, stable operation identity, or lease claim fields. Worker currently receives only SELECT on the outbox, UPDATE on item `(status,error_code,updated_at)`, and UPDATE on job `(status,applied_count)`. That does not express recoverable leasing, deterministic delayed retries, durable attempt limits, or post-commit acknowledgment.

Root ruling fixes migration `008_durable_worker_leases_and_retries.sql` as the minimal additive migration. Extend the existing outbox/items; do not duplicate queue tables. Add bounded job-level lease/claim token/expiry and availability/ACK facts; add a stable per-item operation ID, durable started-attempt/retry count, and next-retry due facts; and extend only hub_worker column grants required for those mutations. Preserve raw/proof immutability, tenant/source/job FK scope, PUBLIC revokes, and all existing role boundaries. Migrations 001–007 remain immutable. Root will change the public M1-5 snapshot migration from 008 to 009; this brief does not edit the public plan.

## Required observable acceptance assertions (future implementation)

Use controlled synthetic data and an independently authored local oracle. The following are implementation acceptance targets, not evidence already run:

- Two concurrent workers cannot own the same unexpired claim or apply the same active item concurrently; bounded `SKIP LOCKED` claims return distinct jobs. An expired claim gets a fresh fencing token; an old token cannot mutate or ACK.
- Expired lease is reclaimable after process termination. A worker killed after claim but before apply retries the item; a worker killed after the canonical item transaction commits but before ACK replays without a second canonical mutation or business outbox event.
- Inject failure after canonical header write, after a selected line write, before item/job status write, and immediately before commit. Each rollback leaves the canonical aggregate/receipt/outbox at T0 and leaves no terminal item result. A successful item transaction commits aggregate, receipt, canonical apply outbox, durable item status and summary atomically.
- FI-03: mapping/identity-reference failure quarantines only the affected item and preserves a safe dependency code; an explicit remap fence isolates affected old work while an unrelated frozen job still completes. This fixture proves isolation and unrelated completion, not successful manual retry.
- FI-05: crash/restart and replay preserve frozen source/mapping/channel/security proof, terminal item identity and aggregate result. The trusted shared worker backend may process jobs from every tenant; do not model a fictitious Tenant A database role or assume implicit RLS. Verify tenant-qualified job/proof queries prevent cross-tenant context, cross-source references, and tenant-mismatched core targets, using the actual worker DB role and least-privilege negative checks.
- Ordinary pause, current source epoch drift, ordinary config/mapping revision changes and ordinary Owner binding changes do not blanket-quarantine valid frozen jobs. Explicit credential compromise, source scope security removal, tenant disable and channel retirement each block only matching unexecuted work, with the expected typed result. Later recovery does not erase those barriers or rewrite accepted proof.
- Lower/equal-same/equal-different/higher version results remain `IGNORED_STALE` / `DUPLICATE` / `SOURCE_VERSION_CONFLICT` quarantine / atomic apply. Replaying after a core commit does not duplicate core state or canonical apply outbox. Job status and counts match persisted terminal item statuses, including mixed `PARTIAL` and all-failure `FAILED`.
- Confirm real worker role grants: claim, lease expiry recovery, safe item/job updates and ACK succeed; core authorization, source registry changes, tenant/source proof changes, raw mutation, and out-of-scope reads fail. Confirm `hub_api` still cannot read raw bytes or perform canonical core DML.
- Retry clock tests assert exactly the root-ratified interpretation of 5/30/120 and maximum-attempt count. Security-barrier results are durable and do not retry as transient failures. No real site IdP, CRM, SQL Server, Hermes, external endpoint, or deployment path is exercised; formal 48 rows remain NOT_RUN.
