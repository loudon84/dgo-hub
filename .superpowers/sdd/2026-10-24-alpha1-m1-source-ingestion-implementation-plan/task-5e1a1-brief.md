## Deliverable

Implement functional `POST /hub/v1/admin/etl-runs/{id}/retry` using existing authenticated snapshot routes and workers. A successful 202 identifies one immutable recovery operation and a linked child run/attempt that actually completes extraction/application through the existing canonical helper paths. It must not reset a terminal original, return an inert receipt, or route through gated legacy watermark reset.

### Strict public contract

- User principal only, current `source:write`, tenant/source derived from original authorized run. Source credentials, wrong tenant or source scope are rejected before writes. Recheck current principal under existing identity locks on idempotent replay.
- Required `Idempotency-Key` uses the established syntax and tenant/source/route scope. Strict JSON exactly `{failed_version: <canonical positive decimal bigint string>, reason: <trimmed nonempty string, max 1000 Unicode codepoints>}`. No source_version, tenant, config, raw facts, target mapping, arbitrary cursor or secret input.
- `failed_version` is a durable server CAS token for the original failed run, not a source business version. Add a monotonic failure/state revision minimally in 009. API-021 safe detail exposes this token for terminal FAILED/INCOMPLETE; do not use a JS time or updated_at as the CAS token. Previously terminal rows are initialized deterministically, and subsequent failure transitions cannot reuse a token. Original CAS/status/facts stay unchanged by API-022.
- Eligible original run: FAILED or INCOMPLETE only, no live extraction/C claim, no active original attempt. Reject COMPLETE/CANCELLED/live/nonterminal/missing or wrong-version requests with the existing safe 409/not-found semantics. No resurrection of successful or intentionally cancelled work.
- 202 envelope data exactly `{operation_id, original_run_id, run_id, attempt_id, recovery_mode, status, replayed}`. UUIDs are durable server IDs; `recovery_mode` is `FRESH_SCAN` or `SEALED_STAGE`; initial status `QUEUED`; replay returns original immutable accepted business result with replayed=true. Mutable execution state remains API-021. A different body under the same key is 409. Failed authorization/security/currentness never replays a 202.
- Add shared contract/error/OpenAPI documentation in existing contracts structure; preserve strict route middleware, envelope/error safety, and existing source-id validation limits consistently. Do not silently claim support for the separately recorded 256-vs160 source-ID mismatch.

## Immutable recovery rules

1. Create a durable immutable recovery linkage with original root/parent run and original attempt, original failure version/proof digest, new operation UUID, child run and new attempt identity, reason, actual initiator/authority facts and audit. One active child per parent/family; concurrent different keys cannot create competing recoveries. Repeated descendant recovery retains the same lineage root. Do not reset original run/attempt/C seal/outcome/ranges/D state or copy secrets into a new public table.
2. A lost/incomplete source snapshot never yields a resumable cursor. FRESH_SCAN performs a new complete read-only consistent scan under the original frozen approved connector/config/mapping/identity/profile/credential/channel/security proof. Retain partial original rows as diagnostics only. Child uses fresh attempt/snapshot identity; it cannot splice original partial pages with new source data.
3. SEALED_STAGE requires the original complete extraction manifest plus immutable whole-stage semantic validation seal and bound observation when that domain requires one. Consume exactly those original facts/digests, no upstream reconnection or latest mapping. Retain original observation/time and previously committed ranges, and apply only unapplied aggregates; exact committed prior receipt/range is the recovery success oracle. Do not treat a previously failed/quarantined outcome as successfully applied. Child-local claim/effect/progress and operation IDs must not mutate or counterfeit the original receipt. If preserving the normal C proof contract requires copying complete immutable stage facts into child coordinates, use narrow worker-owned functions and exact source-to-child digest equality; do not fabricate completed C proof. Record the selected minimal schema/proof loader design before product edits.
4. Complete extraction without a valid semantic seal is not SEALED_STAGE. It can restart a fresh complete scan under the frozen proof. Mapping correction is not E1a1; the API cannot change mappings to make failure pass.
5. One recovery lineage can contribute at most one distinct D absence observation, even when a child replays a sealed stage or a new scan follows failure. Normal unrelated successful snapshot runs retain D semantics. Bind lineage in reservation/consumption so completion does not double-count one original observation; no resetting D candidates/effects. Failed/partial/stale recovery does not increment/reset absence.
6. Ordinary pause/config/admission-epoch drift alone does not revoke the original durable proof. Preserve current source lifecycle/schedule; no autoactivation or scheduling enable. Current typed credential/scope/tenant revocation and channel retirement remain effective and are checked before scan admission and each apply. Retired epoch fails before any version comparison. No new primary channel/config/mapping selection through recovery.
7. Source serialization applies across normal runs, C, D reservations, recovery and future switch. No overlapping run for the tenant/source. Do not allow claim inspection to consume a start; four durable starts with DB5/30/120 retries and crash fallback remain required. Reuse established worker lifecycle without a second competing queue.
8. Guard-first locks, exact current caller scope and bound approval authority as required by the frozen source contract; canonical apply uses caller-owned PoolClient. Supplied/stored tokens and leases must be non-NULL, exact and live; retain fencing/authority locks through apply/outcome commit. False/missing outcome write rolls back the canonical helper. No source/network inside Hub TX.

## Controller pre-implementation clarifications

The immutable 202 attempt_id is preallocated with the recovery child at acceptance and consumed as that exact first attempt by the worker; accepting/claiming does not start or charge an attempt. Acquire the global barrier guard before taking current-principal identity locks, then follow compatible source/claim/authority order. SEALED_STAGE replays an existing source observation: it completes recovery only and creates no new D absence reservation. Existing D facts remain unchanged. FRESH_SCAN has an actual new full snapshot and can contribute at most one cohort per immutable recovery lineage root; independent normal snapshots are unaffected. This conservative zero-new-observation rule for SEALED_STAGE avoids fabricating child observation or manifest provenance and satisfies at-most-once lineage safety.
