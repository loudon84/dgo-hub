## Frozen contracts the builder must implement

- **Identity and trust:** tenant/source/entity/channel are trusted arguments derived from an authenticated source snapshot and the current approved registry; callers do not provide authoritative tenant, source, Owner, version domain, or channel epoch in business payload. Bind ownership only through the exact approved identity mapping revision (and any Owner-confirmation step required by the ruling section below). Never assign an owner from an incoming `owner_user_id` or trust an unapproved target UUID. Do not add authentication, credentials, authorization scopes, a second identity registry, or a migration runner.
- **Identifier validation:** public/business identifiers are case-sensitive, maximum 128 characters, and reject leading/trailing whitespace; do not trim or case-fold. Validate source PK and order-line source PK accordingly. Null and absent canonical fields remain distinct as specified below. Duplicate JSON object properties must be rejected by an upstream parser before schema validation; M1-2 must not pretend ordinary `JSON.parse` can detect them. Keep parser-boundary tests in the acceptance suite that owns that boundary.
- **Exact numeric values:** accept decimal strings and normalize exactly with BigInt: amount and line_amount to scale 2, quantity and unit_price to scale 6. Reject excess input scale, invalid syntax and overflow; never use JS Number or round. Quantity must be strictly greater than zero. Do not infer additional sign rules beyond the PRD/controller rulings. Accept CNY, USD, EUR separately; do not convert. The order header amount is authoritative and must not be forced to equal the line sum; PRD section 9.2 preserves source tax/discount basis. Versions use canonical 1-20 digit nonnegative decimal strings, no leading zero except 0; PostgreSQL storage is numeric(20,0), compared as BigInt/string and never JS Number.
- **Digest separation:** compute `sourceContentDigest` from normalized source-business content before target UUID resolution: retain external identity keys, sort object keys, distinguish null from absent, normalize decimal strings, sort complete order lines by source_line_id, and SHA-256 the canonical serialization. Exclude source_version, observation_seq, channel_epoch, event/batch/request IDs, receive/processing timestamps and other processing metadata. Compute a separate `projectionDigest` only if needed for resolved canonical values; owner-map changes may change it but never the receipt's sourceContentDigest. Keep raw source order/metadata out of both digests unless a field is itself business content.
- **Version semantics:** receipt key is (tenant, source, immutable channel identity/epoch, entity, source PK). Check retired/mismatched channel epoch before comparing versions; return a typed `CHANNEL_EPOCH_RETIRED` outcome. Never compare `SOURCE_VERSION` with `SNAPSHOT_OBSERVATION`; mode/domain are fixed by the active channel and cannot be selected per record. For the same non-retired channel/domain: lower => `IGNORED_STALE`; equal + same sourceContentDigest => `DUPLICATE`; equal + changed sourceContentDigest => `QUARANTINED(SOURCE_VERSION_CONFLICT)`; higher => atomically apply source business content, receipt, tombstone and outbox. Resolve external identity keys through the frozen approved map unless an explicit remap fence supersedes that mapping. Deleted receipts remain and older UPSERT cannot resurrect the record. Only a higher explicit UPSERT in the same version domain can restore it. No M1-2 logic allocates `SNAPSHOT_OBSERVATION`; M1-5 allocates it after complete snapshot validation and passes the persisted value to apply.
- **Aggregate transaction:** API exports applyCustomer(client, input) and applyOrderAggregate(client, input) with mandatory client: PoolClient. They do not connect a pool, issue BEGIN/COMMIT/ROLLBACK, release, or swallow errors. Caller wraps the operation with the existing transaction helper. One order header and its full line set (0-200; explicit [] is valid and missing lines is invalid), version receipt/tombstone, and outbox commit or roll back together. Delete/UPSERT replaces or logically deletes the entire old line set transactionally. Do not mark a caller event/job terminal here.
- **Tenant-safe relational shape:** migration 006 must add concrete tenant-scoped uniqueness and composite foreign keys for all cross-row links: canonical customer/order/line keys use `(tenant_id, id)`; order.customer references customer `(tenant_id,id)`; each line references order `(tenant_id,order_id)`; source identities reference an object key in the same tenant/source/entity. Add appropriate unique indexes before creating composite FKs. Do not rely on UUID global uniqueness as a tenant boundary. Preserve exposed `api.*` views and current indexes/columns required by M0 until their consumers are mapped. Add explicit currency, version domain, channel epoch, deletion/tombstone and hub revision columns through additive DDL where they fit; do not rewrite migration 001/demo rows.
- **Version receipt and tombstone records:** retain one authoritative receipt per tenant/source/channel epoch/entity/source PK with source version as decimal-safe storage, version domain, sourceContentDigest, canonical object UUID, deleted flag and commit time. The digest excludes version/observation_seq/channel_epoch and processing metadata; use projectionDigest separately if useful. Keep deletion receipt/tombstone after logical deletion. Use immutable channel identity from `control.source_channel` and ensure a composite constraint can prove that source/entity/epoch is the matching channel. Do not cascade-delete receipts, identity mappings, or tombstones when canonical rows change.
- **Transactional outbox:** append an immutable event record in `control` in the same database transaction as aggregate update, latest receipt and mapping/ownership effect. No network calls or dispatch in apply. No new outbox event for stale, duplicate or unchanged snapshot-observation content. Shape should carry tenant, source, channel UUID/epoch, entity, canonical object UUID, hub revision, operation, projectionDigest and sourceContentDigest as distinct values, not raw source payload or secrets. A human remap emits a projection change event without rewriting the receipt.
- **Ownership fence and digest semantics:** the receipt stores sourceContentDigest over source-business values and external identity keys, before target UUID resolution; it excludes source_version/observation_seq/channel_epoch and all processing metadata. An identical business payload replay at the same source version under a newer approved identity map returns DUPLICATE without applying its old projection or mutating the receipt; it must not undo a human remap. A genuinely pending higher-version job with the old identity target is fenced. Human remap changes canonical projectionDigest/outbox and ownership audit only; it never mutates sourceContentDigest or the source version receipt. Migration 006 should add only a narrow fence table such as `control.source_identity_remap_fence(tenant_key,source_id,kind,external_id,identity_mapping_revision,created_at)`, primary key `(tenant_key,source_id,kind,external_id)`, with a composite FK to `control.source_identity_mapping_revision(tenant_key,source_id,revision)` and the same kind/ID validation. Store no target UUID there; the existing JSON revision remains the only map authority. API-014 upserts this fence only for the identity key it explicitly corrected. At apply, compare that identity key's fence revision to the job's frozen identity_mapping_revision. If older, first return DUPLICATE for equal source version plus equal sourceContentDigest without touching projection or receipt; for a genuinely pending higher-version apply, return QUARANTINED(AUTHORITY_MAPPING_SUPERSEDED) and require explicit API-014 reconfirmation to use a newer target. Do not replay under a newly approved config automatically, do not cancel unrelated frozen jobs, and do not mislabel as SOURCE_VERSION_CONFLICT. Same-version actual business content changes still quarantine as SOURCE_VERSION_CONFLICT. Reuse reviewed M1-1 `control.source_identity_mapping_revision` and typed `IdentityMapping {kind:user|department|customer, external_id, target_id:string|null}`; do not create a parallel registry. Resolve only the frozen approved identity mapping revision carried by the job: user to enabled same-tenant `control.auth_subject`, department to a department on an enabled same-tenant subject, customer to a non-deleted same-tenant canonical customer. Owner/dept/customer remaps use API-014 expected revision, exact current Data Owner plus `source:approve`, and nonempty reason. Immediately update matching existing canonical references in the same transaction as mapping revision/audit/outbox and affected old/new subjects' auth_epoch; use a narrow controlled function, not broad hub_api core DML. Preserve UUIDs and source receipts/tombstones. Human mapping changes are never SOURCE_VERSION_CONFLICT.

```ts
type ApplyContext = Readonly<{
  tenantId: string;                  // from immutable admitted job
  sourceId: string;
  credentialId: string;
  sourceEpochAtAdmission: string;     // provenance only; not worker freshness
  credentialRevisionAtAdmission: string;
  credentialGenerationAtAdmission: string;
  entity: 'customer' | 'order';
  channelId: string;                  // immutable channel UUID
  channelEpoch: string;
  versionDomain: 'SOURCE_VERSION' | 'SNAPSHOT_OBSERVATION';
  ownerApprovalId: string;
  ownerUserId: string;
  ownerRevision: string;
  configRevision: string;
  configDigest: string;
  mappingRevision: string;
  mappingDigest: string;
  identityMappingRevision: string;
  identityMappingDigest: string;
  endpointProfileDigest: string;
  testReportId: string;
}>;
type ApplyResult =
  | { status: 'APPLIED'; objectId: string; hubRevision: string; digest: string }
  | { status: 'DUPLICATE' | 'IGNORED_STALE'; objectId: string; digest: string }
  | { status: 'QUARANTINED'; code: 'SOURCE_VERSION_CONFLICT' | 'AUTHORITY_MAPPING_SUPERSEDED' }
  | { status: 'CHANNEL_EPOCH_RETIRED' };

async function applyCustomer(client: PoolClient, context: ApplyContext, input: CanonicalCustomer): Promise<ApplyResult>;
async function applyOrderAggregate(client: PoolClient, context: ApplyContext, input: CanonicalOrder): Promise<ApplyResult>;
```
