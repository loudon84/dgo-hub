## Required findings

1. **C5C-R1 — P1: A rejected range record commits canonical writes without its atomic receipt.** `integration-service/etl-worker/snapshot-apply-worker.ts:138` (related lines 52 and 140; `integration-service/migrations/009_snapshot_runs_and_recovery.sql:999`). `applyOne` calls the canonical helper before checking the C token inside the aggregate transaction. If the lease expires before `record_etl_snapshot_aggregate`, its assertion returns `false`; the callback returns that value, `transaction` executes COMMIT, and only the code outside the transaction throws `SNAPSHOT_OUTCOME_COMMIT_REJECTED`. Thus canonical state and outbox can commit without outcome, range or checkpoint, including from an expired worker. This directly breaks the mandatory all-or-none recovery boundary. **Fix:** acquire/assert the live C run/attempt/token/lease under the guard at the beginning of the same caller transaction, before any helper write; throw inside that transaction if outcome/range/checkpoint recording returns false. Verify rejection after helper execution rolls back canonical state, outbox, outcome, range and checkpoint together, and that an already stale token cannot start helper effects.

2. **C5C-R2 — P1: Reusing an older successful observation can certify a snapshot that was never applied.** `integration-service/migrations/009_snapshot_runs_and_recovery.sql:976`. Reuse selects the smallest matching allocation from any prior COMPLETE run. With unchanged scope, A completes at observation 1, B changes business facts and completes at 2, then a new A snapshot reuses 1. The existing customer/order helpers compare receipt versions first and return `IGNORED_STALE` for 1 < 2 (`normalization/apply.ts:239`, `:348`); C treats that as a successful outcome and finalizes COMPLETE, leaving B in canonical storage. A newer failed partial run can produce the same problem even when the last successful run still matches A. This is a correctness failure regardless of whether “prior successful” permits arbitrary historical lookup. **Fix:** preserve observation reuse only while it cannot move behind a later allocated/applied source observation; conservatively reuse the latest allocation only when it has a matching successful COMPLETE binding and scope, otherwise allocate a fresh monotonic value. Controller should confirm the precise policy. Add A→B→A and COMPLETE A→partially applied failed B→A cases; assert canonical facts as well as run status and allocation count.

3. **C5C-R3 — P1: The processing path never renews its C lease.** `integration-service/etl-worker/snapshot-apply-worker.ts:155` (entire `processClaim`, lines 155–169). The store exposes `heartbeat`, but the worker never calls it. The worker claims with the default 60-second lease and performs every page proof check, reference query, semantic conversion and aggregate apply under that original deadline. A valid large snapshot can expire during validation or apply. Subsequent fenced readers return empty results or reject sealing/finalization; these become nonretryable semantic errors, and `fail_etl_snapshot_continuation` accepts the still-matching expired token and can terminally fail the run. During apply this also reaches R1. **Fix:** renew the lease during bounded validation/apply work with an explicit lost-lease stop, and prevent expired workers from recording a terminal failure. Use DB-clock lease decisions and preserve the four durable-start budget. Verify a valid continuation taking longer than one lease can finish, plus heartbeat rejection and expired-token failure fencing.

4. **C5C-R4 — P1: Whole-snapshot validation does not validate customer Owner and department identities.** `integration-service/etl-worker/snapshot-apply-worker.ts:106`. The only live-reference validation before the seal/observation is `validateOrderReferences`; customer conversion checks canonical shape but does not resolve its frozen user/department mapping or enabled sales subject/department. Actual checks occur later in `resolveCustomerOwner` inside `applyCustomer` (`normalization/apply.ts:166`, `:276`). A customer-only batch with an earlier valid customer and a later unknown external Owner therefore passes the success seal, allocates an observation, commits the earlier customer/outbox/range, then quarantines the later customer. Required identity failures must reject the entire batch before those effects. **Fix:** add bounded/indexed whole-batch validation for every live customer's frozen user and department mapping, live enabled target, sales eligibility, matching department and relevant mapping-remap fences before the seal/observation; retain helper rechecks at each aggregate boundary. Verify a late missing/stale/disabled/mismatched identity causes zero observation, canonical, outbox, outcome, range and checkpoint effects.

5. **C5C-R5 — P1: The exact source-qualified customer tuple is not rechecked inside the order transaction.** `integration-service/etl-worker/snapshot-apply-worker.ts:134`. The C-wide reference SQL checks `(tenant, customer_source_id, customer PK, live canonical UUID)` before validation seals. `applyOne` later invokes the unchanged order helper without repeating or locking that exact tuple. The helper checks only the frozen external-key mapping, its remap fence and whether the mapped UUID remains a live tenant customer (`normalization/apply.ts:380`–`:392`); it does not validate that the configured same/foreign source identity tuple still points to that UUID. A tuple change after full validation can therefore pass the effect boundary. **Fix:** in the same guarded, token-fenced aggregate transaction, resolve and validate the exact configured source/PK/UUID tuple against the frozen mapping and live canonical customer before helper apply, with a locking strategy that keeps the assertion valid through commit. Add same-source and foreign-source target-change cases between sealing and aggregate apply. Preserve the canonical helper rather than introducing a bypass authority.

6. **C5C-R6 — P1: Supported boolean tombstones fail before tombstone interpretation.** `integration-service/etl-worker/snapshot-apply-worker.ts:89` (callers at 63, 72 and 118). `normalizeSnapshotTimestamps` treats every string `deleted_at` as a timestamp. PostgreSQL extraction casts boolean source values to text, and the approved C conversion explicitly recognizes `'true'` and `'false'`. Both strings fail the timestamp regex before `sourceDeletion` can interpret them; even ordinary nondeleted rows from a boolean-delete source fail C validation. The pure helper test passes because it bypasses the worker normalizer. **Fix:** interpret deletion markers using the frozen tombstone contract before timestamp normalization, normalizing only actual timestamp values and using approved source_updated_at for true. Add an end-to-end worker case with boolean false and true, checking the stored exact source delete time and no wall-clock substitution.

7. **C5C-R7 — P1: API-013 discovery omits the required operation-time principal check.** `integration-service/source-registry/service.ts:670`. The method checks `source:approve` on the previously supplied principal and calls `currentOwner`, which checks only tenant/subject enabled state. It never revalidates the principal's issuer/subject binding, auth epoch or current scopes in the query transaction. A binding revocation/remap or scope removal after OIDC resolution but before this query can still disclose source PK/UUID pairs while the subject remains enabled and is the registered Owner. `AuthService.assertCurrentPrincipal` already provides the required locked current-principal/scope check (`auth/service.ts:407`). **Fix:** expose/use that existing assertion with `source:approve` inside the guarded discovery transaction, before reading the safe view, and retain the exact current enabled Owner check. Verify stale auth epoch, removed scope and disabled/remapped identity binding are denied at that boundary. The default API-013 behavior need not change.

8. **C5C-R8 — P2: Foreign-source references are incorrectly required to exist in this run's local customer stage.** `integration-service/migrations/009_snapshot_runs_and_recovery.sql:891`. The staged-customer membership condition applies whenever customer extraction is included, even when frozen `customer_source_id` explicitly identifies another source. A combined snapshot containing local customer L and an order referencing foreign source customer F is rejected unless F also happens to be a live row in the local stage, despite an exact frozen mapping and live foreign tuple. The accepted contract requires local stage membership for same-source references and the foreign live tuple for explicit other-source references. **Fix:** apply this membership condition only when `p_customer_source_id = p_source_id`; retain exact frozen foreign tuple/live-target validation and aggregate rechecks. Add the missing fixture with both local customer extraction and a foreign reference whose PK is absent locally.

9. **C5C-R9 — P2: Semantic validation retains hundreds of complete order aggregates at once.** `integration-service/etl-worker/snapshot-apply-worker.ts:71`. `proofFacts` reads a semantic chunk of 500 headers, fetches up to 200 lines per order, and pushes each complete normalized aggregate into `normalized` before yielding it. This retains up to 100,000 normalized lines plus the header page, exceeding the explicit memory contract of one bounded stage page plus one order aggregate. It is bounded by a large product of limits rather than the agreed aggregate boundary. **Fix:** stream each normalized order into the digest immediately (for example yield one aggregate at a time) and release its lines before loading the next. Keep the same deterministic full-key digest and verify a many-order, 200-line case stays within the agreed retained-data bound.

10. **C5C-R10 — P2: Claiming C applies a broader security barrier than the accepted typed tuple.** `integration-service/migrations/009_snapshot_runs_and_recovery.sql:703`. The claim barrier query filters only tenant/source and type; it omits credential, entity and channel matching present in `assert_etl_snapshot_continuation` at lines 731–736. For example, a post-admission order-only scope-removal or unrelated order-channel retirement terminally fails a customer-only run for the same source. Recovery cannot restore it because C failure is terminal and E is outside scope. **Fix:** share the exact typed barrier predicate with the assertion/helpers, including admitted credential and expected entity/channel proof. Verify both a matching barrier that blocks and an unrelated entity/channel/credential barrier that does not invalidate this accepted run.
