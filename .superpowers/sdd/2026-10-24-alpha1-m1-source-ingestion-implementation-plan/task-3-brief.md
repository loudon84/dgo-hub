## Public contract to preserve

Routes are exactly:

- `POST /hub/v1/ingest/crm/customers` (API-015; source entity `customer`).
- `POST /hub/v1/ingest/orders/orders` (API-016; source entity `order`).
- `GET /hub/v1/ingestion-jobs/{id}` (API-017).
- `GET /hub/v1/ingestion-jobs/{id}/items` (API-018).

Success envelope is `{ "request_id": "...", "data": { ... } }`; failure envelope is `{ "request_id": "...", "error": { "code": "...", "message": "...", "retryable": false, "details": {} } }`. Reuse Fastify's server-generated request ID (`request.id`; the current app generates a UUID and disables caller request-ID headers). Do not put request ID into business digest or confuse it with `batch_id` or `event_id`.

The PRD batch is a strict object with `schema_version: "hub.v1"`, UUID `batch_id`, and `records` containing 1–100 items; the complete body is at most 4 MiB. Each item requires UUID `event_id`, case-sensitive `source_pk` (1–128 characters, no leading/trailing whitespace), canonical nonnegative decimal-string `source_version` (1–20 digits; no leading zero except `0`), `operation` in `UPSERT|DELETE`, offset-bearing RFC3339 `source_updated_at`, and `data`. `UPSERT` requires the complete entity image. `DELETE` requires `data: null`. Reject duplicate property names at every JSON nesting depth before schema validation. Reject unknown fields (`additionalProperties=false` semantics) at every level. A structure/auth/idempotency rejection writes no durable batch/job/item/outbox rows.

Use the exact PRD entity images with root's rulings. Customer UPSERT fields: `customer_name`, `owner_external_id`, required `department_external_id`, `status` (`ACTIVE|INACTIVE`), optional nullable `phone`; map the public department field to M1-2's internal `dept_external_id`. Order UPSERT fields: `customer_ref:{source_id,source_pk}`, `order_no`, `status` (`DRAFT|CONFIRMED|COMPLETED|CANCELLED`), offset-bearing RFC3339 `order_at`, decimal-string `amount`, `currency` (`CNY|USD|EUR`), and complete `lines` (0–200). `customer_ref.source_id` follows the existing registry rule `^[A-Za-z0-9][A-Za-z0-9._:-]{0,255}$`: case-sensitive, 1–256 characters, rejecting leading/trailing whitespace without trimming or case conversion. It may differ from the order source but must name a same-tenant CRM source. `source_pk` follows the PRD identifier rules (1–128 characters, no leading/trailing whitespace). Preserve the validated public `customer_ref` values intact as an immutable event fact. M1-3 does not resolve customer existence or mapping during admission. The customer identity mapping remains the order source's frozen typed revision: `external_id = customer_ref.source_pk` maps to `target_id = canonical customer UUID`. M1-4 adapts `source_pk` into M1-2's internal `customer_external_id`, then verifies that the frozen mapping target is the same-tenant live canonical customer reached by `(customer_ref.source_id, customer_ref.source_pk)` in `control.canonical_source_identity`; missing or mismatched refs quarantine that item. Equal source PK values from different customer source IDs may occur in one batch; only the tuple that resolves to the frozen mapping target can apply. Keep `source_id` in the immutable event fact and do not add a mapping authority.

A line requires `source_line_id`, `product_code`, `product_name`, decimal-string `quantity`, `unit_price`, and `line_amount`; line IDs are unique within the order. Amount and line amount have scale 2; quantity and unit price have scale 6; quantity is >0; values outside precision/scale reject without rounding. The PRD does not explicitly say that lexically different valid decimal strings with the same numeric value are equivalent for `request_digest`; preserve the validated submitted decimal strings in that digest, and let the M1-4 adapter pad scale for M1-2. Header amount is source-authoritative; do not require it to equal the line sum. Map public record metadata into M1-2's internal apply shape only in the later M1-4 adapter. The pinned registry and `control.canonical_source_identity.source_id` both use text IDs; retain text values and the source-registry case/whitespace rules.

The public record is the sole location for `source_pk`, `source_version`, `source_updated_at`, and `operation`; reject these transport fields if repeated inside `data`. For DELETE, map outer `source_updated_at` to internal `deleted_at` after UTC normalization. Preserve public DELETE `data:null` in the normalized item facts.

`Idempotency-Key` is mandatory and matches `^[A-Za-z0-9._:-]{1,128}$`; it is case-sensitive, untrimmed, and has no TTL or automatic deletion in M1. Its unique scope is authenticated tenant + source + exact route + key. Use root's canonical request digest, separate from M1-2's source-content digest. Same scope/key and same digest returns the existing job's current safe status/counts; it must not call a later job newly `RECEIVED`. In this M1-3 stage, status remains `RECEIVED`. Changed canonical content returns HTTP 409 and creates no new job. Both intake routes return 202 with `job_id`, `status: "RECEIVED"`, `received_count`, and `applied_count: 0`. Structurally valid missing customer refs do not reject the batch; M1-4 quarantines the affected item.

Use PRD §13.3's exact `request_digest = SHA256("hub.ingest.v1" + NUL + tenant_key + NUL + source_id + NUL + route + NUL + canonical_json(body))`, where tenant/source/route are the authenticated scope and exact route, and `body` is the validated public request. Canonical JSON is UTF-8, has no whitespace, sorts object keys by Unicode code point (UTF-8 byte order is equivalent for valid Unicode), preserves strings' original Unicode and case, preserves array order, distinguishes null from missing, and rejects duplicate keys and unpaired surrogates. Do not normalize UUID case, timestamp offsets, optional-field absence, or public customer-ref source text for this digest. Canonical key order/JSON formatting yields the same digest; changes to batch/event UUID spelling or case, timestamp spelling/offset, absent vs null phone, array order, version, amount lexical form, or any other body value yield a different canonical request. The PRD requires amount and source_version as decimal strings; source_version has its strict no-leading-zero schema. Amount lexical equivalence is not defined, so retain the validated submitted amount string in request_digest. Do not use JavaScript Number. M1-4 may separately normalize UTC timestamps and pad decimal strings for M1-2 input; that adapter normalization does not alter the request digest.

For a same-key replay, first authenticate the currently presented source credential and validate tenant/source/entity scope plus enabled tenant/credential. If the same committed key/digest exists, return its safe current job state even after ordinary PAUSED/config edit; do not re-run `assertCurrentSource`, create rows, or alter proof. A revoked credential or disabled tenant cannot replay. A different digest under the same scope/key is 409. A first-time job still requires current ACTIVE assertion and approved proof.

Use the common failure envelope and stable codes: `AUTH_INPUT_INVALID` follows the existing Hub 422 mapping; invalid/revoked credentials are 401 and source-scope denial is 403 per PRD; `INGEST_INPUT_INVALID` is 422 with safe path and reason code only; `INGEST_JSON_DUPLICATE_KEY` is 422 with safe path if available and never the key value; malformed JSON is 422; unknown content type is 415; over-limit is `INGEST_BODY_TOO_LARGE` 413; idempotency mismatch is `IDEMPOTENCY_CONFLICT` 409; current admission proof/lifecycle conflict uses existing `SOURCE_CONFLICT` 409. Do not return offending values, payload, credential data, SQL, or cross-tenant identifiers in details. 202 means durable receipt only, not successful application or queryability.

API-017 returns batch status, counts, and first/last timestamps. API-018 returns safe summaries (`event_id`, `source_pk`, item status, error code) ordered by ascending immutable ordinal. Pagination defaults to 20, caps at 100, and uses a job-bound canonical base64url cursor over job UUID + ordinal. Add no statuses beyond the existing PRD/M1-4 vocabulary; M1-3 acceptance state is `RECEIVED`. Reads are limited to the source's own tenant/source or an authorized same-tenant OIDC management reader. Neither route returns raw bytes, parsed payload, credentials, secret refs, or another source's object names. Store raw bytes as immutable `bytea`; hub_api is insert-only and hub_worker receives read access. Strict intake fails closed when deployment raw-storage policy is absent. Local tests may use an explicit `local_lab` storage policy; do not claim local storage is encrypted or add an encryption framework. Keep payloads out of HTTP errors, logs, outbox, and test failures.

## Admission and durable transaction

Use one caller-owned PoolClient transaction (`TX-INTAKE`) for immutable raw batch, job, item rows/references, scoped idempotency request digest, frozen admission proof, and processing outbox. Preserve each validated public record's exact string values and missing/null distinctions, including full `customer_ref`, as immutable event facts. Do not resolve customer existence or mapping at admission, add identity-query grants, or reject an otherwise valid batch due to a missing customer; M1-4 quarantines only affected items. Commit once; only after commit send 202. Any SQL error rolls back all intake rows. The intake outbox is for M1-4; do not write M1-2 `canonical_apply_outbox` during acceptance.

Follow M1-2's security-fence lock order. First DB lock in TX-INTAKE is `SELECT control.lock_security_barrier_fence()`; persist its bigint as `securityBarrierFenceAtAdmission`. Load the exact current approval's new `approval_security_fence` (007) and reject only applicable typed barriers with `effective_fence > approval_security_fence`; older barriers covered by a fresh approved recovery do not permanently block new jobs. Then lock current source proof and call `assertCurrentSource` on that client immediately before commit. Freeze tenant/source/entity, credential ID, source epoch, credential revision/generation, channel ID/epoch/domain, Owner approval ID/user/revision and approval fence, config/mapping/identity-map revisions+digests, endpoint digest, test report ID, and admission barrier fence. Source all proof values from authenticated principal and locked DB rows, never body. Never fabricate proof or reinterpret old jobs under today's config.

M1-2 `ApplyContext` requires `securityBarrierFenceAtAdmission`. Apply takes `lock_security_barrier_fence()` before credential/channel locks and blocks barriers newer than the admission fence. Migration 007 adds `source_owner_approval.approval_security_fence`: historical approvals default to `0`; a BEFORE INSERT trigger captures the DB fence while holding the shared guard, and new approval transactions take that guard before source/credential locks. Admission compares matching barriers to the exact bound approval fence. This permits recovery under the same credential row ID after a fresh Owner approval while accepted old jobs remain subject to barriers newer than their admission fence. Ordinary pause/edit/tenant re-enable alone never clears a barrier. Existing source registry flow supports explicit `pause → test → approve → activate` after tenant re-enable; that creates a fresh Owner approval fence. Do not delete barriers or use timestamps/current generation alone as recovery proof. `assertCurrentSource` remains admission-only: it checks ACTIVE, enabled tenant/credential, entity scope, config/credential revision, and source epoch; do not make this a worker lifetime check.

An ordinary pause, config/mapping edit, or ordinary credential replacement after 202 stops new admissions but leaves accepted work eligible under its immutable approved proof. Explicit credential compromise, security scope removal, tenant disable, or channel retirement remains an independent barrier; M1-4 isolates matching old work. An explicitly approved recovery authorizes new jobs only, never retroactively rewrites old jobs. Keep frozen config/map/channel. `SOURCE_VERSION` REST uses the active channel's frozen domain; do not allocate snapshot observations or accept caller-selected channel/version domain.
