## Source transaction, paging, and destination stage

Create a narrow injected `PostgresSourceConnectionFactory` from the frozen profile, in-memory password, and deployment egress/TLS policy; one connection (`max: 1`), no ambient URL. Bind DNS-resolved/pinned peer to the approved host/profile and verify the peer before queries. Enterprise private addresses require explicit policy approval; fail closed if policy is unconfigured. Local fixtures use an injected `local_lab` factory limited to exact loopback. Keep the source connection read-only through separate source and hub DB pools; the production source role must have only required `SELECT` permissions. User values, page bounds and cursor controls are bound parameters. Validate and quote every schema/table/column identifier from the frozen profile/mapping.

Use one source session/transaction for all enabled customer, order-header and order-line reads:

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY;
SET LOCAL TIME ZONE 'UTC';
```

Page sequentially and deterministically per relation. A transaction-bound non-HOLD cursor is preferred; a keyset alternative is acceptable only if every page stays in this same transaction/snapshot and uses a strict stable key order. No cursor or MVCC snapshot survives a lost source connection. Cast numeric, integer/bigint/version, decimal and timestamps to text in SQL before the driver can round them. Validate exact decimal/version grammar and preserve PostgreSQL fractional timestamp precision without JavaScript `Number` or millisecond `Date` conversion. For orders, stage complete header aggregates with line data (or parent/child rows keyed immutably and join-validated); preserve line order by the unique line key, with exact decimal strings.

Use an attempt-scoped private stage, minimally:

- Snapshot attempt state with monotonically increasing attempt ordinal, operation/claim token, lease expiry, DB-clock availability, status/error, source snapshot identity, and immutable admission proof reference.
- Immutable `etl_snapshot_stage_page` receipt keyed by `(tenant_key, source_id, run_id, attempt_id, entity, relation, page_no)`, with row count, first/last ordered key, and page digest.
- Immutable attempt-scoped `etl_snapshot_stage_record` keyed by `(tenant_key, source_id, run_id, attempt_id, entity, full source key[, line key])`, containing canonicalized-but-not-yet-validated JSON/text facts and source-key/version facts. Enforce uniqueness; duplicate source keys fail the attempt. Do not use upsert/conflict-ignore that can hide duplicates.
- Immutable completion manifest keyed to the same attempt, state `EXTRACTED`, enumerating the complete expected entities/relations, page receipts/counts/digests, source transaction identity where safely available, and deterministic aggregate digest. It can be written only after each relation reaches EOF and all key/FK/required-column/page invariants pass.

Commit each destination page's records and page receipt atomically. A lost source transaction, cancellation, query error, lease loss or process crash leaves the attempt incomplete/diagnostic and its pages ineligible for absence, validation, or apply. Mark that attempt `INCOMPLETE`; a retry starts a fresh full source transaction and full scan under a new attempt ID. Never resume source paging from a checkpoint after reconnect. Keep an incomplete attempt's staged pages for diagnosis or controlled expiry; do not silently mix attempts. Only a complete immutable `EXTRACTED` manifest can be consumed by C. In B the ETL run should stop in `VALIDATING` (or the explicit accepted extraction-pending-validation state) and must not become `READY`, `APPLYING` or `COMPLETE`.

## Claim, retry, lease, and scheduling

Reuse API-019's already-created queued run and existing schedule gate; never enqueue a second independent run queue. The runner claims from `control.etl_run` with source/tenant fence ordering, one active run per source, and `FOR UPDATE SKIP LOCKED`; issue a fresh random claim token for each attempt and require that token plus nonexpired lease on every heartbeat, page receipt, attempt/run status, and terminal update. Use database time for lease deadlines and scheduled/retry due checks. A stale token may not publish a page, complete a manifest, change a run, or start apply. Run one source scan at a time (`max:1` source connection, no parallel scans/apply).

Use a bounded four-start budget: initial attempt plus at most three retries. For observed transient failure, persist retry availability at 5, 30, then 120 seconds using `clock_timestamp()`. Permanent profile/permission/contract errors fail without retry. Process-crash/lease-expiry recovery marks the previous attempt incomplete using DB time and follows the same persisted bounded retry budget; exhausted attempts fail the run. Keep the 300-second per-source schedule and preserve the unique active-run gate. Do not claim that an in-process timer alone provides durable scheduling; API/manual admission, due gate, and strict worker wiring all need an independent acceptance trace.
