The implementation adds durable D claim/lease and retry state, bounded four-start processing with database-clock delays, heartbeat fencing, full candidate/currentness checks, and transactional canonical delete, durable outcome, receipt, progress, and outbox writes. The worker processes only a fully validated, frozen C cohort. Candidate operation UUIDs are allocated by `claim_etl_snapshot_delete_apply`: the claim transaction inserts one immutable operation row per `(candidate_id, entity, source_pk)` tuple using the table’s `gen_random_uuid()` default and unique key before the worker starts effects. The worker’s autocommit claim query returns only after this allocation transaction commits. Resume finds that same row under the unique tuple key, so it retains the same operation ID. Effect application is idempotent against the exact durable receipt. Source connector reads and physical business deletes are not introduced into D. API replay returns an existing valid APPLYING/COMPLETE approval result only under the bound identity, owner, epoch, scope, and currentness checks; it does not create a replacement approval. Above-threshold cohorts remain paused/disabled through approval and terminal processing; finalization does not activate them.

The schema contract was recorded before product edits at [m1-task5d3-schema-contract.md](E:/git/dgo-hub/.superpowers/sdd/2026-10-24-alpha1-m1-source-ingestion-implementation-plan/context/m1-task5d3-schema-contract.md). The test now asserts that exact SQLSTATE/constraint and the safe persisted C failure (`SNAPSHOT_C_PROCESSING_FAILED`, one customer outcome, zero order outcomes).
