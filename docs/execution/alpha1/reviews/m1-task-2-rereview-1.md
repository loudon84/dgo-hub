## Remaining Original Finding

### M1-T2-I6 — Important / P1 — The helper rejects a valid ownership change between two approved external identities

- **Locations:** `integration-service/normalization/apply.ts:297`–`:303`; `integration-service/migrations/006_canonical_data_and_receipts.sql:382`–`:388`, especially `:386`.
- **Reproducible cause:** use one frozen approved map containing user `ext-A -> A`, user `ext-B -> B`, and department `ext-D -> D`, with enabled sales users A and B both in D. Apply customer C version 1 with owner_external_id=ext-A. Its authoritative identity-reference row is `(kind=user, external_id=ext-A, target_id=A)`. Apply version 2 of C with owner_external_id=ext-B and the same valid frozen proof. New-target approval/eligibility checks pass. The caller passes `p_external_id=ext-B`, `p_old_target=A`, `p_new_target=B` into the helper. Its current-projection query demands an existing reference whose external_id is ext-B and target is A; the actual old reference is ext-A/A. It therefore raises SQLSTATE 42501 (`source ownership change does not match current projection`) before the legitimate atomic ownership change can finish.
- **Impact:** a valid higher source version cannot apply. The required old/new authorization epoch and audit semantics are not implemented for the original A→B source-content case. A test that remaps the target of the same external key, as the new test does, cannot detect the predicate mismatch.
- **Fix:** independently bind the old reference/key to current authoritative core state and the new reference/key to the frozen approved mapping; do not require old and new external keys to be equal. Derive the old key from the locked reference or pass a separately validated old key. Add the exact two-key/single-frozen-map scenario under hub_worker and assert stable UUID, correct receipt/outbox, old/new epoch/audit effects and rollback.

### M1-T2-I14 — Important / P1 — The new worker definer can mutate an unrelated subject's auth_epoch

- **Locations:** `integration-service/migrations/006_canonical_data_and_receipts.sql:374`–`:391`, with worker EXECUTE at `:611`.
- **Reproducible cause:** the helper checks old target against current core/reference and validates p_new_user, but never binds p_old_user to the customer's actual current owner. Take an existing customer whose current owner/reference is A, a valid next mapping of the same external key to enabled sales B, and a third same-tenant subject Z with no relationship to that customer/source. Invoke the granted helper with the valid customer/key/old_target=A/new_target=B, but `p_old_user=Z`, `p_new_user=B`. The helper can be committed directly without applying the purported canonical change.
- **Impact:** hub_worker has acquired an authorization mutation path outside the intended affected old/new subjects. The role test proves direct auth_subject UPDATE is denied; it does not prove this newly granted SECURITY DEFINER path is narrow. The defect follows directly from the new function's parameter predicates and UPDATE, without assuming the shared worker role is tenant-restricted.
- **Fix:** derive the actual old subject from authoritative locked core/reference state and the new subject from the approved identity proof; enforce that every epoch target is one of those actual affected subjects. Bind the controlled permission effect to its corresponding canonical change in the caller transaction and reject inconsistent parameter tuples. Add a real-worker negative invocation with unrelated Z and assert epochs/audit/core/receipt/outbox remain unchanged.
