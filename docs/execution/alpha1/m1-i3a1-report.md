The trust boundary remains the existing Hub HTTP service plus OIDC/AuthService. SQL principal strings are checked against the current scoped actor/Owner and epoch, but are not cryptographic JWT proof; end users do not have hub_api credentials. This slice does not claim resistance to compromise of the trusted Hub service or its database credential and does not add a capability store, verifier, mapping engine or separate authority system. Replay returns the immutable accepted IDs after current namespace/Owner authorization even after pause, edit or Owner reassignment; it does not refresh the binding proof, reapprove, or revive the operation.

The actual 007 item states `APPLIED`, `DUPLICATE`, `IGNORED_STALE` and `QUARANTINED` take precedence over the job summary; in particular the existing worker records job `FAILED` for an all-quarantined job. A pending item with a durably failed job maps to `FAILED`. The 006 receipt is a current keyed source-version row, not a UUID-addressed historical record. Only an APPLIED child's matching channel/epoch/version/content/reserved UUID can yield bounded current receipt metadata. DUPLICATE and all other outcomes return null; a later source version also makes the receipt null. This row has no event/operation ID, and no stronger historical causality is asserted.

## Null-facts classification boundary

The unchanged 015 `import_recovery_original_facts_internal` returns the same SQL null for several distinct conditions: an index that is not a quarantined import; a missing or out-of-scope original job, a recovery child, an unsupported original route, profile or version domain, an invalid ordinal, or a missing management-admission audit; a missing/non-quarantined/non-UPSERT item, an item/index mismatch, or an unsupported entity/error combination; a mismatch between the original index and job proof tuples; or a missing original approval or mismatch of its frozen approval security fence. For a known, unconsumed namespace the existing envelope cannot distinguish these, so admission fails closed with `RECOVERY_SCOPE_UNAVAILABLE`. This classification does not assert that every such state is reachable through supported Hub operations. The accepted foreign keys, immutable job/index/item facts and audit, and approval grants constrain normal mutations; privileged/manual changes, unsafe historical data, or mutable item-status changes can still produce some of the null cases. In particular, the ordinary worker treats a quarantined item as terminal, but this report does not claim that a privileged database actor cannot change its status.

These nulls are distinct from reachable current-authority and stale-proof conditions when valid original facts are returned. Original security-barrier failure returns `IMPORT_RECOVERY_CONFLICT`. For an otherwise supported original with a missing mapping, a live originally resolved user/department target becoming invalid or a resolved-key remap fence is also a conflict; once the candidate is eligible, current approval/source proof staleness and invalid proposed targets likewise fail as conflict through the existing P2 checks. Actual HTTP regressions cover the original barrier, live target loss, remap fence, stale current proof and wrong target. An original with no missing mapping is unsupported, as is an originally resolved order even if its live target is later corrected; these return `RECOVERY_SCOPE_UNAVAILABLE`. Original proof validation takes precedence over mapping eligibility, so a simultaneous original barrier returns conflict. The private authorizer itself can return SQL null for a missing scoped quarantine, credential or source and the route hides it as 404; accepted relational constraints prevent normal removal of referenced credential/source rows, but privileged corruption is not ruled out. The 015 candidate filter also suppresses facts for a consumed original: A1 checks the operation first, so an authorized replay returns its immutable IDs without asking the candidate resolver to recreate the proof.
