## Result and actual boundaries

- `etl-worker/worker.ts` reads the immutable nullable job discriminator through `to_jsonb(j)->>'import_recovery_operation_id'`, also compatible with historical schemas. Its claim query excludes all non-null discriminators **before** queue ordering and LIMIT. A loaded flagged job is skipped before hooks, record adaptation, attempt creation, the ordinary REST guard or claim finish/ACK. Defensive guards also prevent `setInvalidFacts`, `applyItem`, and `finishClaim` from acting on a flagged loaded job. Ordinary jobs keep the existing REST binding guard and queue order.
- `migrations/017_import_recovery_worker_context.sql` installs exactly `control.read_import_recovery_worker_context(text,text,uuid,integer,uuid,uuid) RETURNS jsonb`, with fixed `search_path=pg_catalog`, effective `hub_worker` check and worker-only EXECUTE. It accepts namespace, child job, ordinal, ordinary item UUID and claim token, derives the operation from the immutable job flag, and checks the scoped reverse link, `PROCESSING` job, ordinal-zero `APPLYING` item, matching item UUID, unacknowledged live lease and token. It reuses the accepted 016 cycle checker and the 015 private original-facts reader after consumption, not the public consumed-candidate filter. Operation and auth tables gain no new broad grants; the worker is not granted the API-only 016 lookup/admission functions.
- The definer takes the existing global security guard, outbox and item locks, source credential, source registry, ordered relevant channel locks, current tenant/subject/binding locks, then the existing resolver's canonical identity and target locks. Current tenant, actor and exact issuer/subject binding must be enabled, the frozen auth epoch must match, `source:approve` must remain present, and the designated Owner ID and revision must match. The SQL return carries precise decimal strings, bounded original effective record, actor/operation/reservation identifiers, separate original and binding proof metadata, confirmed bindings and observed fence; it does not carry raw bytes or a credential verifier. OIDC issuer/subject use exact existing binding keys, not canonical target identifier rules.
- `etl-worker/import-recovery-context.ts` is the transaction-scoped TS seam. It validates the selected record and original metadata, compares each stored approval sample digest and approval fence, checks approval <= admitted/observed fence <= currently locked fence, and invokes existing `verifyFrozenApplyContext` separately for original and binding contexts. It retains the existing validator's barrier semantics and does not add a stricter older-approval-fence barrier engine. The returned internal record and proofs are not HTTP serialization. The result is only valid while the caller retains its transaction and locks. No recovery identity resolution or canonical apply is implemented in W0.
- Internal failures are `IMPORT_RECOVERY_CONTEXT_INVALID`, `IMPORT_RECOVERY_AUTHORITY_INVALID`, `IMPORT_RECOVERY_PROOF_INVALID`, and `WORKER_CLAIM_LOST`; unauthorized roles get SQLSTATE `42501`. Flagged jobs never become ordinary jobs because an operation is absent or inconsistent. Referential/immutable constraints make some missing or mismatched operation states unreachable through supported writes; these are not claimed as directly forged production mutations.
- The UUID fix compares `record.event_id` and stored PostgreSQL UUID text case-insensitively **after** strict validation. It changes neither raw input, public record, digest, event value, source version nor conversion helpers; no version/variant restriction was added. A trusted corruption fixture temporarily disables the immutable-item trigger inside its own transaction, changes the stored event UUID, flushes deferred checks, re-enables the trigger and commits the deliberately inconsistent fixture. A genuinely different value is still quarantined as `DURABLE_FACTS_INVALID`; no canonical identity appears. This is a deliberately privileged impossible supported-write state, not a production mutation capability.
- The shared P1/P2 fixture now explicitly excludes 017 from its historical 001–012 bootstrap; the 013/014/015/016 staged assertions are unchanged. Three existing migration-history assertions now explicitly include 017. Both import contract documents describe the W0 staging boundary. The pre-code freeze is `context/m1-i3w0-contract.md`; its initial incorrect workspace-report path and overly broad barrier wording were corrected by controller ruling before the reader and history changes. The corrected contract was stable throughout the final bracket.

The processing outbox INSERT remains atomic with admission. Eventual canonical aggregate/lines, receipt, canonical outbox, item outcome and job summary remain one live-claim application transaction. Processing-outbox ACK is a separate subsequent claim-checked transaction; W0 does not redesign or claim to have tested FI05. No exception to the frozen actor auth epoch is introduced for the potential 006 ownership side effect; W1 must first produce the actual existing-customer ownership-change fixture and bring a concrete contradiction to the controller if it arises.

## Fix round 1 — live lease at reader completion

The independent W0 review found one Important defect: the SQL reader checked lease liveness only on entry, and the TypeScript seam returned after proof validation without rechecking it. The outbox row lock prevents claim replacement during the transaction but does not pause wall-clock expiry. This was a seam-contract defect; W0 still does not apply a recovery child. The SQL/TS signatures, grants, authority and proof semantics are unchanged. The `context/m1-i3w0-contract.md` fix1 addendum froze the two completion checks before product edits.

`017_import_recovery_worker_context.sql` now repeats the exact job/tenant/source, token, unacknowledged and `lease_expires_at > clock_timestamp()` predicate after its potentially blocking authority/original-fact work. `etl-worker/import-recovery-context.ts` repeats the scoped predicate after both `verifyFrozenApplyContext` calls and immediately before returning. Either failure is `WORKER_CLAIM_LOST`. These are non-mutating reads and do not renew or revive an expired lease; the existing `lockClaim` was deliberately not used because it extends the lease. The caller still owns the open transaction and its locks. W1 must independently check live claim through its own effects and commit; a successful W0 return is not a future lease guarantee.

Two new tests use the existing actual OIDC/A1 fixture and a rollback-only controlled claim. The first holds the real actor binding row lock, observes the reader blocked using `pg_blocking_pids`, waits on the actual PostgreSQL clock until the known lease deadline, releases the lock and calls the SQL function directly as `hub_worker`. The second confirms SQL returned while the lease was live, then a test-only client wrapper delays completion of the second real proof-barrier query until PostgreSQL's clock reaches the deadline. This exercises the TS boundary independently; no production hook or fake clock is introduced. Both compare before/after actor, tenant, binding, Owner, item/claim/ACK and canonical/receipt/outbox snapshots, confirming no side effects and unchanged authority. Existing initially expired, replaced, acknowledged, wrong-role and scoped claim tests remain in the full file.
