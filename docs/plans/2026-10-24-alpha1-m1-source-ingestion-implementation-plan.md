## Frozen cross-task rules

1. **Authority/revisions:** M0 source credentials remain the only source-token authority. A source row's revision identifies the active approved source-config revision; `source_epoch` is a monotonic admission-auth freshness counter, not a business source version or the lifetime authorization for a durable job. Config and mapping revisions have canonical digests. TESTED and APPROVED records bind both digests, the source credential revision, exact schema/delete/version contract and test report. Ordinary credential/config/mapping/owner edits invalidate affected tests/approvals and move an active source to PAUSED/DRAFT before edit. A durable job keeps its immutable, previously approved revision contract through an ordinary edit or pause. An Owner-binding revision change invalidates API-007/API-060 approvals bound to the previous Owner; any Owner-gated action must revalidate the current Owner identity and revision at execution, even when ordinary ingestion under a frozen contract can continue. Explicit revocation for credential compromise/leakage, source-scope removal/leakage, tenant disable, or channel retirement creates a separate durable security barrier and isolates matching unexecuted jobs. Do not blanket-cancel jobs because the admission epoch changed, and do not let frozen jobs bypass a matching security barrier. Routine credential replacement does not mean revocation unless the old credential is explicitly revoked. There is no source delete in Alpha.1.
2. **Lifecycle and capability probe:** DRAFT → TESTED → APPROVED → ACTIVE → PAUSED; resume is a new activation against still-current test/approval revisions. API-006's operation tests only bounded capability: approved endpoint and secret reference resolution, source identity, read-only role, selected object/field shape, mapping validity, version/deletion contract. It does not require or start a full snapshot apply. REST and PostgreSQL probes ship before full snapshot apply. SQL Server stays DRAFT/untestable/inactive until its real adapter can perform the complete approved read-only consistent-snapshot preflight; TCP success is never TESTED. A test result is durable evidence and never asserts enterprise Owner approval.
3. **Controlled secrets/network/SQL:** inject a deployment-owned SecretResolver; accept only configured opaque references in the approved namespace. Never accept secret bytes, local file paths, arbitrary URLs or arbitrary client host/port as a reference. Resolve only in process memory, bound time/size, redact values and references where revealing, and never return them. Endpoint approval and egress allowlisting are a separate control. Before any actual IdP or source capability probe, an approved controlled outbound path and exact endpoint reachability must be supplied and proven; do not broadly widen networks. SQL identifiers come only from frozen validated mappings and individually quoted adapter identifiers; bind all values. No DDL/DML on source systems.
4. **Admission versus durable-job authorization:** intake authenticates and checks tenant/source/credential/entity/config under a caller-owned PoolClient lock immediately before committing durable acceptance. Every admission-relevant change advances `source_epoch`; each accepted item/run stores credential identity, admission epoch, tenant/source/entity, frozen source-config and mapping revisions/digests, immutable channel identity/epoch, and the security-revocation facts current at acceptance. That admission epoch decides whether a new batch may commit; it is not a worker lifetime authorization token. Workers use the stored approved revisions and channel identity, then re-read authoritative current security facts before each apply transaction. Ordinary pause or ordinary endpoint/config/mapping edit stops new admission and leaves already durable jobs eligible to finish under their frozen approved configuration, as PRD §8.6 requires. Explicit credential compromise/revocation, source-scope removal or leakage, tenant disable, or channel retirement creates a durable security barrier for the affected credential/source/entity/channel; the worker must isolate matching unexecuted work even when its frozen config remains valid. Never blanket-cancel because `source_epoch` changed, and never let a frozen job bypass a matching security barrier. Routine planned credential replacement is an ordinary edit only when the old credential has not been explicitly revoked; revocation is separately recorded and cannot be undone by a config edit. Do not add a second token table or auth authority.
5. **Channel identity and single-primary lifecycle:** each entity has at most one active primary synchronization channel for a tenant/source. Current and pending channel identity are immutable tuples including connector, entity, mode/version domain, and monotonically allocated `channel_epoch`. A REST `SOURCE_VERSION` and snapshot `SNAPSHOT_OBSERVATION` are distinct domains and are never compared. First activation can use M1-1's bounded capability probe and exact Owner approval without depending on M1-5; a channel or version-mode switch remains unavailable until the M1-5 reconciliation capability exists. A switch serializes with intake/apply: stop admission on the old channel, drain or isolate its in-flight work, perform and validate a complete initial reconciliation for the pending channel, obtain approval from the exact currently bound Owner for the pending channel/reconciliation digest, then atomically retire the old channel and cut over configuration plus `channel_epoch`. If any pre-cutover step fails, the old current channel remains authoritative and no new epoch is partially active. Old-epoch events are isolated with `CHANNEL_EPOCH_RETIRED`; they are never reinterpreted under the new mode. Canonical object UUIDs survive the switch by the approved identity mapping.
6. **Source auth freshness:** a pause, config edit, ordinary credential replacement, scope update, or lifecycle transition races linearly with new admission: whichever transaction commits first defines acceptance. Jobs accepted before an ordinary transition retain their frozen contract, subject to the independent security barriers above. Apply uses a transaction-scoped current security check against authoritative credential revocation state, tenant/source identity, and channel retirement; it does not require equality with the latest ordinary config epoch. Keep security revocation facts durable and monotonic so a later resume, config edit, or credential replacement cannot erase them.
5. **Canonical apply:** preserve one transaction per customer or complete order aggregate; complete replacement lines set is <=200. Use tenant + source + channel_epoch + entity + source PK as version receipt key. Never accept caller-supplied tenant/source/owner. Resolve external IDs only through approved, revisioned mappings; ownership assignments require explicit mapping/Owner confirmation and epoch bump in the same database transaction. Hash canonical JSON with sorted object keys, preserved array order and null-vs-absent, reject duplicate JSON keys, sort order lines by source line key for entity digest, exclude event/batch IDs from entity digest. Exact decimals remain validated strings; versions remain canonical digit strings/BigInt, never JS Number.
8. **REST durability:** strict /hub/v1/ingest/crm/customers and /hub/v1/ingest/orders/orders; body has 1–100 records and at most 4 MiB, event UUID, source PK, decimal-string source version, RFC3339 offset time, full UPSERT image or null DELETE. Reject repeated JSON property names before schema validation. Commit raw immutable batch, job/items, scoped request digest/idempotency record and processing outbox in one transaction; only then return 202. Same scoped key + same canonical body replays the same job ID; same key with changed canonical content returns 409. 202 records durability, not successful application. Already accepted work continues from its frozen approved config across ordinary pause/edit. Workers check current security barriers and channel retirement before apply; they do not require current `source_epoch` equality. Never return raw payload through job/item read APIs.
9. **Event version semantics:** lower version is IGNORED_STALE; equal version and equal canonical entity content is DUPLICATE; equal version with different content is quarantined; higher version atomically applies full aggregate/tombstone, receipt and outbox. Same source PK/version across batches cannot double-apply. Job terminal state derives from item states: all APPLIED/DUPLICATE/IGNORED_STALE => SUCCEEDED; mixed terminal success/failure => PARTIAL; all rejected => FAILED. Never mark accepted item complete before its aggregate/receipt/outbox transaction commits.
10. **Snapshots/deletes:** one active scan per tenant/source; PostgreSQL starts read-only REPEATABLE READ, extracts customer/order/line rows from one snapshot into durable staging, validates full completeness/unique keys/mappings/amounts/deletion contract before apply. Never apply absence/delete before the whole run validates. Hard-delete candidates require two consecutive successful complete snapshots; partial, failed, stale or invalid runs do not advance candidate counts, observation sequence, checkpoints or deletion state. If a run's candidates exceed 5% of active objects, pause and require the explicit API-060 Owner approval bound to the exact run and digest before deletion. Tombstone/delete receipts remain. Default cursor is FULL_SNAPSHOT every 300 seconds.
11. **Snapshot observation and retry:** where no aggregate source version exists, only a verified full snapshot can allocate server-assigned monotonic SNAPSHOT_OBSERVATION; allocate once after full validation, persist it in the run, and reuse it on recovery/replay. No unchanged content generates a new outbox event. Stage pages and checkpoint processed ranges durably; checkpoint and range receipt commit atomically and do not imply every business row is queryable. Retry delays are 5/30/120 seconds, at most three automatic retries after the initial attempt (at most four starts), using the frozen config/mapping/channel epoch; before each apply, check persisted security barriers. Exhausted/invalid input goes to quarantine with explicit dependency. No partial run reconciles delete candidates.
10. **SQL Server fidelity:** pin exact mssql and resolved tedious lockfile versions only when implementing the adapter; no dependency install in this planning stage. Each configured source owns its pool; use one SNAPSHOT transaction across customer/order/line reads, sequential requests on that transaction, cancel+rollback on errors, discard unusable connection, await close. Preflight requires actual read-only approved-object permissions and ALLOW_SNAPSHOT_ISOLATION=ON; adapter never changes source DB settings. Cast decimal/numeric to text in SQL before TDS; preserve exact decimal strings and 20-digit decimal versions, validate grammar/scale without Number. Never use MAX(rowversion), identity maxima or timestamp as a committed-safe aggregate cursor. Change Tracking is optional only if full header+line version coverage and retention/min-valid checks are proven. No product code/test claim until an owned real SQL Server fixture is available; no EULA acceptance or external deployment.
11. **Independent oracle/acceptance:** synthetic CRM/order fixtures and expected results use independently authored expected rows/amounts, not the same normalizer/query code under test. Run local FI-01..05 injections and compare final rows with independent oracle. Keep source-owner exports/real Oracle, site identity/approval and product acceptance separate. All 48 existing required A/N/FI rows remain NOT_RUN until real evidence.
12. **UI worktree:** after API/schema/envelopes and lifecycle contracts stabilize, inspect the pinned OpenMetadata enterprise extension seam read-only; implement in a new isolated worktree based on its pinned release, preserving the three user clones. Add P02–04 source/mapping/job views against real M1 APIs, not mock-only completion. Keep P01/P05/P12 ownership elsewhere. UI local mock/storybook is usability evidence only; authenticated end-to-end API lifecycle remains necessary.

### Durable-job and channel transition examples

| Event | New intake | Already accepted work | Required persisted decision |
|---|---|---|---|
| REST batch commits under config R, mapping M, channel C at admission epoch E; source is ordinarily paused before worker claim | Denied while PAUSED | Continues under frozen R/M/C if current security facts still permit it | Keep accepted item and frozen revisions; do not reject only because current `source_epoch` differs from E |
| Source is ordinarily edited from R to draft R2 or mapping M2 after the same 202 response | Uses only a separately tested/approved active revision; otherwise denied | Finishes on R/M/C if R/M/C was approved at acceptance and no security barrier applies | Preserve immutable job snapshot; R2/M2 remains ineligible until its own test/approval/activation |
| Per-source Data Owner binding changes after the 202 response | Admission follows current lifecycle and approval | Ordinary frozen ingestion may finish; Owner-gated approval/delete action using the prior binding is denied | Increment owner revision and invalidate API-007/API-060 approvals; revalidate exact current Owner before any Owner-gated action |
| Credential is explicitly revoked for suspected leakage, source entity scope is withdrawn as a security action, or tenant is disabled | Denied | Isolates matching unexecuted work; frozen token/config is not sufficient | Persist typed revocation/disable fact and affected credential/source/entity scope; worker checks it in apply transaction |
| Channel switches from REST `SOURCE_VERSION` to PostgreSQL `SNAPSHOT_OBSERVATION` | Old lane admission stops during switch; pending lane only after cutover | Drain old lane or isolate it; old epoch is rejected after cutover | Reconcile pending lane, get exact Owner approval, atomically cut over config and epoch; old event gets `CHANNEL_EPOCH_RETIRED`; preserve UUIDs |
| Two first activations or two switches compete for one entity's primary lane | At most one transaction wins | Losing operation has no active channel or partially advanced epoch | Serialize on tenant/source/entity primary identity; unique active-primary constraint and one-winner test |
| Pre-cutover reconciliation or approval fails | Old channel remains current and admission resumes only under old valid state | Old jobs follow ordinary/security rules for that still-current channel | Do not partially activate the new epoch/config; pending channel stays inactive for retry |
